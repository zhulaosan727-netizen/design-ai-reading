01 三句话结论

第一，安全产品的体验标准，被 1Password 收成两个词：信任（trust）和确定性（certainty）。用户自动填充登录、在桌面打开保险库，或在浏览器扩展里批准一个 AI 智能体的凭证请求时，每一次提示都要让人清楚：点下去会发生什么。要设计这种确定性，就得在「看起来、用起来都像真产品」的东西上试，而不是在空的、被接线的（wired-up）演示稿上试。

第二，给人读的设计规范，不会自动变成工具会遵守的规则。直到大约八个月前，1Password 的集中式设计系统团队仍主要靠文档和一起讨论，把内容设计（content design）、原则、组件、字体选择和设置流程的理由交给设计师。现在界面越来越多由 Figma Make 和其他智能体生成，这些护栏（guardrails）必须写成工具在执行任务时能取用的上下文：人可以问一句「现在该遵守什么」；智能体接到任务时，也要自己找得到边界。

第三，他们没有把设计师直接推进生产环境，而是建了一座前端专用的原型操场。仓库里是从 Figma 文件和产品参考搭出的各产品代码模板，并配上技能（skills）和规则（rules）。因为有 Code Connect，操场里的编码组件和已发布的 Figma 组件库相对应，把主按钮改成次按钮可以从下拉菜单选，而不必先改 HTML，或向智能体重新口述一遍。Figma Make 改模板时，一次三十处里大约对了八成，剩下的由人收。更大的收益不是速度本身：而是更早对齐、用编码原型做更真实的可用性测试，以及工程师和产品经理也能把原型带到同一块画布上。

02 安全产品的「好体验」，先被定义成信任与确定性

Davey 负责大约 40 人的设计组织，按 1Password 服务的对象分组：安全与 IT 管理员、消费者、开发者。面对这么多对象，一致性本身就是集中式设计系统的工作。但在谈工具之前，他先回答了一个更靠前的问题：安全产品的好体验究竟是什么？

I'd say it's trust and certainty. — Matt Davey

每一次提示，都要清晰到让人确切知道，自己采取行动之后会发生什么。这不是一句可以挂在品牌墙上的话，它会改掉你怎么做原型、怎么做测试。一个「批准智能体使用这组凭证」的弹层，如果只有愉快路径（happy path），测试者点完就被送到预先接好的下一屏，你测到的是演示是否顺畅，不是他在不确定时会不会停下来、会不会误批。信任是在犹豫、核对、拒绝这些动作里被建立或破坏的。

编者点评：设计「确定性」时，最容易偷懒的办法是把说明写长。一长串权限清单看起来很完整，用户却更可能直接跳过。1Password 强调的是：人要在行动之前就知道会发生什么。写给智能体的提示、写给用户的确认文案，其实用的是同一种标准——先说后果，再说细节。如果你自己的产品里有「授权插件 / 授权 Agent / 撤销密钥」这类几乎不可逆的操作，先检查确认层是在说明后果，还是在展示系统设计得有多全。

03 人会读的规范，工具不会自动遵守

Williamson-Cardneau 把信任说成他们一切工作的基础。随着界面开始被即时生成，多年沉淀下来的护栏和最佳实践就变得格外要紧。工具不会因为仓库里躺着一份写得很好的原则文档，就在生成设置向导时，自动引用那条「不要在用户还没看清后果时请求权限」的理由。

转折大约出现在八个月前。此前，设计系统团队提供文档和指引，设计师阅读，再一起讨论。这套做法默认读者是人：人会打开文档，会在评审里问「我们为什么用这级字号」，会在设置流程里感到不对就停下来。智能体不会自动做这些事。于是他们把近二十年的设计指导，转写成工具能用的上下文：内容设计、设计原则、组件，以及每一个字体选择、每一段设置流程背后的理由。

Williamson-Cardneau 把读者写得很清楚：这套上下文既给正在提问的人，也给已经接到任务、正在想「我该怎么完成、我的护栏是什么」的智能体。关键不是再叠一份「给 AI 看的文档」，而是同一套规范要同时服务两种读者。人需要理由，才能在例外里做判断；工具需要在任务发生的那一刻拿得到边界，而不是事后再被纠正回设计系统。

编者点评：这里和读本里谈 DESIGN.md、技能（Skill）的那些篇是同一类问题，但对象更硬：安全产品里，工具一旦绕开规范，后果不是「圆角略有偏差」，而是确认层被写丢、权限被默认勾选、不可逆操作看起来像一次普通保存。把理由一并写进上下文，不是为了让模型学会写得更像品牌手册，而是为了让它在该停的地方停下来提问。

04 不要把设计师丢进生产环境，先搭一座原型操场

直接在生产环境里做原型，对大多数设计师并不现实。环境太重，搭建和维护的成本太高。Williamson-Cardneau 的判断是：它们对设计师来说太笨重，拿不起来。

他们的解法是一座内部原型操场：只含前端的仓库，里面是 1Password 各产品的代码模板，模板直接从 Figma 文件和产品参考搭建。设计师打开操场就能开始，仓库里已经放好技能和规则。有人仍更习惯直接进集成开发环境（IDE）；也有人因为还待在熟悉的 Figma 里，才敢往代码这边走。他提到一个很具体的动作：点进去，改一段文案，改动就在那儿，并且排进队列。人们开始找到各自使用手头工具的新办法。

这座操场不是「把生产仓库的权限开给设计师」的折中。它承认一件更朴素的事：要让更多人用编码原型，先要降低环境的重量。模板已经长得像产品，技能和规则已经在仓库里，人不必先成为这座仓库的维护者，才能试一个新方向。

举一个可以拿回自己产品里用的例子。假如你在做「授权 AI 助手读取账号」的流程，生产环境里可能有真实的鉴权、审计日志和多端同步。设计师为了改一句确认文案而去克隆整套后端，会在第一天就放弃。一座前端操场可以预置几种一定会遇到的状态：待批准的智能体请求、已共享且即将过期的条目、空保险库。人在熟悉的画布里改文案、改组件变体，测的是真实会碰到的状态，而不是去维护一条生产流水线。

05 Code Connect：改组件不必先会改 HTML

因为配置了 Code Connect，操场里的组件和团队已发布的 Figma 组件库是对应的。设计师若要把主按钮改成次按钮，从下拉菜单里选即可，不必钻进 HTML，也不必向智能体描述「请把这个按钮改成 secondary」。

这看起来只是一个小交互，其实是在减少一类很常见的失败：人明明知道设计系统里有正确的变体，却因为改代码的路径太长，只好用提示词再做一次，让模型重新生成一个「看起来像次按钮」的东西。重新生成往往会带上新的间距、新的圆角、新的状态，于是设计系统反而被绕开了。下拉菜单把「选用已有组件」重新变成默认动作。

读本在 No.47 里写过 Coinbase 如何用 Code Connect 给智能体喂设计系统、把令牌（token）成本压下去。1Password 这篇把它从「喂给智能体」转了一面：先让设计师自己能在编码原型里，用跟画布上一样的方式选用组件。智能体不是唯一的读者；人如果没法方便地用对组件，就会用提示词把它绕开，智能体随后也只会学到「绕开」这一条路。

06 一次三十处改动，工具对了八成

Williamson-Cardneau 最近用 Figma Make 更新一款已正式发布产品的模板。他把 Figma 里更新过的界面交给现有的编码模板，再细调个别属性，比如找到一处顽固的内边距（padding），换成正确的设计系统变量。三十处要快速改的地方，工具大约做对了八成，剩下的由他收。他说，他知道工具用的是设计系统的基础（foundations）。

百分之八十不是用来宣传「已经可以放手」的数字。它的意思是：在模板、变量和映射都齐的前提下，机械性的对齐可以由工具先做一轮，人把精力放在那两成——通常是变量没对上、层级被理解错，或某个状态根本不该被改掉的地方。没有 Code Connect、没有变量、没有模板，这八成不会凭空出现；出现了，也不该被误读成可以少看一眼。

编者点评：报出「百分之八十」之后，下一次评审里最该问的不是「能不能再快一点」，而是「那没对上的两成是什么性质」。如果错的是一处内边距，收一收即可；如果错的是确认层被写成了普通按钮、或把主操作默认成了「允许」，这两成就不是边角，而是信任被改写的地方。百分比只能说明批量改动的命中率，不能说明剩下的错误可不可接受。

07 视觉分支：在画布上并排放两个真能点的方向

设计师还可以把几个设计方向做成同一个原型里的开关（toggles），在一处来回切换。Davey 把画布上这一侧的工作称为视觉分支（visual branching）：复制一份原型，做小改动，在画布上并排放在一起比较。他说，这在任何其他媒介里都非常痛苦。

注意他强调的不是「生成很多方案」，而是「并排、可点、改动很小，仍然能比较」。这和在聊天窗口里连续要三个全新版本不是一回事。连续生成往往会一次改掉布局、文案和层级，你没法指出到底是哪一处让信任感上升或下降。视觉分支保留了对照实验的结构：同一条流程，只改确认层的写法，或者只改权限的默认展开方式。

他们也开始尝试代码图层（code layers）：把编码原型直接放到画布上，好让设计师看到并讨论整段用户流程的鸟瞰，而不只是一个能跑的局部，也不必再录一段旁白。Williamson-Cardneau 提到，Figma 智能体能够跟上他在代码图层里的点击，并生成画板（artboard）——流程不再只存在于演示的时间轴里，而能摊在画布上被一起指认。读本在 No.51 里写过代码图层如何让团队在画布上并排试编码原型；1Password 把它用在了「看清整段体验，而不是听一段口播」这件事上。

08 当智能体成为对打的伙伴

对话一旦连上 1Password 的模型上下文协议（MCP），Figma Make 还成了设计上的对打伙伴（sparring partner）。Davey 会来回问：这个和这个放在一起，你觉得成立吗？

It's a sparring partner. — Matt Davey

这不是让模型替他做决定，而是把「这两个决定是否互相冲突」问出口，让另一个能读到当前上下文的对象接话。对打成立的前提是：你手里已经有两个具体的东西——两句确认文案、两种权限默认值、两个并排的分支——而不是一句「请给一个更好的方案」。

编者点评：「对打伙伴」很容易被用成「请直接给一个更好的方案」。后者会把判断交出去；前者要求你先提出一个具体的并列关系。视觉分支也是同一逻辑：先做出可比较的一对，再讨论，而不是先要一个答案。若你发现自己的第一句提示总是「帮我优化这个」，可以先改成「下面两个确认层，哪一个让后果更清楚，哪一处还在打架」。

09 最大收益不是更快，是更早对齐

Williamson-Cardneau 把最大的收益说得相当明确：他们一开始要解决的，不是「能不能更快做完」，而是「如何更早地对想法达成对齐和沟通」。能不能更快走到一个大家都同意的好想法，并且保真度（fidelity）高到足以理解，他们将交到用户手里的价值是什么？

Davey 把这件事重新放回 Figma 一直以来的超能力：画布。他把它比成从前把网站每一页打印出来，贴在白板上——能够把这些界面元素放在一起看，本身就非常有价值。编码之后，沟通早期概念的成本变低了。他们能够展示从前展示不了的微交互（micro-interactions）。

这和「用 AI 加快交付」不是同一件事。加快交付，终点仍是某人的任务做完；更早对齐，终点是一群人在足够真的东西上，一起看清他们准备交给用户的是什么。保真度在这里不是视觉润色，而是：交互是不是真的会发生，状态是不是真的会碰到，后果是不是真的能被看见。

10 空金库测不出信任

保真度接着走进了可用性测试。1Password 已大体上用编码原型，替换了原先接线的 Figma 原型。被试再也不会走到原型的边缘，就被送回愉快路径。对安全产品来说，这种真实程度会改变测试结果。

User testing someone with an empty test vault containing no real credentials is a completely different scenario from giving that user a realistic, populated experience. — Matt Davey

这句话值得当成方法来用。空金库里，搜索不会撞上太多相似条目，共享列表不会显得拥挤，过期项不会冒出来干扰，智能体的授权请求也不会和已经存在的共享叠在一起。你测到的是「界面是否通顺」，不是「人在复杂、略有压力的真实库存里，是否仍然清楚自己在批准什么」。信任和确定性恰恰出现在后一种情境里。

把这个方法放到一个具体任务上。假设你在测「批准一个 AI 助手读取旅行相关密码」。空金库里，列表上只有这一条请求，确认层显得干净，几乎没人会误批。换成一个已经有八十条密码、三个家庭共享、两条即将过期的共享，以及一条上次被拒绝的智能体请求的库，确认层必须在噪声里仍然把「将要发生什么」说清楚。空金库测的是版式，满金库测的是确定性。

编者点评：很多团队并不是不愿意做编码原型，而是测试脚本仍按「空数据、愉快路径、十分钟走完」来写。于是即使用上了更真的工具，测到的仍是演示。改测试，往往比改工具更急：给保险库（或收件箱、权限列表、草稿箱）填上会互相干扰的真实内容；允许被试走到拒绝、核对、返回；不要在边缘把人送回预先接好的下一屏。测不到犹豫，就测不到信任。

11 设计师、工程师、产品经理站到同一块场地

每一位持许可证的设计师都已进入这座操场。工程师在黑客马拉松（hackathon）里先用起来，后来把自己的原型也带到讨论里；产品经理最近用其中一个原型去讲一条路线图。Williamson-Cardneau 把这看成一个相当强的结果，而且远远超出你原本预期谁会一上手就使用设计工具。

操场里放着团队各处开始的原型，每一个都从编码的 1Password 产品模板起步。对设计团队而言，这种工作方式把他们推得更靠近真正会发布的东西。Figma Make 让这一步不那么吓人：在这块新领地上还能看见熟悉的 Figma，有助于设计师相信，自己可以和其他人一起走进来。文章收在一句对仗上：在 1Password，信任不只是他们设计的对象，也是他们带所有人一起走的方式。

熟悉感在这里不是怀旧，是降低进入编码原型的门槛。工具可以换，场地的重量和熟悉程度，会决定谁愿意走进来、谁会把讨论留在各自的文档里。

12 对照表：给人读的规范，和给工具用的上下文

原型像不像真产品接线的 Figma 原型，走到边缘会被送回愉快路径前端编码模板，能展示微交互，也能带上接近真实的数据与状态
比较多个方向多份静态稿，或在不同文件里各做一套，难以控制只改一处同一原型里用开关切换；在画布上复制后做小改动，并排比较（视觉分支）
可用性测试测到什么空测试金库、被规定好的路径，容易显得「都挺顺利」填满的、接近真实的体验；不确定、误批、拒绝这些动作才进得了现场
成功标准常常是「这页做完了 / 这版看起来完整了」更早对齐：大家是否在足够真的东西上，理解将交给用户的价值
谁能加入主要是设计师设计师全部进入；工程师和产品经理也能把原型带到同一块画布
它不自动保证什么不保证工具会遵守你写过的原则不保证那百分之八十的自动改动已经可以发布；没对上的两成仍要人收，而且要看错在哪里

13 可粘贴：规范上下文、原型操场、测试禁令

原文是访谈，不是一份现成的模板。下面把他们反复出现的结构收成三段，方便贴进你自己的设计系统仓库、技能或测试脚本。方括号是你必须填写的决策；填不出的空，就是工具会用「看起来差不多」填上的地方。

① 把设计规范写成两种读者都能用的上下文

本产品在关键路径上要保护的，是：[信任 / 确定性 / 其他，写一句可观察的后果]
人在采取不可逆行动之前，必须先看清：[将要发生什么，而不是一份完整权限清单]

请同时写入给人和给智能体的上下文：
- 与这条路径有关的设计原则，以及为什么（写理由，不要只写口号）
- 必须使用的组件变体，以及内容设计规则
- 明确禁止：不要重新生成「看起来像」的组件；不要跳过确认层；不要在用户还没看清后果时请求权限
- 遇到现有规则覆盖不了的情况：先停下来提问，不要默默做完再演示

人和智能体在动手前都要能回答：我的护栏是什么？任务要是越界，我该问谁？

② 原型操场，而不是生产环境

不要把设计师直接放进生产仓库。先准备一个前端专用、从设计文件和产品参考搭出的模板仓库：
- 每个产品一条可运行的模板，组件与设计库通过 Code Connect 或同等映射对齐
- 预置真实会遇到的状态：[例如：空库 / 满库、待批准的智能体请求、即将过期的共享、上次被拒绝的请求]
- 改已有组件变体必须走属性或下拉菜单，而不是用提示词重做
- 比较方向时，复制后只改一处，在画布上并排，或用开关在同一原型里切换
- 向对打伙伴提问时，先给出两个具体的东西，再问它们放在一起是否成立

③ 可用性测试不得只用空金库和愉快路径

测试任务：[具体任务，例如批准一个 AI 助手读取某类凭证]
禁止：走到边缘就被送回预先接好的下一屏；只用空的、没有真实内容的数据。
必须看到：人在噪声和压力里，是否仍然清楚自己在批准什么；他能否拒绝、能否核对后果。
若编码原型还做不到这些，测试结论只能写成「版式是否通顺」，不能写成「用户会信任这个操作」。

14 自查清单

  • 我把关键路径上的「好体验」写成了可观察的后果（比如人能否在行动前知道将发生什么），还是只写了「要有信任感」？
  • 设计规范的读者是否只是人？智能体在接到任务时，能不能自己找到护栏和理由？
  • 例外出现时，工具是按上下文停下来提问，还是默默做完再让人在演示里发现？
  • 设计师要改一个已有组件变体时，是从下拉菜单或属性里选，还是不得不用提示词重新生成一个「看起来像」的？
  • 我有没有把设计师直接推进过重的生产环境，而不是先提供一座有模板、有规则、有真实状态的前端操场？
  • 比较方向时，我是在画布上并排放两个只改了一处的可点原型，还是在聊天里连续要了三个全新版本？
  • 我把智能体当成对打伙伴时，第一句是在问两个具体决定是否打架，还是在请它「给一个更好的方案」？
  • 工具批量改对了八成之后，我有没有单独看过那两成错在哪里——是边角，还是确认层、默认权限这类会改写信任的地方？
  • 最近一次可用性测试，用的是空金库和愉快路径，还是填满的、允许拒绝和核对的真实库存？
  • 测完之后，结论写的是「界面挺顺」，还是「人在噪声里仍然清楚自己在批准什么」？
  • 工程师和产品经理能不能把原型带到同一块场地，还是讨论仍各自留在文档和幻灯片里？
  • 熟悉的画布是否降低了进入编码原型的门槛，还是新工具把一部分人留在了门外？

16 边界：像真的，不是为了更像演示

1Password 这篇容易被读成又一次 Figma Make 的成功案例。更值得带走的，是他们给「像真的」设下的条件。规范如果只给人读，工具就会在生成时另起一套；原型如果只在空金库和愉快路径上跑，测试就只能证明演示通顺。他们用一座前端操场降低环境的重量，用 Code Connect 让选用已有组件重新成为默认动作，用视觉分支保留可比较的对照，再用填满的体验去测信任。

百分之八十的自动改动、全员进入操场、产品经理用原型讲路线图，都是结果，不是起点。起点是一句更前的定义：在安全产品里，好体验就是人在行动前清楚将发生什么。做不到这一点，工具再熟、原型再快，测到的仍不是信任。

若只记住一件事：规范要写成工具在任务发生时能用的上下文；测试要在像真产品一样被填满的东西上进行。空金库测不出信任。那没对上的两成，尤其要看它改没改写将要发生的事。
