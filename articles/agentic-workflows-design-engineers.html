01 三句话结论

第一，按时间尺度分工，而不是按「哪个模型更强」。回路（Loop）交给 Cursor：亚 100 毫秒的视觉反馈，用来调模态弹簧（modal springs）、画廊错落（gallery stagger timing）、不透明度过渡（opacity transitions）。长弧（Arc）交给 Claude Code：多文件重构、读后端契约（backend contracts）、以及那些一旦自己切换上下文就要丢掉半小时的结构性工作。Claude Code 跑在终端里，任何编辑器或 iTerm 都能接上。一个功能，他最初估 40 小时，这套组合压到了 12 小时。有的日子他会在 Cursor 里待满 8 小时，因为当天全是视觉；有的日子他会并行调度 5 个 Claude Code agent，去重构一套设计系统。

第二，不要用 Claude Code 做视觉打磨（visual polish）。它会把你手调过的动画「改进」成更干净、也更差的东西。Mark 的教训很具体：它把一条手调的 expo.out 缓动（easing）换成了 power2.inOut，只因为 GSAP 文档里后者出现得更勤。代码显得更「正确」，交互却是死的。

第三，精致的一次性提示词挡不住漂移。前两个月，他为每个任务写很长的提示词，约束还是会漂、错误还是会重复。把不变量搬进 CLAUDE.md 之后，一致性立刻改善。Cursor 一侧则用 .cursor/rules/*.mdc，按文件 glob 门控上下文。配置仍然是反应式的（reactive）：它在生成之后抓住问题。他正在做一份 Variable Design Standard，想从规格层减少设计和落地代码之间的碎片化。

概念一句话对 Zhu 的用处
Loop（回路）亚 100ms 的视觉反馈，用来调手感封面母题、卡片 hover、正文栏对齐、动效曲线——这些要自己看见再改
Arc（长弧）跨文件的结构推理，用来改骨架一篇读本入库（封面、正文、articles.json、构建脚本）或一次信息架构调整
Project rules把反复被打破的不变量写成配置，而不是当天的提示词CLAUDE.md / Cursor rules 里写清封面系统、正文栏约束，以及「不要做」
What NOT to do禁令比形容词更能拦住「好心改坏」禁止左侧竖向色条、禁止发明原文没有的数据和引言、禁止未要求就重写邻页

02 Loop 与 Arc：两种时间尺度

Mark 说自己大部分职业生涯都走在设计和工程中间，行业还没给这个位置起名字的时候就已经如此：一边是组件架构（component architecture）和动效设计（motion design），一边是后端契约和交互模式（interaction patterns）。对设计团队偏技术，对工程团队又偏视觉，中间地带并不舒服。这套工作流，就是为「两边都要」的工作准备的。

他随后把工作劈成两种时间尺度。回路是短的、可看见的、必须反馈够快的：模态弹入、画廊错落、透明度过渡，差几十毫秒手感就不对。这类活他放进 Cursor，因为亚 100 毫秒的预览循环，才配得上「调」这个动作。长弧是长的、跨文件的、结构性地往前推的：一次多文件重构、读懂后端契约再改 UI、以及那些若由自己切换上下文，半小时就会耗在找文件上的事。结构性工作由 Claude Code 顶着，人就可以把注意力留在表面（the surface）。

两种尺度不会在同一天以同样比例出现。全是视觉的日子，他就在 Cursor 里待 8 小时；要重构设计系统的日子，他会并行编排 5 个 Claude Code agent。工具选择跟的是任务的时间结构，不是对某个产品的忠诚。

Don't use Claude Code for visual polish. It will "improve" your animation by refactoring it into something "cleaner" that looks objectively worse. — Mark Learst

那次失败值得单独记住。Claude Code 把一条手调的 expo.out 换成了文档里更常见的 power2.inOut。从「代码是否像文档示例」的角度看，它做对了；从「交互是否还活着」的角度看，它把东西弄死了。

The code was more "correct." The interaction felt dead. — 原文

编者点评：读本和个人站正好也有这两种时间尺度。调一张封面的线描、卡片 hover、文章页那一层极淡的 tint，是回路——你得看见，差一点点就不对。新增一篇读本（封面 SVG、正文 HTML、articles.json、跑 build.py、提交）是长弧——跨文件、有契约、不该靠手点来回切。危险在于把两种活交给同一个「请帮我优化」：Agent 很可能会以文档里更常见的缓动、更常见的卡片样式，覆盖你已经手调过的东西。封面系统、正文栏左右对齐、禁止左侧竖向色条，都属于不该被「改进」的手感。

03 为什么配置比一次性提示词更重要

Mark 把反复出现的约束写进项目配置，为的是限制一次性 token、以及那些会把设计系统撕碎的工具函数。他把规则调准，花了几个月。前两个月，每个任务都写很长的提示词，约束照样漂移，错误照样重复。把不变量（invariants）搬进 CLAUDE.md 之后，一致性立刻改善。

Cursor 一侧，规则放在 .cursor/rules/，用 glob 按文件模式门控上下文。他真正在用的一份是 design-system.mdc，作用域是 src/components/**/*.tsx。动画规则三条：始终用 useGSAP() 管生命周期；用 gsap.utils.selector(ref) 防止查询漏到全局；缓动默认 expo.out，离场必须比入场快 30%。token 规则两条：间距走 gap-4（1rem）台阶，禁止随手写 mt-[13px]；颜色走语义 token（他举例 text-monokai-pink），不要直接写十六进制。

每条规则背后都有一次具体的疼：

  • useGSAP() 负责动画清理。写在 useEffect 里、又没有显式清理的动画，卸载后还会活着。他有过一个模态，累积了 47 个孤儿 tween，才被抓到。
  • gsap.utils.selector(ref) 把查询限制在当前组件。没有它，Cursor 会生成 gsap.to('.card', ...)，于是页上每一张卡片一起动。
  • 离场比入场快 30%，来自用户测试：离场如果和入场一样长，会显得拖。

他做过对照实验：一整周不用 .mdc 文件。结果是同一功能里出现 3 种缓动曲线、每次编辑都在漂的任意间距 mt-[13px]，以及一条用了已弃用 TimelineLite 语法的 GSAP timeline。

Claude Code 一侧，CLAUDE.md 先写架构，再写「不要做」。架构很短：做流畅的乐观界面（optimistic UIs）；默认服务端组件，'use client' 只留给交互；动画一律走 GSAP 加 useGSAP()。真正拦住祸事的，是那一组禁令：

  • 不要重构动画代码，除非被明确要求。
  • 不要为了「调试」加 console.log。
  • 不要改缓动。永远不要。
  • 不要通过删掉你看不懂的 aria-label，来「改进」无障碍（accessibility）。
  • 不要新建工具函数。使用已有模式。

最后一条来自一次具体越权：Claude 写了一个 formatDateRelative()，而项目里的 date-fns/formatDistanceToNow 就在三个文件之外，而且已经被引进来了。

编者点评：读本反复出现的「别堆形容词」，在这里变成了工程动作：能被违反、并且你已经违反过的事，才配写进配置。封面画布必须是 1200×750、底色 #E6E6E6、每篇只有一个强调色、卡片和正文禁止左侧竖向色条、不要发明原文没有的数据或引言——这些不宜每次在对话里再恳求一遍。它们该出现在 CLAUDE.md 或 Cursor rules 的「不要做」里。配置不是品味宣言，是一张你已经付过学费的清单。

04 三阶段：Architect → Painter → Auditor

当一个功能同时碰到数据和界面，他走三段。原文里的例子是自动化构建器里的工作流步骤编辑器（workflow step editor）：用户要配置一组可多步的动作序列。

第一阶段，建筑师（Architect），交给 Claude Code。先让它读已有契约和数据形状，再生成一份供人审阅的规格，而且这时候不准写代码。提示词的骨架是：读 src/types/workflow.ts 里的 WorkflowStep 类型，读 src/server/routers/steps.ts 里的 stepRouter，识别必须遵守的 mutation 契约，然后生成 specs/WORKFLOW_STEP_EDITOR.md——里面要有组件层级、乐观更新（optimistic updates）的状态管理思路，以及校验、错误态、并发编辑这些边角。最后一行是硬约束：DO NOT write code. Spec only.

「先不要写代码」把实现挡在规格评审之后。没有这句，Claude 会在你还没认可方案时，先搭出 12 个文件。先读现有契约，规格才有 API 可对齐，而不是凭空发明一套数据结构。

原文给出的规格摘录，大致长成这样：

块规格里实际写了什么
已有契约createStep、updateStep（乐观，出错后重新校验）、reorderSteps
组件层级StepEditor 容器；StepTypeSelector；随 step.type 变化的 StepConfigForm；保存 / 删除 / 复制的 StepActions
状态本地草稿用 useReducer；保存时经 tRPC useMutation 做乐观更新；遇到 409 Conflict（并发编辑）回滚到服务器状态
边角空配置显示占位并禁用保存；中途改类型要确认丢弃已有配置；网络失败则 toast + 重试，并保留草稿

第二阶段，画师（Painter），交给 Cursor。打开那份规格，选中它，Cmd+I 唤出 Composer。他要求按规格搭出 StepEditor，用 GSAP 做切换步骤类型时的面板过渡，并引用 design-system.mdc。手感要求写得很具体：过渡该是灵敏的（responsive），用户不必等动画播完才能继续交互。

生成结果站在了规则一侧：useGSAP()、限定作用域的 selector、缓动 expo.out，过渡时长 0.25 秒，容器间距走 gap-4。他因此把时间花在 reducer 逻辑上——大约 20 分钟，而不是花 2 小时去修动画基本功。

// Painter 阶段实际产物里，GSAP 部分遵循了 .mdc（摘录，非法完整组件）
useGSAP(
  () => {
    const q = gsap.utils.selector(containerRef)
    gsap.fromTo(
      q('.config-panel'),
      { opacity: 0, x: 12 },
      { opacity: 1, x: 0, duration: 0.25, ease: 'expo.out' },
    )
  },
  { scope: containerRef, dependencies: [draft.type] },
)

第三阶段，审计员（Auditor），再交给 Claude Code。视觉工作就绪后，他让 Claude Code 跑这个功能的测试套件：若布局测试或无障碍检查失败，就读错误日志、改组件、再验证，直到全部通过。

失败发生在这里：Claude Code「修好」一次无障碍失败的方法，是删掉一个它看不懂的 aria-label。axe-core 检查通过了，使用屏幕阅读器的人却彻底失去了上下文。他随后补进 CLAUDE.md 的，不是又一句「请注意无障碍」，而是更硬的禁令：不要通过移除 aria 属性来修复无障碍报错；先问。

编者点评：三段的价值不在名字好听，而在每段只准做一种事。建筑师不准写代码，否则你审的是已经铺开的 12 个文件，而不是方案。画师对着规格在回路里调表面，才用得上 .mdc 里那些手感规则。审计员最危险——它有测试当借口，会为了让 axe 变绿而拆掉你看不懂的标签。同一失败模式换到读本或个人站，就是 Agent 为了「更有层次」在卡片或告警左侧加一条色条，或为了让某条 lint 安静而删掉一段你需要的语义标记。先写进「不要做」，比事后在 diff 里生气便宜。

05 失败模式对照

原文把反复踩过的坑写成一组可对照的失败模式。它们不是模型「不够聪明」，而是编排和约束没有跟上班。

失败模式它实际长什么样他怎么挡
上下文窗口耗尽（Context Window Exhaustion）200K token 听起来很大，一旦跨约 40 个文件重构就不够。大约到第 30 个文件，它开始「忘记」CLAUDE.md，把前 20 个文件里已经正确避开的 TimelineLite 又写回来重构按 15–20 个文件分批，每批换一份新上下文
重构陷阱（Refactor Trap）你请它修 Button.tsx 里的一个缺陷，它会「注意到」Card.tsx 有类似模式可以「改进」。你还没看完 diff，它已经动了 8 个文件每条提示都写显式作用域：Do NOT modify any other files. 接受前先核对 diff
导入幻觉（Import Hallucinations）Cursor 从训练数据而不是你的 package.json 里取包。项目用 heroicons，它却从 lucide-react 导入。组件能渲染，图标是错的，到生产环境才发现把明确的包约束写进 .mdc
自信问题（Confidence Problem）他没找到办法让工具的自信程度变成有用的审查信号。隐蔽的竞态条件（race condition）和修一个笔误会用同一种语气每一行仍然自己读
误改无障碍审计阶段删掉看不懂的 aria-label，换来 axe 通过、读屏用户失去上下文；子代理（subagent）被允许「自行修复」时更糟禁令写进 CLAUDE.md；子代理只准报告、不准改文件

子代理用来做他不想亲自成为专家的专项工作，约束却只有一句：报告，不要修复。除非被拦住，Claude Code 会「帮忙」把改动直接做进去。他是在一次无障碍子代理「自主修复」之后学到的：它动了 47 个组件，其中 12 个变得更差。现在每条子代理提示都以 Do NOT modify files 结尾，直到他审完报告。

文档方面，他用 Context7 MCP 拉取包括 GSAP 3.13 在内的现行文档，避免 Claude 沿用 2023 年那些已弃用的 ScrollMagic 模式。无障碍审计则限定在改过的文件上，并再次写明「不要改文件」。报告先到，改动后到。

编者点评：在一个人维护的站点上，重构陷阱几乎是默认事故。你只想改读本卡片 dek 的截断，Agent 却「顺便」重写首页分组、目录样式和相邻文章。显式作用域——「不要修改任何其他文件」——应该成为每条改动提示的结尾，而不是生气时才补的一句。自信问题同样适用：Agent 解释为什么要用某颗语义色，和它解释为什么该重做整页信息架构，语气会一样稳。语气不能当审查信号，diff 才是。

# Animation Rules
- ALWAYS use `useGSAP()` hook for lifecycle management.
- Use `gsap.utils.selector(ref)` to prevent global scope leakage.
- Easing: Default to `expo.out`. Exits must be 30% faster than entrances.

# Token Enforcement
- Spacing: Use `gap-4` (1rem) steps. No arbitrary `mt-[13px]`.
- Colors: Use semantic tokens over hex codes.

# B. CLAUDE.md「不要做」（按原文）
## Architecture
- We build fluid, optimistic UIs.
- Server components by default. 'use client' only for interactivity.
- All animation via GSAP with `useGSAP()` hook.

## What NOT to do
- Do NOT refactor animation code unless explicitly asked.
- Do NOT add console.log statements for "debugging."
- Do NOT change easing curves. Ever.
- Do NOT "improve" accessibility by removing aria-labels you don't understand.
- Do NOT create new utility functions. Use existing patterns.
- Do NOT remove aria attributes to fix a11y errors. Ask first.

子代理：只准报告，不准修改文件。

08 自查清单与诚实部分

用了这套工作流六个月之后，Mark 觉得最难的不是再找一个工具，而是决定何时停止迭代。一段动画还可以再顺 2%，代码也可以再干净一点；工具让「再来一轮」变得非常容易。该不该出货，仍然得自己拍板。

the hardest part is deciding when to stop iterating. — Mark Learst

他也看见过设计师拿起这些工具之后仍然把东西做坏：要把输出约束在已有原语（existing primitives）上，你得先理解这套系统。审查结果，意味着你分得清「代码是对的」和「代码只是能编译」。

项目配置至今仍是反应式的：它在生成之后抓住问题，而不是从一开始就让错误无法发生。他正在做的 Variable Design Standard，想用可强制执行的规格，去处理设计意图和落地代码之间的碎片化，让跨交接、跨工具的漂移变少，也让这些事后补上的纠正性规则渐渐不那么必要。

他最常用的两条脚本，也服从同一纪律。spec 只生成 markdown 规格，不写实现；variant 做出带功能开关的组件变体，而且是加法——旗标关闭时不得改变原有行为。交互实验因此可以在运行时关掉，而不必为了回滚再发一版。

  • 这次是回路（要看见手感）还是长弧（要跨文件改结构）？我有没有把视觉打磨交给 Claude Code？
  • 不变量写在项目配置里，还是只写在今天这段提示词里？
  • CLAUDE.md 或 Cursor rules 有没有「不要做」？里面是不是我已经亲手撤回过的错？
  • 建筑师阶段我有没有写 DO NOT write code？有没有在它搭出一堆文件之前先审规格？
  • 提示里有没有显式作用域：Do NOT modify any other files？我看过 diff，还是只看了那段很有把握的总结？
  • 一次重构是否超过 15–20 个文件？到第 30 个文件时，它会不会开始忘记规则？
  • 子代理是只准报告，还是被允许「自行修复」？上一轮有没有人借无障碍或 lint 的名义删掉重要标记？
  • 它是不是又新建了一个附近已经存在的工具函数？导入的包是项目里的，还是训练数据里更常见的那个？
  • 我继续迭代，是因为东西还没准备好出货，还是因为再顺 2% 太容易？
  • 配置是在事后抓错，还是已经把意图写成可执行的规格？有没有把同一种禁令只停留在对话里、却不写进仓库？

一句话收束：Mark 证明的不是「设计工程师应该同时开 Cursor 和 Claude Code」，而是「两种时间尺度不该混用，反复被打破的约束不该只活在提示词里」。回路用来看见手感，长弧用来推动结构；建筑师先出规格，画师再对着规格调表面，审计员不准为了让测试变绿而拆掉它看不懂的东西。工具会用同一种语气谈论竞态条件和笔误，也会把更常见的缓动当成正确答案。该停下来的时候，仍然得你自己说。
