01 先给结论：三句话读懂评测

第一，Skills 默认触发率不可靠。在 Vercel 的 Next.js 评测里，56% 的用例 Agent 根本没 invoke Skill；默认 Skill 配置通过率 53%，与「完全没有文档」的 Baseline 持平（+0）。

第二，写进 AGENTS.md 的显式指令能把 Skill 拉到 79%，但措辞脆弱。「MUST 先 invoke」vs「先 explore 项目再 invoke」会改变 Agent 锚定顺序，同一 Skill、同一文档，结果差一截。

第三，把压缩文档索引直接写进 AGENTS.md，通过率 100%（Build / Lint / Test 全满分）。从约 40KB 压到 8KB 仍保持 100%。对框架横切知识：被动上下文目前优于按需检索。

02 问题：训练数据跟不上 Next.js 16

编码 Agent 依赖的训练数据会过期。Next.js 16 引入的 'use cache'、connection()、forbidden() 等 API 还不在当前模型训练分布里——Agent 要么写出错误代码，要么退回旧模式。

反过来也成立：你还在跑旧版 Next.js，模型却建议尚不存在的新 API。Vercel 想解决的是：给 Agent 与项目版本匹配（version-matched） 的文档访问权。

和设计侧同构：模型「见过很多仪表盘」，不等于见过你仓库的 token、组件名、以及 Zhu「禁止左侧竖向色条」硬规则。框架 API 缺口与设计系统缺口，都是 pre-training-led reasoning 的失败模式。

03 两条路：Skills vs AGENTS.md

Skills（按需）AGENTS.md（持久）
形态打包 prompts / tools / docs，Agent 识别需要时 invoke项目根目录 Markdown；每回合可用，无需决定是否加载
类比工具抽屉：用时打开工作台铭牌：始终在眼前
上下文开销理论上更省（只在需要时）始终占用；必须压缩
失败点「该不该查」的决策写太长导致噪声
Claude Code 对应SkillsCLAUDE.md 同类机制

团队先押注 Skills：干净的关注点分离、最小上下文开销、skills.sh 上可复用目录看起来很对。然后他们跑了 eval。

04 Skills 默认几乎等于没装

配置通过率相对 Baseline
Baseline（无文档）53%—
Skill（默认行为）53%+0pp

56% 的用例里 Skill 从未被 invoke。文档在环境里，Agent 就是不用。更糟：在 Build / Lint / Test 细项上，默认 Skill 有时比 Baseline 更差（例如 Test 58% vs 63%）——闲置 Skill 可能引入噪声或分心。

这不是 Vercel 独有：当前模型「不可靠地使用可用工具」是已知限制。设计侧同理：你装了 frontend-design Skill，但 description 路由弱、或任务表述不像触发词，Agent 会直接用训练平均「好看界面」开干。

05 显式指令能救，但措辞很脆

他们在 AGENTS.md 里加了显式指令，例如：先探索项目结构，再 invoke nextjs-doc Skill。触发率升到 95%+，通过率到 79%（+26pp）。

指令措辞行为结果倾向
「You MUST invoke the skill」（先读文档）先锚定文档模式易错过项目上下文
「Explore project first, then invoke skill」先建心理模型，文档当参考更好

原文举 'use cache' 评测：invoke-first 写出正确的 page.tsx，却完全漏掉必需的 next.config.ts 改动；explore-first 两边都拿到。

同一 Skill、同一文档、措辞微调 → 行为大幅摆动。这种脆弱性让「靠指令催 Skill」难以放心上生产。

短引用（Jude Gao / Vercel）：措辞脆弱性是他们担心 production 可用性的核心原因之一。对 Zhu：别指望「记得先读 DESIGN.md」这类一句软提醒——要么被动塞进 AGENTS.md，要么接受触发失败。

06 评测怎么硬化才可信

早期套件有模糊 prompt、测实现细节而非可观察行为、以及测「已在训练数据里」的 API——测不到真正关心的缺口。硬化手段包括：去掉 test leakage、消解矛盾、改为 behavior-based assertions，并专门加入训练数据外的 Next.js 16 API。

聚焦套件覆盖的 API 包括：

  • connection()（动态渲染）
  • 'use cache' 指令
  • cacheLife() / cacheTag()
  • forbidden() / unauthorized()
  • proxy.ts
  • 异步 cookies() / headers()
  • after()、updateTag()、refresh()

后文所有数字都来自这套硬化评测；各配置同一测试，并重试以降低模型方差。

07 赢家：AGENTS.md 压缩文档索引

关键直觉：去掉「该不该查」这个决策点。不是把全文塞进 AGENTS.md，而是塞一份索引——告诉 Agent 去哪里找与当前 Next.js 版本匹配的具体文档文件；需要时再读 .next-docs/ 里的文件。

注入内容里的关键指令：

IMPORTANT: Prefer retrieval-led reasoning over pre-training-led reasoning
for any Next.js tasks.
配置通过率相对 Baseline
Baseline（无文档）53%—
Skill（默认）53%+0pp
Skill + 显式指令79%+26pp
AGENTS.md 文档索引100%+47pp
配置BuildLintTest

Skill（默认）84%89%58%

「笨」办法（静态 Markdown）打败了更「聪明」的 Skill 检索——即使已经微调了触发指令。

08 为何被动胜过主动检索

原文工作假设三点：

  1. 无决策点。AGENTS.md 没有「我要不要查一下？」的瞬间；信息已在场。
  2. 持续可用。Skills 异步、且仅在 invoke 后加载；AGENTS.md 内容在每回合的系统侧上下文里。
  3. 无排序问题。Skills 会制造「先文档还是先项目」的序列决策；被动上下文整段绕过。
主动（Skill）路径：
  任务 → 是否 invoke？→（常跳过）→ 预训练瞎写
                 ↓（偶成功）
              读文档 → 仍可能顺序错

被动（AGENTS.md）路径：
  任务 + 索引已在场 → 按索引读 .next-docs/ → 版本对齐代码

09 上下文膨胀：40KB → 8KB 仍满分

把文档嵌进 AGENTS.md 的代价是上下文膨胀。他们把初始约 40KB 压到 8KB（约 80% 削减），通过率仍 100%。压缩格式是 pipe-delimited 索引，指向可检索文件，而不是全文：

[Next.js Docs Index]|root: ./.next-docs
|IMPORTANT: Prefer retrieval-led reasoning over pre-training-led reasoning
|01-app/01-getting-started:{01-installation.mdx,02-project-structure.mdx,...}
|01-app/02-building-your-application/01-routing:{01-defining-routes.mdx,...}

Agent 知道文档在哪，但不把全文常驻上下文；需要时读 .next-docs/ 对应文件。

设计侧可抄作业：AGENTS.md 里不要贴整本设计规范。贴「token 文件路径 + 组件目录 + 硬禁令三行 + Prefer design-system files over training averages」的索引式短文，需要时再 Read 具体 token / 组件文件。

10 一键接入：npx agents-md

npx @next/codemod@canary agents-md

官方 @next/codemod 包能力，三件事：

  1. 检测你的 Next.js 版本
  2. 下载匹配文档到 .next-docs/
  3. 把压缩索引注入 AGENTS.md

尊重 AGENTS.md 的 Agent（如 Cursor 等）同一套路可用。

11 对框架作者与 Zhu 的分工建议

Skills 并非无用。原文分工：

AGENTS.mdSkills
适合横向（horizontal）框架知识，几乎每个任务纵向（vertical）显式工作流
例子版本匹配 API 索引、硬护栏upgrade Next、migrate App Router、专项 best practices
用户动作装一次即可用户 / Agent 明确触发更稳

实践建议（框架作者，也可映射到设计系统维护者）：

  • 别干等 Skills「工具使用变好」——现在就要结果。
  • 激进压缩：索引指向可检索文件即可。
  • 用 eval：专门测训练数据外的 API / 规则。
  • 为检索而设计文档结构：让 Agent 能定位单文件，而不是必须一次吞全书。

目标一句话：把 Agent 从 pre-training-led reasoning 推到 retrieval-led reasoning。目前最稳的载体是 AGENTS.md。

# 自查清单
[ ] 框架 / 设计系统「几乎每任务都要」的知识：是否已在 AGENTS.md？
[ ] AGENTS.md 是否索引化（路径列表），而非贴全文？
[ ] 体积：能否压到个位数 KB 级仍可检索？
[ ] 纵向流程（升级、迁移、专项审查）是否做成 Skill 而非撑爆 AGENTS.md？

[ ] Skill 的 description 是否带触发词？默认触发率你测过吗？
