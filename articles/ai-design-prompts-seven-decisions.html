01 先给结论：三句话读懂这篇

第一，有用的 AI 设计提示是一份压缩版 design brief（设计简报），不是情绪词清单。「干净、现代、高级」只点了 mood（情绪），没定字体、色板、密度、空表长什么样——空缺会被工具默认值填满，于是长出熟悉的 AI 脸。

第二，七项决策让输出可复核（reviewable），而不只是可评价（judgeable）。User & job → Screen & real content → Visual thesis & reference → Type & color tokens → Layout → Components / states / motion → Guardrails & acceptance checks。同事能就某一行和你争论，才算写够具体。

第三，迭代一次只动一项，并显式写出 DO NOT CHANGE。修密度时顺便「暖一下色板」，最容易把整页带跑；scoped edit（作用域编辑）是对抗漂移的纪律，不是工具保证。

写法模型听到的你能验收的
形容词堆mood + 大量开放决策「好像不够高级」——不可证伪
七项决策 brief受众、真内容、tokens、布局、状态、禁令「1440px 能否看见 ≥14 行」——可勾选
有 mood + 无锚定仍可能滑向默认卡片栅格需要补 reference / hex / 排除项

02 为什么「干净、现代、高级」交不出界面

原文借用社区语言（vibecoding / Cursor / Wix 等讨论作「问题形状」的旁证，非基准测试）：人们要 cool and professional，却不点名字体、圆角、密度；结果是挤布局、卡片过多、默认 Tailwind、弱层级。模型侧也同构：Anthropic 提示指南提醒，缺少具体转向时 Claude 易收敛到通用前端模式；OpenAI 前端提示指南则强调按受众与领域定制 layout / components / style，而不是吃通用视觉默认值。

形容词不是禁词。「Editorial」「brutalist」「warm」可以定 mood——但必须立刻兑成字体、色值与参考。形容词是方向，决策是目的地。

诊断篇见 No.05 / No.24；本篇是处方：把开放决策一项项关掉。Zhu 的硬规则也可写进 Guardrails：例如禁止卡片/告警左侧竖向色条（border-left accent bar），改用标签、图标或顶边强调。

03 七项决策：从用户到验收

  1. User & job：谁看这屏、要完成什么事。「我的 App 仪表盘」等于没说；「客成经理周一早晨决定先打哪些客户」已经暗示密度与克制。
  2. Screen & real content：钉死一屏，写入真标签、可信数字、可上线文案。Lovable 也强调用真实内容、按组件推进；Lorem 会把层级问题藏起来。
  3. Visual thesis & reference：一句话方向 + 双方都懂的参考（「更像体育杂志而不是 SaaS 模板」）。形容词在这里才值钱。
  4. Type & color tokens：点名字体、字号、hex，并给用法规则。强调色没有规则就会到处出现。
  5. Layout & composition：谁占据视口、怎么分栏。「表格是英雄、全宽；筛选在 220px 左栏；首屏不要卡片」——否则模型常替你做成三张居中卡。
  6. Components, states, motion：列出组件，再写 empty / loading / error / hover 的真文案；加一条动效规则（可以是 none）。屏幕最常在无人提示的状态里崩。
  7. Guardrails & acceptance checks：排除项（不要 KPI 卡片栅格、不要紫渐变、圆角不超过 8px）+ 验收句（1440px 至少看见 14 行）。提示够不够具体：同事能否就它争论。

04 Master template：把括号填成决策

原文模板把七项收成可粘贴块：Build [screen] → USER & JOB → CONTENT（禁用 lorem）→ DIRECTION / Not → TYPE / COLOR → LAYOUT → COMPONENTS & STATES → ACCESSIBILITY & RESPONSIVE → AVOID → ACCEPTANCE。每一个你填不出的括号，都是模型会替你做的决定。

An adjective is a direction; a decision is a destination. — v-1.design（大意：形容词是方向，决策才是目的地）

05 三类范例各自押什么

三例体裁不同，但每一行都可复核。模式摘要（非全文照搬）：

体裁押注的决策典型 Guardrail / Acceptance
SaaS 风险账户表表格英雄、交易终端密度、风险红有职责禁 KPI 卡栅格；1440px ≥14 行；红只标风险
夜间日记移动端安静、单手、纸本灯感；反游戏化禁火焰连胜、亮蓝链；最亮元素是正在写的字

Acceptance 行的作用：把「做好看」换成十秒能勾选的检查。

06 迭代纪律：一次只改一项

实务失败模式：修一处，其它几处被悄悄重绘。推荐纪律（原文称为建议，非工具保证）：

  1. 对照 acceptance checks 验收，不靠 vibe。
  2. 点名失败的那一项（密度 / 强调色用法 / 字阶）。
  3. 发 scoped edit：精确重述该项，钉死其余不变。
The table is too airy: only 8 rows are visible at 1440px.
CHANGE: row height to 40px, base font to 13px, remove vertical padding on the summary strip.
DO NOT CHANGE: fonts, colors, the filter rail, column order, or any copy.

两项都错就发两条提示；合并「修密度 + 暖色板」常会邀请超范围改动。

07 工具手记：同一 brief，不同包装

  • v0：有参考图就连同书面 brief 一起附上，别靠回忆描述。
  • Lovable：开放请求可能先探索最多约三个方向；字体/色/参考/具名 DS 写全时可跳过探索，直接建。
  • Bolt / Replit：启发式——首条消息放 brief，结构大改时重述相关 guardrails；仍用同一套 acceptance 验收。
  • Cursor：规划先行、目标具体；仓库里可用 tokens 文件 + 参考组件承载决策 4–7。
  • Claude Code / Codex：同一书面验收标准 + 现有 tokens + 参考截图；跑完检查后要求汇报视觉缺口。

Brief 可移植；期望各工具吐出一模一样像素则不可移植。

08 和 No.29 / No.05 / No.24 怎么排

  1. No.05 / No.24：诊断——为何会落到可互换的 AI 脸与平均水准。
  2. No.29 四维提示词：把前端拉出默认脸的另一套结构；与七项决策可叠加，不必二选一。
  3. No.13 TC-EBC：Figma 侧「备菜式」提示纪律，偏生成控制；本篇偏界面 brief 完整性。
  4. 本篇：把「可争论的决策清单」写成可粘贴模板，并强调 acceptance 与 scoped iteration。

09 可粘贴：缩短版中英对照模板

Build [屏幕] for [产品], a [一句话产品说明].

USER & JOB: [谁] uses this to [任务]. Optimize for [最重要的事].

CONTENT（必须用这些，禁止 lorem）:
- [真标题 / 列名 / 数字 / 按钮文案]

DIRECTION: [一句视觉主张]. Reference: [风格 / 产品 / 体裁].
Not: [绝不能像什么].

TYPE: [展示字体] for [用途]; [正文字体] for [用途]. Base [n]px.
COLOR: bg [hex], text [hex], accent [hex]. Accent only for [规则].

LAYOUT: [栅格 / 栏], [密度], [谁占据视口].

COMPONENTS & STATES: [列表]. Include empty / loading / error / hover.
Empty: "[真文案]". Motion: [一条规则或 none].

AVOID: [3–6 条具体排除，可含：no left accent bars].
ACCEPTANCE: [2–3 条可验证检查].

10 自查清单

  • 我的提示里，形容词有没有立刻兑成字体 / hex / 参考？
  • 七项里哪一项仍是空括号——是否准备让模型替我决定？
  • 内容是真货还是 lorem？空状态有没有真文案？
  • 强调色有没有「只用在何处」的规则？
  • Guardrails 是否具体到同事能反对（而不只是「不要太俗」）？
  • Acceptance 能否在十秒内勾选？
  • 这次迭代是否只改一项，并写了 DO NOT CHANGE？
  • 换工具时，我改编的是包装，还是偷偷改了决策本身？

一句话收束：别再向模型索要「高级感」——向它交付七项可复核决策。Mood 可以留一句；其余用用户与任务、真内容、视觉主张、tokens、布局、状态与禁令、验收句钉死。提示够不够好，不看形容词密度，而看同事能不能就某一行和你吵架，以及你能不能在十秒内说「过」或「不过」。
