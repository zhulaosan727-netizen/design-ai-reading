在 Thinkmill，我们一直在帮助设计系统团队采用 AI 辅助设计与开发。如今，这项工作很大一部分都围绕一个核心问题展开：如何配置 AI 智能体，才能产出真正有用的成果？

关于 AI 的文章大多聚焦于炫目的演示或宏大的预测。我想知道团队如今实际是怎么工作的。于是我在网上搜集资料，观看了数小时对 Stripe、Shopify、Ramp、Atlassian 和 Intercom 的设计师与工程师的访谈。每位受访者都介绍了在 AI 加入之后他们的设计流程。

我发现每个团队都在三个关键方面投入了精力：

  1. 一个做原型的地方
  2. 一种为 AI 提供正确上下文的方式
  3. 帮助大家采用这两者的工作

以下是基于发稿时公开信息整理的各团队做法概览：

  • Atlassian 使用 Figma Make 和 Replit 等现成工具，并配合经过精细调整的设计系统文档。
  • Intercom 借助 Claude Code、Figma Code Connect 和 Figma MCP server，直接在生产代码库中做原型。
  • Stripe 自建了原型环境 Protodash，它运行在生产环境之外的独立环境中。
  • Shopify 使用名为 Quick 的内部工具包，以及一个镜像其管理后台界面的 playground。
  • Ramp 自建了名为 Inspect 的定制平台，用于在生产环境中处理 bug 修复和客户反馈。

一个做原型的地方

分道扬镳的做法

这五个团队在原型方面的做法有两点不同。

自研工具 vs 现成工具

首先要看团队是自研了原型工具，还是选用了现有工具。Stripe 和 Ramp 投入建设了内部平台。Atlassian 则更依赖 Figma Make 和 Replit 这类产品。Intercom 和 Shopify 介于两者之间，既有自己的工作流，也有自己的集成。

有的团队投入配置现成工具，有的团队则打造定制工具，两种做法并存。

沙箱隔离 vs 直连生产环境

其次是原型离生产环境有多近。Stripe 似乎把 Protodash 隔离在沙箱中，但它基于真实的设计系统构建，因此设计师在评审中发布的内容，就是工程师可以直接接手的代码。Ramp 走得更远，直接在生产环境的一个分支上做原型。两种做法产出的原型都足够真实，让人愿意信任。

在如何将原型设计融入开发流水线上，各个设计团队的态度各不相同。

趋同的功能

尽管原型搭建方式各异，许多团队和工具却在趋向相似的功能。这些功能都旨在让设计沟通更轻松，帮助大家更早达成一致，并快速探索想法。

可分享的托管 URL 与 CLI 命令 & 辅助工具

这五个团队都为设计师打造了一个安全的空间，用来存放和分享原型。组织内的任何人都能直接在浏览器中查看原型，无需安装任何软件，也无需搭建本地环境。

Intercom 和 Shopify 为原型创作者提供了 CLI 命令，优化了原型的发布流程。

控制面板 UI

另一个常见功能是用于控制应用状态的 UI 面板。原型创建者和评审者无需重建原型，就能在空状态与有数据状态之间切换、用杂乱的数据测试、预览另一种语言，或者对比查看界面对初创公司和企业客户的表现。这让原型更加实用，因为它能针对常见的用户场景，快速检验设计的健壮性。

保真度控制与基于规则的输出调整

Stripe 和 Shopify 会刻意表明工作尚未完成。早期概念以灰度显示，或使用不符合品牌风格的 UI 组件，让评审者自然地把它们当作早期原型，而不是可以直接发布的精致设计。

为了便于设计评审，Stripe 和 Shopify 都把评论功能直接内置到了原型中。AI 会汇总反馈，然后根据所提出的修改意见采取行动。Atlassian 则借助 Figma Make 实现了类似的功能。

原型工具与自研工具的功能对比。上表省略了 Atlassian，因为他们使用的是 Figma Make。

这些想法中的每一个，都为设计原型的制作过程减少了一点摩擦。

上下文决定成败

[大语言模型（LLM）] 会凭空想象出整个设计系统，而且在设计系统并不存在时也不会告诉你。——Owen Williams，Stripe 工程师

如果说原型环境是工作发生的地方，那么上下文就决定了成果的质量。

这是五支团队中最突出的共同规律。AI 生成成果的质量，取决于它所获得信息的质量。每支团队都投入精力，在设计系统、项目和客户三个层面提供上下文。

设计系统上下文

设计系统上下文是大多数团队投入精力最多的地方，这也理所当然。难点在于幻觉。正如 Stripe 的 Owen Williams 所说，大语言模型（LLM）“会凭空想象出整个设计系统，而且不会告诉你它其实并不存在”。即便输出建立在根本不存在的组件之上，看起来往往也很可信。陷阱在于，这样的成果看上去已经完成，团队便在其上继续构建，等到有人要发布真正的产品时，才发现组件并不存在，或者用法根本不是那样。

好几支团队都遇到了同样的局限。设计令牌（design token）能比较顺利地转换给 AI 工具使用，而组合真正的组件则困难得多。

Atlassian 直接从组件包生成指令文件，但只向模型开放精心挑选的一小部分，把范围收窄到 20 到 30 个组件，并为每个组件配上清晰的示例。他们发现，上下文越多，结果往往反而越差。他们还为每个组件建立了一张“从 Tailwind 转换”对照表。由于语言模型见过大量 Tailwind 和 React，Atlassian 让模型先用熟悉的概念去思考，再把这些概念映射回正确的设计系统组件。

Intercom 在整个组件库中使用 Figma Code Connect。AI 不再从零重建组件，而是拿到生产代码库中真实的导入路径，基于现有的组件工作。

Stripe 通过 MCP（模型上下文协议）服务器提供其设计系统，并要求 AI 在编写任何代码之前先查询该服务器。同样重要的是，他们还定义了服务器不可用时该怎么做，让模型如实报错，而不是信誓旦旦地编造答案。

这些做法背后的原则是一致的：当 AI 能依赖可信的事实来源，而不是自己去填补空白时，表现会更好。我的同事 Joe Prisk 在文章 Why your design system is the most important input to Claude Code 中探讨过这一点。尽管出发点各不相同，这些团队都把现有的设计系统用作 AI 原型工具的上下文。

项目上下文

项目上下文要简单得多：它就是项目简报、需求和工作背景。Stripe 的设计师会把产品需求文档直接从 Google Docs 粘贴到原型里。一些 Shopify 的设计师会在每个项目旁边放一小批 markdown 文件，让模型在生成任何内容之前，就先拿到正确的上下文。

客户上下文

在 Ramp，设计师的起点是了解客户正在经历什么。他们会在 LogRocket 中查看会话录屏，使用内部工具汇总用户遇到困难的环节，并用 Notion AI 查询研究访谈记录。这些洞察既会影响原型，也会影响生成原型所用的提示词。

这些工作大多仍靠手动完成。设计师自己阅读研究资料、识别规律，再把这些洞察带入原型制作过程。

围绕设计系统和项目上下文逐渐形成的那套规范，同样可以用于理解客户。随着这些工作流日益成熟，AI 获得的将不只是界面应该如何构建的更好信息，还有关于其服务对象的更好信息。

推动采用

这些工作流中最不显眼的部分，可能恰恰最重要。

设计团队汇聚了技术背景迥异的人。有些设计师从未打开过代码编辑器，有些则熟练使用 Git 和命令行。哪怕是设置权限、安装工具或部署原型这样的小障碍，也可能让人在真正开始工作之前就止步。我观察的这些团队并不把这当作事后补救。他们对培训的投入，与对工具的投入同样用心。

在 Shopify，CEO Tobi Lütke 明确提出期望，使用 AI 将成为人们工作方式和绩效考核的一部分，此后 AI 的采用明显加速。Intercom 的推动力来自其 CTO 和设计负责人。Atlassian 举办了全公司范围的“AI Builder Week”，据其介绍，数千名员工暂停日常工作一周，专门学习 AI 原型制作。

采用得最好的团队还让大家很容易互相学习。Intercom 搭建了一个 Prototyping Hub，提供实用资源，包括一份通俗易懂的“面向设计师的 Code 101”指南和分步视频。Shopify 内部维护着一个原型画廊，同时有一个可供他人复用的共享提示词库。Atlassian 甚至发现，邀请大家加入 Slack 频道的效果并不理想，而发送群组私信则能带来强得多的参与度。他们据此做了一个小型机器人。

更广泛的启示是：对工具的投入和对人的投入必须同步推进。如果只有少数人有足够的信心去使用，再精密的原型环境也发挥不了多大作用。

首先要做好什么

进展最快的团队有一个共同点：在 AI 进入工作流之前，他们就已经拥有了成熟的设计系统。设计系统的意义，始终是让一个团队的决策清晰明确，并能被其他所有人复用。设计令牌（design token）、组件、文档和指南的存在，都是为了帮助大家保持一致地构建。这项工作我们已经做了十多年。AI 智能体只是同样需要这种清晰性的又一类“使用者”。如果你正在思考这对你的团队意味着什么，我们随时乐意一起探讨。
