01 先给结论：三句话读懂这篇

第一，五家团队路线各异，但都投资了同样三件事：一个做原型的地方（somewhere to prototype）、一套给 AI 喂对上下文的方式、以及帮人真正用起来的功夫。

第二，决定 AI 产出质量的，不是工具，而是上下文。其中最费力、也最见效的是设计系统上下文：不给可信的「事实来源」（source of truth），模型就会编造一整套并不存在的组件，而且看起来很像真的。

第三，跑得最快的团队，在 AI 之前就已经有一套强设计系统。设计系统本来就是为了让一个团队的决定清晰、可复用；AI Agent 只是这份清晰的又一个读者。

02 这篇是怎么来的（以及它的局限）

作者 Jordan Geizer 在澳大利亚的设计与工程咨询公司 Thinkmill 工作，日常帮设计系统团队落地 AI 辅助设计与开发。他发现关于 AI 的文章大多是炫目演示或宏大预测，于是去搜集了这五家公司设计师和工程师的公开访谈，看了好几个小时，整理每家「现在实际怎么工作」。

这意味着两点。好处是：样本都是一线大厂的真实流程，不是厂商宣传稿。局限是：信息来自公开资料，作者也注明是「发表时」的状态；具体工具名、比例会很快过时，真正值得带走的是结构——下面的整理也按这个思路来。

读这类「大厂怎么做」的文章，编者建议你盯住「为什么这样设计」而不是「用了哪个工具」。工具半年一换，但「先查设计系统再写代码」「早期稿故意做成灰阶」这种做法背后的道理，换什么工具都成立。

03 五家团队快照

团队原型环境离生产多近值得记住的做法
Atlassian现成工具：Figma Make、Replit，加上精调过的设计系统文档独立于生产只给模型 20–30 个精选组件；做了「从 Tailwind 翻译」对照表

04 两条分歧：自建还是现成，沙盒还是接生产

原文指出五家的原型做法在两个维度上分道扬镳。

自建 vs 现成（hand-rolled vs off-the-shelf）。Stripe 和 Ramp 投资了内部平台；Atlassian 更依赖 Figma Make、Replit 这类产品；Intercom 和 Shopify 居中，有自己的工作流和集成。

沙盒 vs 接生产（sandboxed vs wired to production）。Stripe 看起来把 Protodash 隔离在沙盒里，但用真实设计系统搭建，所以设计师在评审里展示的，就是工程师可以接手的那份代码；Ramp 更进一步，直接在生产的分支上做原型。两种方式都让原型「真到足以让人信任」。

编者把两条轴交叉成一张选择表，帮你判断自己的团队适合哪一格：

沙盒（安全、自由试错）接生产（真实、可直接交付）
现成工具起步最快，适合设计系统还不成熟、想先培养习惯的团队（接近 Atlassian）需要代码库本身整洁、组件有映射（接近 Intercom 的 Code Connect 路线）
自建平台前期投入大，但可以把设计系统、发布、评论都内建进去（接近 Stripe）门槛最高，要求工程文化强、权限与评审流程清楚（接近 Ramp）

值得补一句：Notion 的设计师 Brian Lovin 公开分享过，他们的共享原型仓库之外，越来越多设计师开始直接在生产代码里用功能开关（feature flag）做原型——说明「沙盒 → 接生产」可能是随着模型变强而自然迁移的方向。

05 四个趋同功能

路线不同，功能却在趋同。原文列了几类，它们都在做同一件事：让设计讨论更容易、让大家更早对齐、让探索更快。

功能原文里的做法解决什么问题编者的例子
可分享的托管 URL + CLI 发布五家都有安全的原型存放与分享处；Intercom、Shopify 给创作者 CLI 命令任何人点开浏览器就能看，不用装环境一条 publish 命令输出链接，贴进评审文档
状态控制面板（control panel）一个切换应用状态的 UI 面板不重建原型就能测空状态、脏数据、多语言、小公司 vs 大企业右下角浮层：空列表 / 1 条 / 1000 条 / 超长名字 / 德语
保真度信号（fidelity control）Stripe、Shopify 把早期概念做成灰阶，或故意用非品牌组件评审者自然把它当早期稿，不去抠细节「探索」模式全局灰阶 + 系统字体；「定稿」模式才加载品牌主题
原型内评论 + AI 汇总Stripe、Shopify 在原型里直接评论，AI 汇总后执行修改反馈不散落在 Slack，修改闭环更短评论按主题聚类，AI 先列「准备怎么改」，你确认后再动

「保真度信号」是这篇里最被低估的一招。AI 让高保真变得太便宜，结果早期讨论总被拉到文案和像素上——Google 设计师 Katie Jacquez 在另一篇文章里把这叫作「过早打磨」。用灰阶和非品牌组件主动「降级」，是在用视觉语言告诉评审者：现在讨论结构，不讨论表皮。

06 上下文决定质量：设计系统、项目、用户

如果原型环境是干活的地方，上下文就决定活的质量。这是五家里最强的共同模式，作者分成三层。

设计系统上下文：对抗「一本正经地编造」

“[An LLM] will just imagine the entire design system without telling you when it’s not there.” — Owen Williams，Stripe（原文引述）

陷阱在于：产出看起来很完整，团队就在上面继续搭，直到有人要上线时才发现那个组件根本不存在，或者行为不一样。几个团队都撞上了同一个限制：设计令牌（design tokens）迁移给 AI 相对容易，组合真实组件要难得多。三家的解法各有侧重：

团队做法背后的原理
Atlassian从组件包自动生成指令文件，但只暴露 20–30 个精选组件，每个配清楚的示例；他们发现上下文越多结果往往越差。另做一张每个组件的「从 Tailwind 翻译」对照表少而精胜过大而全；让模型先用它最熟悉的 Tailwind / React 思考，再映射回自家组件
Intercom整个组件库接 Figma Code Connect，AI 拿到生产代码的真实导入路径不让模型「重画」组件，只让它「引用」组件
Stripe设计系统通过 MCP 服务器暴露，要求 AI 写代码前先查询；还规定了服务器不可用时该怎么办让模型诚实失败，而不是自信地编造

三者的共同原则是：AI 能依赖可信的事实来源时，表现比让它自己填空好得多。

项目上下文：最简单，也最容易漏

就是需求简报、要求和背景。Stripe 的设计师把 Google Docs 里的 PRD 直接粘进原型；部分 Shopify 设计师在每个项目旁放几份 markdown 文件，让模型生成前先读到正确背景。

用户上下文：目前还主要靠人工

Ramp 的设计师从理解客户体验出发：在 LogRocket 里看会话录像，用内部工具汇总用户卡在哪，用 Notion AI 检索研究访谈记录，再让这些洞察同时塑造原型和生成原型的提示词。作者指出这部分大多仍是手工的，并预期它会像设计系统上下文一样被规范化。

对追求独特审美的设计师，这一节有个反直觉的启示：Atlassian 发现「上下文越多越差」。你的风格指南、参考图、规则文件也一样——给 Agent 一份 30 页的品牌手册，不如给它 10 条最关键的判断和 3 个好坏对照例子。精选，本身就是品味。

07 最容易被忽略的一环：帮人用起来

作者认为这可能是最不显眼、却最重要的部分。设计团队里，有人从没打开过代码编辑器，有人熟悉 Git 和命令行；装工具、开权限、部署原型这种小坎，都可能让人在开始干活前就放弃。

团队推动力降低门槛的具体做法
ShopifyCEO Tobi Lütke 明确表示，使用 AI 会成为工作方式和绩效评估的一部分内部原型画廊 + 可复用的共享提示词库
IntercomCTO 和设计负责人推动Prototyping Hub：浅白的「给设计师的 Code 101」指南、分步视频
Atlassian全公司「AI Builder Week」，据其说法数千名员工暂停日常工作一周学 AI 原型发现拉人进 Slack 频道效果一般，发群组私信反应强得多，于是做了个小机器人

作者的总结是：工具投资和人的投资必须同步。再精巧的原型环境，如果只有少数人有信心使用，也没多大用处。

08 先做对什么

文章收尾只给了一个结论：进展最快的团队，在 AI 进入工作流之前就有强设计系统。令牌、组件、文档和指南，十多年来一直是为了让人一致地构建；现在只是多了一类读者。

编者把全文压成一个优先级顺序，适合团队做路线图时参考：

  1. 整理事实来源：令牌、精选组件、每个组件的示例与「不要这样用」。
  2. 定一个能分享的原型落点：哪怕只是一个共享仓库 + 自动部署。
  3. 约定项目上下文的格式：每个原型旁放 brief.md、constraints.md。
  4. 加上状态控制面板和保真度开关。
  5. 投资采纳：入门指南、提示词库、画廊、有人答疑。
  6. 最后才考虑自建平台和接生产。

09 个人设计师的缩小版

五家都是大团队，但结构可以缩到一个人身上。如果你也用 AI 做自己的网站和作品，可以这样对应：

团队级做法个人缩小版
Protodash / Prototype Playground一个 playground 仓库，每个想法一个目录，推送即自动部署到 GitHub Pages 或 Vercel
设计系统 MCP / Code Connect一份 tokens.css + 一个 components/ 目录 + 一份规则文件，要求 Agent 只能用其中的东西
Atlassian 的 20–30 个精选组件只列你最常用的 10–15 个组件，每个附一段好的用法
状态控制面板让 Agent 在每个原型右下角加一个开发用浮层，切换空 / 少 / 多 / 极端数据
灰阶早期稿一个 ?mode=explore 参数：去掉品牌色和字体，只看结构
共享提示词库一个 prompts/ 文件夹，把好用的提示词存成可复用的 skill

10 模板：给原型 Agent 的规则文件

下面这份规则文件把 Stripe 的「先查再写、查不到就诚实失败」、Atlassian 的「精选 + Tailwind 翻译」和保真度开关合在一起，可放进 AGENTS.md 或 CLAUDE.md：

# 原型规则（AGENTS.md）

## 事实来源（必须先读）
- 设计令牌：/design/tokens.css
- 可用组件：/design/components/README.md（只有这里列出的组件可以使用）
- 写任何 UI 代码前，先列出你打算使用的组件，并确认每一个都在清单中。

## 找不到时怎么办（诚实失败）
- 需要的组件不在清单里：停下来，告诉我缺什么，提出「用现有组件组合」或「新建」两个选项，等我决定。
- 禁止自行发明组件名、属性或令牌。
- 无法读取上述文件时，直接报告，不要凭记忆继续。

## Tailwind 翻译表（你可以先用 Tailwind 思考，但输出必须映射）
| 你想写的 Tailwind | 实际使用 |
| rounded-lg shadow p-4 | <Card> |
| text-sm text-gray-500 | <Text tone="muted" size="s"> |
| bg-blue-600 text-white px-4 py-2 | <Button variant="primary"> |

## 项目上下文
- 每个原型目录下必须有 brief.md；开始前先读，并用三句话复述目标。

## 保真度
- 默认「探索模式」：灰阶、系统字体、不加载品牌主题。
- 只有我说「进入定稿」后，才切换到品牌主题。

## 状态面板
- 每个原型加一个开发浮层，可切换：空数据 / 1 条 / 50 条 / 极端长文本 / 加载中 / 出错。

# 评审汇总提示词（配合原型内评论使用）
以下是这次原型评审收到的全部评论：[粘贴]
1. 按主题聚类，每类注明提出者人数。
2. 区分「结构问题」和「表层问题（文案、颜色、间距）」；当前处于探索阶段，表层问题只记录不修改。
3. 对每个结构问题，列出你准备怎么改、会影响哪些文件。
4. 等我确认后再动手。

12 自查清单

  • 我有没有一个「点开链接就能看」的原型落点？
  • Agent 可用的组件是不是一份精选清单，而不是整个组件库？
  • 规则里有没有写明「找不到组件时停下来问我」？
  • 每个原型旁边有没有 brief 之类的项目上下文文件？
  • 原型能不能一键切换空状态、极端数据、出错状态？
  • 早期稿是否用灰阶或非品牌样式，防止评审过早抠细节？
  • 评审反馈是集中在原型里，还是散落在聊天记录里？
  • 如果是团队：有没有入门指南、提示词库和能答疑的人？

这篇最后一句话值得反复读：AI Agent 只是设计系统的又一个读者。很多团队想「为 AI 做准备」，结果去研究最新工具；但五家大厂的经验说明，真正的准备工作十年前就该做——把决定写清楚、让它可复用。对个人设计师也一样：你越早把自己的令牌、组件和规则整理成文，AI 就越早开始像你的同事，而不是一个爱编故事的实习生。
