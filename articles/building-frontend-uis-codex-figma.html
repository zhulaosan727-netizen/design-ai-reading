01 先给结论：单向手写已经不够

多数「AI 做前端」工作流仍是单向的：要么从 Figma 截图 / 选区丢进 Agent 生成代码，要么在 IDE 里 vibe coding 完再人工截图贴回设计文件。单向意味着探索与执行被切成两个世界——画布上的假设改不动代码，代码里的真实交互也回不到画布上的多方案并排。

OpenAI 这篇的核心主张可以压成一句话：Figma MCP server 在 Codex 里不是「多一个读设计的插件」，而是把代码与画布做成可往返的同一工作面。Codex 桌面端本来就是为并行 Agent、跨项目上下文与外部工具准备的；Figma 画布本来就是为探索与并排比较准备的。MCP 把两边的强项接在一起：一边擅长落地，一边擅长发散。

短引（OpenAI）：「so you can build on your best ideas, not just your first.」对设计师来说，这句话比「更快出代码」更重要——往返是为了保留探索权，而不是把第一稿焊死成生产。

02 这条链路实际接通了什么

原文把场景拆成两段，但先把基础设施说清更有用：

端角色MCP 工具（文中点名）
Figma（Design / Make / FigJam）选区、布局、样式、组件信息的来源；也是回写后的可编辑画布选区 URL（Copy link to selection）作为节点句柄
Codex 桌面端Agent 编排、项目上下文、调用 MCPget_design_context、 generate_figma_design 等
运行中的 UI本地或公网渲染页，作为「真交互」的真相源捕获整屏或单元素，写入 Figma 图层

注意：选区可以来自 Figma Design、Make 或 FigJam。这意味着「灵感板 / 草图 / 高保真」都能当起点，而不必先整理成完整 Design 文件。

03 方向 A：画布 → 代码（get_design_context）

标准路径：

  1. 在 Figma 里选中 frame / 节点，右键 Copy as → Copy link to selection。
  2. 该 URL 绑定到具体节点：可以是单个元素，也可以是一组组件。
  3. 在 Codex 打开新项目或既有仓库，把选区链接放进指令，并明确「尽量复用现有设计系统组件」。
  4. Agent 调用 get_design_context：抽出布局、样式、组件信息，再据此写代码。

原文示例 prompt 很短，但短得好——它把两件事钉死：实现这个选区，以及 优先复用仓库里已有的 DS 组件。没有第二句，Agent 很容易「长得像、API 却是新造的」。

help me implement this Figma design in code,
use my existing design system components as much as possible.
只贴截图选区 URL + get_design_context
像素猜测；间距与组件名易幻觉结构化布局 / 样式 / 组件上下文
难对齐设计变量与真实 token更接近「按设计系统落地」
适合情绪板适合要进仓库的实现

Zhu 实践：第二句可以写得更狠——点名组件库路径（例如 @/components/ui）、禁止新造 Button/Card、以及硬禁令（卡片/告警禁止左侧竖向色条）。MCP 给事实，prompt 给边界。

04 方向 B：代码 → 画布（generate_figma_design）

这是多数团队缺的半边。代码迭代之后，你要在画布上并排比较流程、改变量、补空态——而不是对着浏览器截图做拼贴。原文路径：

  1. 先把应用跑起来（本地或公网）。
  2. 让 Codex「帮我 generate 一个新的 Figma design file」——触发 generate_figma_design。
  3. Codex 引导：选新建还是写入已有文件 → 选 workspace → 准备 UI capture → 打开应用的浏览器会话。
  4. 页面顶部出现捕获工具条：Entire screen（整屏） / Select element（单元素） / Open file（打开 Figma 检查图层）。
  5. 捕获完成后回到 Codex，文件 URL 已在对话里。

关键性质：回写的是可编辑的 Figma frames，不是一张死图。你可以继续在画布上接设计系统组件、把样式接到 variables、改布局、加批注、做空态与多方案——然后再走方向 A 拉回代码。

05 往返迭代才是产品形态

原文第三节标题「There and back again」说的不是炫技，而是工作节奏：

阶段在哪里做什么
探索Figma 画布多方案、批注、variables、空态、协作
落地Codex + 仓库get_design_context → 复用 DS 写代码
验证运行中的 UI真交互、真数据、真视口
回写generate_figma_design把真实 UI 变成可编辑图层，继续探索

「可以从任何一端开始」是这篇真正对设计师友好的承诺：有人从 FigJam 草图起步，有人从已有代码页回写起步，有人从 Make 原型起步——往返闭环让起点不再决定终点质量。

与读本里 Stripe Harbor、Vercel design.md、Figma Specs 对照：Harbor 强调「在浏览器里用 DS + mock data 出可分享原型」；design.md 强调「仓库外也要有可加载的品牌判断」；Specs 强调「Markdown 上下文住在画布上」。OpenAI 这篇补的是Codex 这条具体 Agent 链路上的双向 MCP 操作面。

07 可落地的检查清单与 prompt

开工前清单

  • Figma MCP 已在 Codex 桌面端安装并可鉴权。
  • 仓库里有可点名的设计系统组件（路径 + 主要 primitive 名）。
  • 本地或预览 URL 能稳定渲染要捕获的页面。
  • 明确本轮目标是「探索」还是「收敛可合并的实现」——两者 prompt 语气不同。

画布 → 代码模板

Implement this Figma selection in our repo:
<selection-url>

Constraints:
- Prefer existing components under @/components/ui (Button, Card, Input…).
- Map colors/spacing to our CSS variables / tokens; do not invent a parallel palette.
- No left accent bars / border-left status stripes on cards or alerts.
- Match reachable states implied by the frame (empty / loading / error if present).
- After first pass, list any DS gaps you had to approximate.

代码 → 画布模板

My app is running at <local-or-public-url>.
Use generate_figma_design to capture:
1) the primary flow screen (entire screen)
2) the empty state of the list (select element if needed)
Write into a new file in workspace <name>.
When done, give me the Figma URL and a short note of what layers were created.

往返一圈的最小仪式

  1. 选区 → 代码（复用 DS）。
  2. 跑起来，修交互与状态。
  3. 回写画布，并排 A/B，接 variables / 批注。
  4. 再拉一次 get_design_context，只合并画布上「决定留下」的改动。

一句话总结：这篇不是教你「用 AI 更快画界面」，而是把 Codex 的执行力与 Figma 的探索力用 MCP 焊成环。单向生成只会放大第一稿；往返才让最好的想法有机会被选中。
