01 三句话结论

第一，票单等工程师不如自己改小漂移。你清楚 dropdown 该怎么开、hover 该什么手感，但等到工程做完，常常已经「差一点」。Claude Code 让你用自然语言描述改动，拿回可运行代码——前提是它读到的是你们的真组件与 token，而不是截图猜色。

第二，Figma MCP 是桥，不是又一个导出插件。它让 Agent 直接读帧、组件、变量；也能把代码侧改动推回画布成原生可编辑层。设计文件与代码库开始双向同步，而不是单向「标注交接」。

第三，从低风险小任务练手。修一个组件的 padding、对齐一个按钮到正确 token、修 hover、清 empty / error 文案——不要一上来碰新架构或全应用改动。本地副本上试；什么都不进生产，直到你决定。

02 痛点：hover 感觉在交接里漂走了

原文开场几乎每个设计师都经历过：交互感觉在脑中很清楚，ticket 写了，等排期、等实现，上线一看——开合时机、反馈强度、空态文案，全漂了一点点。传统解法是再开一轮 ticket；新解法是：在本地代码里自己改到满意，再交给工程审。

Figma 2026 AI report 给出组织背景：参与开发的设计师比例从 21% 升到 41%（近乎翻倍）；做设计工作的开发者从 44% 升到 60%。85% 受访者认为 AI 让自己更高效，63% 觉得因此更擅长本职，70% 认为产出质量上升。约 41% 的产品构建者说 AI 改变了整队协作方式——更少交接、更多重叠——是两年前的约六倍。

原文钉得很清楚：Claude Code 能写代码，但交互是否说得通、是否可上线，仍由人决定。AI 改的是「活怎么干」，不是「质量谁说了算」——和读本 No.06 Linear、No.22 决策权威顺序同族。

03 对设计师来说，Claude Code 是什么

把它想成坐在代码库里的 Agent：你描述想要什么，它打开文件、写代码、跑起来——你不必亲手碰终端细节。它在你打字前就开始收上下文。

能力对设计师意味着什么容易误解成什么
读团队规则文件（类似 Skill）知道你们怎么组织代码、命名、约定以为「会魔法」，其实靠仓库里的短规则文件
跨会话记住纠正与偏好上次骂过的间距错误，下次少犯以为永久全知；仍须你持续纠正
经 Figma MCP 读真组件与 token生成对齐设计系统，而非截图猜色距以为贴一张 PNG 就够——不够
只改本地副本大胆试、随时撤，不进生产直到你点头以为一保存就上线——不会

一句话：它不是「设计师版 IDE 教程」，而是带着你们设计系统说话的结对程序员——前提是 MCP 已接通、提示里明确要求复用现有组件与 token。

04 四类用得上的活

场景典型问题Claude Code 能帮什么你仍须盯什么
设计系统同步代码里三周前改了 token 名，Figma 变量没跟上从代码库拉现状，同步回 Figma，使文件对齐正在上线的东西语义是否仍正确；有无破坏性重命名
Design-to-code新功能已 mock，想在排期会前看到真活拿帧链接，用真组件搭可运行原型范围是否最小；有没有顺手发明新组件
带真实交互的原型干系人问：「数据空了怎么办？」Figma 原型答不上做出含 empty / error / loading 的可点版本状态是否产品真可达（呼应 No.22）
文档与 a11y 审计继承来的组件库零文档；按钮为什么不一致没人记得写文档、标出无障碍问题，赶在 QA 前暴露文档是否写「为何」而不只是 API 列表

原文也提到 Figma Make：若你只想「提示出可运行原型、连终端都不开」，那是另一条轻路径。本篇焦点是已有代码库 + 真设计系统时，设计师如何进入开发环，而不是从零生成玩具 demo。

05 高阶接入：插件 → 授权 → 帧链接 → 具体提示

Figma MCP server 像翻译器：让 Claude Code 直接碰到真帧与 token。路径按原文四步压缩为高阶清单（具体命令以官方页为准，组织策略可能禁止装插件——需找账号管理员）：

  1. 安装 Figma 插件到 Claude Code（已安装 Claude Code 的前提下）；装完若会话已开着，重启一次。
  2. 授权 Figma 账号：在插件列表里选 Figma，浏览器 Allow，回到会话确认已 connected。
  3. 在 Figma 里右键目标帧 → Copy link——链接告诉 Agent 读哪一块，而不是整个文件瞎扫。
  4. 把链接贴进提示，并写死复用约束。例：「用 React 实现这个 checkout 表单。复用我们现有组件；间距与颜色从设计 token 拉，不要硬编码。」
步骤成功信号常见翻车
装插件插件列表能见到 Figma企业策略禁装；装完未重启会话
授权显示 connected授权了个人号却读团队文件权限不足
复制帧链接Agent 能指名该帧复制了页面链接或整文件链接，上下文过噪
提示输出使用已有组件 / token 名没写「reuse existing」→ 它发明一套平行 UI

提示里最值钱的不是文采，而是禁止发明第二套系统：点名复用、点名 token、点名不要新造色值。

06 往回推：改动变回可编辑 Figma 层

出来怎么走，回去就怎么走——还是经 Figma MCP。你提示 Claude Code 把当前文件状态推回画布，工具会在 Figma 里创建或更新为原生可编辑图层。

这意味着：不必等工程「再导出一版」才能在 Figma 里看见代码侧的修正。你可以自己拉回来、微调、再递回去。封面母题里那条穿过 MCP 桥的强调色路径，指的就是这趟 round-trip。

方向你给什么你得什么
Figma → Code帧链接 +「复用组件 / token」约束本地可运行、对齐系统的实现
Code → Figma「把当前实现推回画布」类提示可编辑原生层，而非扁图像

07 第一批任务清单（别一上来改架构）

原文建议从「小而具体」开始。编成可勾选清单：

  • □ 修单个组件上已偏离规范的 padding
  • □ 把某按钮的间距或颜色对齐到正确设计 token
  • □ 修一个与文件不符的 hover 态
  • □ 清理 empty / error 上的套话文案（改成你们产品语气）
  • □ 不要：新架构、跨全应用的重构、一次改十条用户路径

大改需要更多上下文与评审；第一次试就碰它们，出错时更难纠偏。把第一次成功定义成：「我在本地看到 hover 终于对了，并且能解释它用了哪个 token」——而不是「我重写了设置页」。

和 No.22 联用的姿势：小漂移用 Claude Code 改；一旦发现「同类决策第三次出现」，别继续私人 hotfix——把它写进 Decision / Skill / lint。工具负责手感闭环，仓库负责判断沉淀。

08 FAQ：要不要会写代码 / 替不替工程师 / 会不会弄坏生产

问题原文答案编者补充
设计师要会写代码吗？不必。自然语言即可；但懂 padding、components 等基础词，指示更准、一次更近。把「会一点术语」当成设计系统词汇表，不是转行前端
会取代开发者吗？不会。能写可运行代码 ≠ 能在更大产品与生产约束下做技术判断。你的产出应默认进 code review，而不是绕过工程
改错会弄坏生产吗？不会。工作在本地副本；不对就撤或重来，不动已上线。仍要遵守团队分支与 PR 规范——本地安全 ≠ 可以偷偷 push main

10 编者点评

编者点评：Figma 这篇资源页最好的一点，是把「设计师学写代码」从励志口号落成一张小任务菜单：padding、token、hover、空态文案。MCP 桥的价值也不在炫技，而在禁止截图猜色——Agent 读真组件与变量，才能少发明第二套 UI。配合 21%→41% 的参与开发数据，职业现实已经变了；但 FAQ 三条（不必会写码、不取代工程、只动本地）把焦虑按回去：你要练的是「说清约束 + 验收手感」，不是去抢 SRE 的活。建议阅读顺序：先 No.04/15 熟悉画布 Agent → 本篇接通代码环 → 用 No.22 把第三次重复的判断写进仓库。这样，从帧到真代码的路径上，既有手感闭环，也有判断沉淀——而不是永远靠下一次 ticket 把 hover「修回来」。
