设计和烹饪有一个共同的真理：准备决定结果。结构化的提示词能让 AI 从靠猜变成可靠的设计伙伴。

分享 约束下的烹饪：设计师打造更优 AI 提示词的框架

首屏插图：Jimmy Simpson

每天下班后，我就开始了第二份“工作”：为家人做饭。备料可能在下午的休息时间就开始了：切蔬菜、腌肉、给烤箱或 Instapot 设定计时器。烹饪和设计非常相似。要做什么菜、何时调味、如何备料、何时克制，每一个动作都关系到最终想要的结果。

我从不对我的刀说“谢谢”，对炉灶、烤箱或微波炉也一样。它们的按钮上写的不是“请开始”，这是有原因的。工具不需要共情，它们需要的是清晰。

大语言模型也是如此。它们是为了解读而生的机器，而不是为了感受。它们能输出出色的共情，却不需要把共情当作输入。事实上，你对模型越客气，引入的歧义就越多。

模型需要干净的指令和清晰的约束。如今，提示词运用能力正在成为许多岗位的基本门槛，而对产品设计师来说，它是一项格外关键的技能。原因在于，模型天生具有概率性和不确定性，而设计恰恰相反：精确、可重复、有意为之。要弥合这道鸿沟，靠的是系统思维，而不只是语言能力。

Stochastic（随机性）指系统中的随机现象；在大语言模型（LLM）中，它解释了为什么输出是概率性的，而不是完全确定的。

代码有结构，AI 有随机性，而设计介于两者之间。设计必须清晰易读。这正是在设计工具中进行提示词设计与众不同的地方：你无法单凭氛围就得到一个可用的原型。你需要的是能把不确定性收敛为结构的输入。

Mise en place（餐前备料）

烹饪如此，提示词设计亦然：备料就是一切。高级料理界有句话叫 mise en place，意为“一切各就其位”，它能让你在热锅开火之前就把混乱理出秩序。把准备工作做对，之后返工修补的时间就会少很多。

作为设计师，我们很多人对工作环境都很讲究：播放什么音乐、布置怎样的灯光，以及桌面和电脑桌面上每样东西摆在哪里。有时这意味着给自己开一个新文件、一页干净的页面、一块空白画布。做提示词设计时，我们同样需要把几样东西安排妥当。每个提示词都需要清晰的表达、上下文和约束。我一直在搭建自己的提示词框架，这套 TC-EBC 结构（Task 任务、Context 上下文、Elements 元素、Behavior 行为、Constraints 约束）对我帮助很大。这样的结构不仅能让你得到更好的结果，也与各领域的提示词工程师和系统设计师正在趋同的做法一致。一位 Reddit 用户广为流传的清单积累了 1000 多小时的大语言模型（LLM）提示词设计经验，得出的优先级与此相同：明确任务、设定约束、模块化排序。Microsoft 的 Semantic Kernel 文档也印证了这一点，其提示词设计模式强调定义意图、模块化构建以及可预测性，而非耍小聪明。这更关乎意图的对齐，而不是一份精确到克的食谱。

举个例子，假设你要为一款新的 Figma Make提示词、原型，一气呵成：Figma Make 现已向所有用户开放今天，Figma 的所有 AI 功能和产品都已结束 beta 测试，包括 Figma Make，现在人人都可以试用。看看团队如何用这款“提示词生成应用”的工具想得更大、动作更快、协作更好。应用设计提示词，它能根据食品储藏柜的照片生成食谱。如果你只是用自然语言写下自己想要达成的目标，可能会是这样：

Please build a new app that allows home cooks to take a picture of their pantry or freezer to suggest recipes. Remember any allergies or preferences. Thanks!

这就好比把所有食材一股脑倒进锅里，指望煮出一顿饭。说实话，我对得到的结果并不满意。

由于没有讨论视觉设计，这个结果总体上差强人意。作为起点并不差，它具备一些基本的特性和功能，但整体平淡无奇，只比线框图稍微好一点。

现在，我们用 TC-EBC 格式改写同一个提示词，再试一次：

  • Task: Build an AI-powered meal suggestion app using pantry/fridge photo inputs
  • Context: Home cooking assistant for households with dietary restrictions
  • Elements: Camera input, pantry scanner, dietary settings form, meal suggestions list, recipe cards
  • Behavior: User uploads photos; app scans inventory, filters by diet prefs, suggests recipes
  • Constraints: Mobile-first, iOS/Android, accessible UI, supports multiple household profiles

可以看到，TC-EBC 格式的提示词清晰、易于扫读，对期望的行为和 UI 也交代得很明确。它也更有可能生成你想要的结果；而最初的提示词冗长、含糊，还把任务埋在了客套话里。结构化版本用清晰的指引取代了猜测。一个精心构建的提示词能消除意图上的歧义，就像一套优秀的设计系统能为设计提供恰当的结构与指引一样。

结果如何？左侧的界面是用上面的 TC-EBC 结构化提示词一次生成的初始结果。上下文、元素和约束为 Figma Make（及其底层的大语言模型）提供了所需的信息，让它构建出我们想要的应用，也就是我们原本打算构建的应用。除了设计更丰富、视觉上更吸引人之外，优化后的提示词也为后续迭代搭好了更好的基础。

问问你的模型需要什么上下文才能成功，然后把其余的统统去掉。多余的冗词会拖慢流程、迷惑模型，至少也会迫使大语言模型（LLM）多花几轮去揣摩含义。AI 中的优雅与设计中的优雅一样，都是做减法的过程。关键在于精简到只剩必要的部分，这需要细致的准备，以及一套稳健、定义清晰的设计系统，来确保清晰与一致。

想在提示词上获得帮助？试试我的 Make Prompt Assistant GPT。我把最初那条“礼貌”的提示词输入这个 GPT，并让它为提示词增加结构和清晰度，从而做出更出色的应用。结果就是我们上文用到的 TC-EBC 提示词。

打磨食谱

结构良好的提示词就像一张食谱卡：简短、直接、有指导性。每一个“也许”“只是”或“请”都会稀释意图，增加噪音。目标不是冗长或客气，而是清晰。

我们用 TC-EBC 来建立这种结构：

  • Task（任务）定义你要构建什么。
  • Context（上下文）说明为什么做、为谁做，防止跑偏。
  • Constraints（约束）设定护栏，让系统保持可控、一致。

TC-EBC 结构的每一部分都在缩小歧义、强化意图。合在一起，它们把猜测变成引导。我们都曾花上好几个小时，盯着大语言模型（LLM）那条“思考—等待—推理—调整—决策”的状态信息，因此凭直觉就明白：表达精确是一种节省精力、建立清晰度的设计选择。消耗更少的 Token，也就成了一种效率训练。

我们再看一个示例，场景是大多数产品设计师最近都遇到过的：

模糊的提示词：

Write a description for this feature. Keep it simple but also exciting. Maybe like how Apple does it?

TC-EBC 提示词：

  • Task: Write a short product feature description.
  • Context: For a new “One-Click Export” feature in a design tool.
  • Elements: Headline (max 7 words), subheadline, single-sentence body copy.
  • Behavior: Body should imply speed, simplicity, and trust.
  • Constraints: No jargon. Match the brand tone of Duolingo or Notion. Total length: under 200 characters.

TC-EBC 提示词在说明你想要什么、以及如何达成方面要出色得多。为元素和行为提供约束与具体指引，无疑能让你更接近目标，我认为你得到结果的速度会更快，也更精准。

正如 Figma 开发者倡导者 Jake Albaugh 所说：“语言越直接，交流越高效。”具体不等于僵化。它是精确与适应性的结合：足够紧凑以保持形态，又足够灵活以持续演进。就像设计和烹饪一样，关键在于平衡。

层层叠加风味

提示词设计是一个迭代的过程。你要边做边尝、边测、边调。目标不是完美，而是校准，每一轮都会暴露出模型推理中新的亮点、缺口或越界之处。无论你是在 Make 中构建应用、与 ChatGPT 一起琢磨一本书的创意，还是用 Cursor 和 Figma’s MCP serverIntroducing our MCP server: Bringing Figma into your workflowToday we’re announcing the beta release of the Figma MCP server, which brings Figma directly into the developer workflow to help LLMs achieve design-informed code generation. 编写代码，修订提示词的意义都在于不断叠加上下文，一步步做出更好的最终成果。

进阶提示：把 ChatGPT、Claude 或 Gemini 这样的大语言模型（LLM）当作提示词搭档，让你的 Make 更干净。先教它 TC-EBC framework，再让它协助你打磨修订提示词。附上图片、截图和你期望的结果，大语言模型（LLM）就会回给你结构清晰的修订提示词。写修订提示词时，我总会在 TC-EBC 提示词的 Constraints 部分加上说明，明确告诉工具哪些地方不该改动。

要充分发挥修订提示词的作用，关键是界定哪些内容应该进入模型的视野，哪些不该。Anthropic 称之为上下文工程：有意筛选模型能看到、记住和权衡的内容。目标是让意图保持纯粹。如果说 mise en place 是准备，那么上下文就是纪律。

在 Figma Make 中，你可以为作品提供丰富的上下文设计团队开拓新领域的 4 种方式：借助 Figma Make从重绘产品路线图到构建起步模板，来自 Maven Clinic、Pendo、ServiceNow 和 LinkedIn 的这些 Figma Make 创意，展示了设计师如何用提示词开辟前路。。与使用其他模型一样，你可以直接上传截图，为 Make 提供设计上下文——这种做法有它适用的时机——但只要条件允许，提供 Figma 画框会带来更好的结果。原因在于，设计画框包含结构化数据。你不必让 Make 去推断和解读一张图片，而是直接给它结构清晰的设计数据作为构建基础。它无需费力转换，因为这些内容本来就是用它能直观理解的语言“写成”的。

此外，你还可以指明希望 Make 使用和参考的 API 和/或依赖，例如 three.js 或 D3js.org。虽然在修订提示词中采用 TC-EBC 这类结构化写法依然很重要，但额外的上下文能让作品更有分量，并带上你期待的、精致且可交付的设计所具备的独特风味。

你还可以通过添加库来叠加样式上下文，通过调整 Make 指南来添加行为和结构方面的护栏，或者通过 MCP（模型上下文协议）连接器介绍我们的 MCP 服务器：将 Figma 融入你的工作流今天，我们宣布 Figma MCP 服务器进入 Beta 测试，它将 Figma 直接带入开发者工作流，帮助大语言模型（LLM）生成基于设计的代码。接入 Notion、Asana、Github、Atlassian、Linear 和 Monday.com，为提示词加入深层上下文。与其只是描述想要的改动，不如直接添加你在 Notion 中写好的 PRD，或是已在 Asana、Jira 或 Linear 中定义好的任务。（还有一个用于创建这些 PRD 的 GPT。）

不妨把这看作创意调试。随着时间推移，每一次修订都会让模型学习你的设计风格与思路，你也会更了解模型的局限：它能吸收多复杂的内容、哪里需要结构、什么时候简单反而更好。每一轮下来，整个过程都会变得更快、更紧凑，也更有表现力。

与 AI 模型协作并不是一门精确的科学，但加入设计上下文能让过程更可控，而不再像把食材一股脑扔上炉灶、然后祈祷能做出一顿饭。最终你写出的提示词，不再像纸上的食谱，而更像练熟了的手艺。

选对刀

每个模型的“切法”都不一样。架构、训练数据和对齐方式，把它们各自塑造成不同的刀刃：有的擅长精细处理，有的则适合更宽、更快的切割。把它们当作一套齐备的工具箱：当你了解每个模型的锋芒所在，就能选择最适合当前工作流的那一把，让成果更出彩。

在 Figma Make 中，我们的默认模型是 Claude Sonnet 4.5。它擅长总结、理解细腻的结构或轻量的上下文，并且语气友好。只要提示词清晰，CS 4.5 往往能很好地推断意图，也更青睐内嵌丰富逻辑的架构型提示词，比如 TC-EBC 提示词框架。可以把 Claude 想象成一位训练有素的副厨：指令明确，它就能完成得漂亮；指令含糊，它就会一心讨好你，有时甚至过了头。

最后，GPT-4 以及现在的 GPT-5 被用在我的 Make Prompt Assistant GPT 中，它们也是最广为人知的一批模型。GPT 是那个知根知底的老搭档：聪明、话多、能力极强，但偶尔过于热心。它喜欢示例，对演示的响应很好，至今仍是最出色的通才型选手。

提示词的熟练度不只关乎结构，也关乎模型的选择。在 Figma Make 中，我们允许你明确地切换模型。这意味着你可以让提示词和你的预期，匹配最适合这项任务的模型。这样一来，提示词设计就成了一项设计决策，而不只是一次交互。

那么该用哪个？取决于具体任务：

把 Claude 当作均衡的协作者，它能遵循分层的结构。

  • 擅长：清晰的摘要、有条理的后续执行，以及友好、带轻度上下文的工作
  • 最佳场景：指令简洁明确，逻辑直接写在提示词里（TC-EBC 的拥趸们，请举手）
  • 氛围：训练有素的副厨——给它明确的指示，它会端出漂亮的成品；指令含糊，它就会过于努力地想讨你欢心

当你想在狭窄的任务上获得快速、稳定的结果时，选择 Gemini。

  • 擅长：精炼的提示词、快速的结构化任务，以及任何有明确约束的事情
  • 最佳场景：需要精确但输入很短——重命名这个、替换那个、润色这里的措辞
  • 氛围：锋利的多功能小刀——利落、迅速，容不得含糊其辞；交给它一件窄而具体的活，每次都能切得干净

需要推理、示例或探索式的重新构思时，选择 ChatGPT。

  • 擅长：通用推理、丰富的示例、长篇结构，以及任何适合“展示而非讲述”的任务
  • 最佳场景：你提供它可以遵循的演示或模式——它会通过模仿你的示范来让自己更精准
  • 氛围：人人信赖的经典厨师刀——能力出众、乐于相助，依然是抽屉里最可靠的通才

摆盘上桌

在任何一次借助大语言模型（LLM）的设计或开发过程结束时，你产出的不只是结果，而是在为未来设计一套可重复使用的系统。你从清晰的意图出发，梳理了逻辑结构，为任务选对了模型。如果做得好，你还能把最终结果追溯到塑造它的每一个决策。

提示词设计不是魔法咒语，也不是巧妙措辞，而是关于架构、上下文和工具的熟练运用。它要设计一套工作流，让模型无需猜测，只管执行。正如设计系统能让团队更快、更一致地推进工作，结构化的提示词设计也能让我们把意图转化为可运行的原型。

这就是新的创作循环：以清晰为起点，用上下文逐步充实，再通过反馈不断打磨。真正让你在牌桌上赢得一席之地的，是匠心与精准，而不是讨巧。
