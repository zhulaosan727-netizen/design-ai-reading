01 三句话结论

第一，软件设计的主流工具很长时间都是同一类通用软件：先是 Photoshop，再是 Sketch，再是 Figma。它们很强，也因此容易让人以为：设计工作就是在一套要学很多年的工具里，把画板越拧越细。Luke 观察到另一种做法正在变多——设计师开始为自己面前的那一个问题，临时做一个高度专用、甚至用完就扔的小工具。他把这叫做 design by playground（按游乐场来设计）。

第二，playground 的要点不是「把界面做出来给别人点」，而是把设计决策收成变量（variable），在真实运行环境里立刻看到结果。长文案、短文案、没有文案；字号、字重、颜色；加载、空状态、错误、动效时序——这些都可以变成旋钮。以前它们往往要等到开发接入真实数据，才会暴露问题。

第三，以前很少有人这样设计，不是因为这个主意不好，而是因为做一个很可能只用一次的工具，比在静态稿（static mockup）上改来改去更贵。前沿模型配上合适的运行环境（harness）之后，几分钟、很低的成本就能搭起来。于是可以为一个下午的问题做一把尺子，看完就拆。而且这把尺子最好跑在产品真正所在的环境里：Web、iOS 或 Windows 上的真实字体渲染、滚动、悬停与触控、性能和屏幕尺寸，都是画布只能近似的东西。选定的值还可以直接导出成代码或设计令牌（design token），交给工程师，或交给下一个编程 Agent。

02 通用设计工具活了几十年，专用尺子一直太贵

Luke 把话从头说起。只要还有「软件设计师」这个角色，就几乎总有一个占主流的设计工具。工具会换代，模式却很稳定：你在一个通用画布里摆界面，用组件和自动布局去逼近真实产品，再把结果交给后面的人去实现。这套工作方式训练了几代设计师的肌肉记忆，也塑造了评审习惯——打开文件，对着几张看起来完整的画板说话。

问题不在通用工具「不够好」。Figma 已经把静态稿推到很高的完成度，原型也可以被点通。真正的限制是：通用工具必须同时服务所有人的所有问题，因而很难为你今天这一个问题提供最合适的旋钮。你要比较三种标题长度对卡片高度的影响，画布上通常还是得复制出三帧，手填三种文案；你要感觉 180ms 和 280ms 的退出动效差在哪里，常常只能在脑海里补，或做一个很浅的原型。工具很通用，尺子却不够专用。

前端开发者对 playground 其实并不陌生。它说穿了就是：做一个能让你拨变量、并立刻看见界面结果的小环境。可以一次摊开许多变体，可以一边调一边真正去操作。设计师不是不知道这好用，而是长期算不过来那笔账——为了一个可能再也不出现的问题，先造一个工具，通常不值得。

编者点评：把「不会做」和「不值得做」分开，是这篇最有用的第一刀。许多设计文件里缺的不是想象力，而是一把只为当前问题存在的尺子。尺子一直能做，只是过去太贵；现在贵的那头变了，判断却还停留在「我们用的是不是行业标准工具」。工具是不是主流，和它能不能回答你今天下午的问题，不是同一件事。

03 所谓 playground，不是「更好看的原型」

评审里常把「可交互的东西」统称为原型（prototype）。Playground 和原型有重叠，但目的不同。原型通常是为了演示一条路径：让别人走一遍下单、开通、或撤销。Playground 是为了回答一个设计问题：让你自己把关键变量拧来拧去，比较结果，直到某个组合站得住。

Luke 写到的几项能力，正好可以当成一把鉴别尺：

  • 一次看见许多变体。同一张卡片排上长文本、短文本、没有文本，不是做完后再补边界情况，而是一开始就把边界摊开。
  • 选项即旋钮。大字、粗体、红色这类变化，不必复制画板，而是直接拨动控件。
  • 可以真正交互。不是看一张「看起来能点」的图，而是在可运行的界面上滚动、悬停、点按、打断动画。
  • 接得进真实内容。长名字、缺失图片、空列表、失败重试，不再等开发后期才来开 issue。
  • 把时序也变成可调项。动画时长、缓动、过渡、加载与错误状态，都可以当成控件来试，而不是写在注释里想象。

所以，如果一个文件只是把三条路径画成可点击的热区，它仍更接近原型；如果它把「要决定的那几件事」收成控件，并让你在真实渲染里比较，它才更接近 playground。

编者自己补一个例子。假设你在做一个中文阅读栏，要决定一行排多少字、字号和行高怎么配。在 Figma 里，你多半会准备两三个画板，手工填一段看起来刚刚好的正文。可「刚刚好」常常是理想文案造成的错觉：标题一换长、注释一出现、代码块一进来，栏宽就塌。一个下午的 playground 可以只做这一件事：左边是字号、行高、每行字数、段距的滑杆，右边是真实文章在浏览器里的渲染，并内置「短标题 / 长标题 / 有图注 / 有对照表」几个样本。你不是在给阅读栏画一张更完整的稿，而是在为「这一栏读起来累不累」做一把可以拧的尺。

编者点评：Playground 的输出也不只是「看来看去很过瘾」。它应能留下一组被选中的值：字号 18、行高 1.7、每行约 46 个汉字——这些值随后可以写成 CSS 变量或 design token，让下一棒（人或 Agent）接着用。若一场游乐场玩完只留下几张截图，它就又退回静态稿了，只是绕了一圈。

04 以前不做，是因为工具本身比问题还贵

既然好处这么明显，为什么过去不是人人都这样设计？Luke 的回答很干脆：做一个游乐场，所花的时间通常超过它能省下的时间。在静态稿上拧一拧，更快，也更省事。而你写下的这个小工具，很可能用过这一次就不会再打开。为一次性问题造专用工具，账算下来是亏的。

这解释了为什么设计团队会长期停在「近似」里。不是设计师喜欢假数据，是真实数据、真实动效、真实设备行为，都太贵，只好用画布去模拟。开发后续再来补长名字、缺图和慢网，也变成一种被默认的分工。Playground 不是新发明，它只是一直付不起。

05 AI 把「为这个问题做一把尺子」变成午后能完成的事

局面改变的不是「设计师终于愿意写代码了」，而是成本结构。Luke 的判断是：一个前沿模型（frontier model），再配上合适的 harness，可以在几分钟内、以极低成本搭出一个游乐场。于是门槛消失了——你可以为某一个设计问题或某一个功能临时做一个专用工具，得到答案之后就把它扔掉。

「扔掉」是这篇里最容易被忽略的一句。工具不必进入设计系统，不必写成团队平台，也不必活过这个迭代。它的寿命可以只有一个下午。学了几年的通用软件仍然有位置，但不再是唯一入口：现在也可以先做一个只回答当前问题的小工具，用完就走。Luke 写道，设计工具曾经是你要花许多年去学的东西；现在它可以是你做出来、用一个下午、然后愉快离开的东西。

对已经会一点代码、也习惯和编程 Agent 共事的人来说，这句话特别硬。你不必先成为「会做内部工具的人」，才配用这种方法。问题定义清楚、变量列出来、样本数据准备好，Agent 往往已经够把场子搭起来。你的工作是判断这场该不该搭、旋钮该有哪些、何时可以拆。

编者点评：这里有一个反直觉的结果。工具越容易做，越要克制自己把它产品化。一旦你开始为这个下午的尺子补账号体系、权限和文档，它就不再是 playground，而变成又一个要维护的内部产品。能拆，是它便宜的前提。留不住手，成本会从「几分钟」涨回到过去那种「不值得做」。

06 为什么专用工具常常胜过通用画布

Luke 给出的理由不只是「更快」，而是「更真」。一个高度专用的工具，往往胜过通用工具，尤其当它跑在软件真正运行的环境里：Web、iOS、Windows 等等。你那时看到的是真实的字体渲染、滚动、触控与悬停、性能，以及真实的屏幕尺寸——这些都是静态稿只能近似的东西。

近似会在一些问题上足够用。图标网格、卡片圆角、浅色背景上的对比，在画布里就能看得很清楚。可一旦问题涉及「读起来累不累」「滑起来顿不顿」「长名字会不会把按钮挤出屏幕」「这段动画在低端安卓上会不会掉帧」，近似就开始骗人。你在 2 倍画板上觉得刚刚好的间距，到了真实滚动里可能太密；你在原型里看过一次的过渡，到了可中断的交互里可能太黏。

更实际的一层是交接。在 playground 里选定的值，不必再靠标注和截图去翻译，而可以直接导出为代码或 design token，交给工程师，或更常见地，交给下一个编程 Agent。尺子和产物开始说同一种语言。通用画布当然也可以借助 MCP、Code Connect 去靠近代码，但那仍是「从近似走向真实」；playground 反过来：一开始就站在真实环境里，只把要决定的变量露出来。

07 Luke 自己搭过的几场，以及一个可以亲手拧的例子

原文用几张截图说明：playground 不是一种样子，而是一种「为问题定制控件」的习惯。他展示过为应用里的背景动画而做的场子，为邮件通知而做的场子，为探索设计语言、生成品牌资产而做的场子，以及一个把 Figma 文件做成 PDF 的专用工具。它们各自只服务一类问题，旋钮也不通用——这正是重点。你不会希望用同一套面板既调动画流体，又排邮件，又导出文档。

文中可以亲手试的例子，围绕一个在 Agent 产品里反复出现的争论：智能体（agent）会做很多事，包括推理（reasoning）、工具调用（tool use）、委派（delegation）、监控（monitoring）。这些过程，该在界面里露出多少？有人觉得过程压得人喘不过气，只想看结果；有人觉得不看见过程就无法监督。Luke 把这场争论收进一个可运行的游乐场，而不是收进又一轮口头偏好。

打开那个例子，会看到一排非常具体的旋钮，而不是「多露一点 / 少露一点」这种空形容词。步骤是逐条列出、按相关步骤合并、按消息编组，还是只显示实时状态、只显示变更与失败？过程本身是完整呈现、降低存在感、收成一行，还是干脆隐藏？推理是保留标题、只留首句，还是完全不露？失败是每行都记，还是只记失败？图标、命令的摘要或原文、分隔线和对齐方式，都可以单独拧。右侧的界面跟着变。争论被拆成可比较的变量，你才能看见「露出工作过程」到底是哪一层在吵。

这就是 playground 比再开三张画板更厉害的地方：它逼你把口头分歧写成控件。写不出来的，说明问题还没被问清楚；写出来并能在真实界面里切换的，评审才有共同对象。

编者点评：不要把这个例子理解成「Agent 界面必须这样排」。它示范的是方法：先把争论里真正在变的那些维度找出来，做成可以来回切换的控件，再在真实环境里看取舍。你自己的问题可能是筛选芯片过多时怎么折行，也可能是桌面端通知该堆叠还是该替换——只要变量能列出来，就值得考虑先搭一场，而不是先画三张看起来完整的稿。

08 对照表：静态稿、通用画布、一次性游乐场

静态稿（static mockup）通用设计工具里的画板与原型一次性 playground
它最擅长回答这一屏看起来像不像、层级清不清流程走不走得通，组件和品牌是否一致某几个变量怎么组合才站得住
运行环境图片或画板，全部是近似仍主要是设计画布，交互常被简化最好就在 Web / iOS / Windows 等真实环境里跑
数据与边界通常是理想文案和理想图片可以换组件，仍容易停在假数据一上来就接长名字、缺图、空状态、错误与慢加载
动效与性能画出来或写在注释里能做有限的原型动效时长、缓动、中断都可以当旋钮，也能感觉到卡顿
AI 出现以前的成本低，所以成为默认中等，值得为完整流程投入高，常因为「只用一次」而不值得做
有编程 Agent 之后仍然快，适合早期构图仍然适合系统化和协作几分钟就能为当前问题搭起来，用完可拆
留下什么图片、标注设计文件被选定的值、token 或代码；工具本身可以扔掉
典型误用把理想稿当成已经验证过的界面用更多画板代替把问题写成变量把下午的尺子做成要长期维护的内部产品

09 可粘贴：向编程 Agent 要一个下午就能拆的游乐场

在动手之前先写四行。写不出来，就还不必叫 Agent 开场。

这一场只回答的问题：
[一句可验证的问题，例如：中文阅读栏在桌面宽屏上，怎样的字号 / 行高 / 每行字数，读 800 字仍不累]
明确不回答的问题：
[例如：不讨论首页导航，不重新设计品牌色，不做账号体系]
变量（每个都要有范围和默认值）：
- [字号：14–22，默认 18]
- [行高：1.4–2.0，默认 1.65]
- [每行汉字数：32–52，默认 46]
必须内置的样本 / 边界：
- [短标题；超长标题；有图注；有对照表；代码块；空正文]
运行环境与导出：
- [浏览器真实渲染，使用产品最终会用的字体]
- [把当前值导出为 CSS 变量 / JSON token，复制即可交给下一棒]
寿命：
- 这是一次性工具。问题答完就停，不要加登录、路由、文档站点或设计系统包装。

然后可以把下面这段交给 Claude Code、Cursor 或其他编程 Agent。按你的问题改中括号里的内容即可。

请做一个一次性的设计 playground，不要做成产品。

问题：[只回答这一句]
界面分成两栏：左边是控件，右边是真实预览。不要用截图模拟预览。

请把这些变量做成控件，并写明单位和范围：
[变量列表]

预览必须内置这些样本，并能一键切换：
[长 / 短 / 空 / 错误 / 加载 等]

约束：
- 跑在 [Web / iOS / 桌面] 的真实环境里，使用 [最终字体]，不要用设计工具的近似渲染。
- 所有边界情况从一开始就可切，不要等我再要求「再做一个长文案版本」。
- 提供「复制当前值」：输出 CSS 变量或 JSON，键名稳定，便于交给工程师或另一个 Agent。
- 不要添加导航、账号、权限、主题市场，或任何让这个工具活过今天的功能。
- 先给出可运行的最小版本。若要加控件，先问我，不要自行扩大问题范围。

10 自查清单

  • 我今天下午真正要回答的，是「看起来完不完整」，还是「某几个变量怎样组合才站得住」？
  • 这些问题里，有没有一个其实更适合先做 playground，我却习惯性开了三张画板？
  • 我准备对比的变体，是手工摆出来的理想稿，还是一开始就包含长文案、空状态、缺图和错误？
  • 动效、滚动、悬停和性能，我是在真实环境里感觉的，还是在画布上想象的？
  • 若让编程 Agent 来搭这场，我能不能先写出变量、范围、样本和「不回答什么」，而不是只说「做一个更好的原型」？
  • 这场打算跑在产品真正所在的环境里吗？字体、滚动和触控，会不会又变成近似？
  • 选中的值将如何离开这个下午——是导出 token / 代码，还是只留下几张截图？
  • 我有没有想把这个一次性工具做成内部平台？若有，它还是不是 playground？
  • 问题已经答完的时候，我愿不愿意把工具拆掉，而不是继续给它加功能？
  • 评审时，我们是在对着可切换的变量说话，还是在为三张看起来都完整的稿投票？

11 和读本相关篇怎么排

读本篇目它解决什么和本篇差在哪
No.62 光束变宽了，启发式没有生成让一次能看的方案变多，但「离目标还有多远」这把尺仍要人来写那篇管搜索时怎么打分和回头；本篇管尺子的载体：有些分，在静态稿上是打不准的，要把变量放到真实环境里拧
No.51 画布上并排试代码原型把代码层放到 Figma 画布上，和设计稿并排比较可运行的原型两条路都在追求「真一点」。那篇是把代码请回通用画布；本篇是离开通用画布，为单个问题搭一个用完可拆的场
No.45 加速实验，不外包思考设计工程师用 AI 加快实验，但不把判断交出去本篇把「实验」说得更具体：实验对象往往不是又一个页面稿，而是一个只活一个下午的专用工具
No.12 Stripe 的 Harbor用设计系统把 AI 原型变成公司里可共享的语言，避免「模糊紫泥」Harbor 是可复用的团队原型环境；playground 可以更轻、更一次性。系统负责品牌和组件的稳定，游乐场负责当下这个问题的变量
No.55 当一切都变得很容易制作几乎免费之后，设计师要改做编辑，主要是删两篇都在处理「便宜了以后怎么办」。那篇管页面上别因为容易就堆效果；本篇管工具层：别因为容易做工具，就把一次性尺子养成要维护的产品

若只记住一件事：通用设计工具仍然有用，但不必再承担每一个问题。现在可以为一个下午的问题搭一场专用的游乐场，在真实环境里拧变量，把选中的值带走，然后把工具拆掉。工具不必活过这个下午。
