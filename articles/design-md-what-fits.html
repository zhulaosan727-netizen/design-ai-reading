01 先给结论：三句话读懂这篇

第一，DESIGN.md 擅长说「产品该有什么感觉」，不擅长当活字典。Supernova 按规格手写 Backpack 的 DESIGN.md，文件里最终只有 32 个 token 级条目；而 @skyscanner/bpk-foundations-web 源里是 434。能读完的文件装不下全部真值——这不是失败，是格式边界。

第二，散文里的角色说明，比 YAML 色值列表更值钱。例如 Navy primary 扛主操作，Blue accent 只给链接与 hero、绝不做按钮底——这种「为什么有两支蓝」是 agent 生成新屏时最容易缺的推理。

第三，绿野新页可以用；已上线产品要另接 source of truth。alpha 规格下：复制的值会过期；组件 props 没有 schema 槽；modes / themes 不受支持。做法：md 写 intent（意图）；精确、当前、可解析的值让设计系统 MCP 或源包回答。

改已上线产品里的真实 Button不够：缺当前值、props、主题DS MCP / 源包 / 可 import 组件
跨工具便携身份强项（护照）与内部 MCP 同源，避免两套真相

02 434 → 32：差距为什么有用

Backpack 的 web foundations 包里有 434 个 design tokens。他们按 DESIGN.md 规格手写一份，最后文件里留下 32。文章把「差距」当作有用部分：格式适合告诉 agent 产品该有什么感觉；不适合承载 agent 在现有产品里构建时所需的精确值、组件 API 与版本。

对 Zhu 的启发很直接：个人站或小设计系统若把「全部 token 倾倒进 md」当安全感，文件会变得既不可读又迅速过期；不如主动做编辑——留下角色与禁令，把字典留给源头。

03 DESIGN.md 是什么（Stitch / alpha 规格）

DESIGN.md 是一份给 AI coding agents 描述视觉身份的 Markdown：顶部用 YAML 放 tokens，正文用白话写 rationale（理据）。Google Labs 在 Stitch 设计工具中引入，并在 2026-04-21 开源草案规格；GitHub 上的规格到 2026-11-03 仍标 alpha。

规格大致规定：

  • Token 组：colors、typography、rounded、spacing、components，可用 {colors.primary} 这类引用。
  • 正文顺序：Overview → Colors → Typography → Layout → Elevation & Depth → Shapes → Components → Do's and Don'ts。
  • CLI：lint 校验，diff 比较两版，export 转到 Tailwind 或 W3C DTCG。

社区热度很高：VoltAgent 的 awesome-design-md（从公开网站抽 DESIGN.md）在他们 2026-11-03 查看时约有 125,000 GitHub stars。另文提醒：项目 instructions（如 CLAUDE.md）是另一份文件、另一份工作，不要和 DESIGN.md 混为一谈。

读本 No.03 的 Vercel design.md 与本篇的 Stitch DESIGN.md 名字相近、职责同属「便携视觉意图」，但规格与生态不同。选型时先问：我要的是「仓库品牌说明书」，还是「Stitch/alpha 工具链可 lint 的那份」——再决定文件名与字段。

04 Backpack 实作：色彩角色胜过裸 token 表

选 Backpack 是因为它公开、成熟、持续发版。源取自 @skyscanner/bpk-foundations-web 24.9.0（2026-10-06）以及 @skyscanner/backpack-web 43.19.0 的 button API。

YAML 头部（文中缩写）是常见的 day mode 子集：primary / accent / surface、正文字阶、圆角、以及 button-primary 若干样式字段。真正赚到的是正文：

## Colors
Navy `primary` carries primary actions. Blue `accent` is for links
and hero surfaces, never for buttons.

## Do's and Don'ts
- Do use one primary button per view
- Don't use the accent blue as a button background

第二块是文件里最强的东西：它说明两支蓝为何存在、哪支能上按钮。裸 token 列表说不出这些；而这正是 agent 生成新屏时最常缺的推理。

That second block is the strongest thing in the file. — Supernova（大意：正文角色说明才是文件里最强的部分）

06 三条硬缺口：过期真值、无 props 槽、无主题

对「在已有产品里让 agent 构建」来说，三个缺口最伤：

  1. 解析后的值会过期。文件复制的是当时的值。Backpack foundations 到 2026 年 10 月初已有 12 次发布；组件包在 1–8 月间有 81 次稳定发布。每次都可能改掉文件仍当作事实的数字。diff 只能比两份 DESIGN.md，不能告诉你文件是否已与系统脱节。
  2. 组件 props 没有槽位。规格里 components 是最多约 8 个样式字段（backgroundColor、textColor、typography、rounded、padding、size、height、width）。Backpack button 有 16 个具名 props；loading 是否保宽、icon-only 要不要 label，只能写进散文。规格自己也说 components 部分「is actively evolving」。
  3. Modes 要么撑爆文件，要么出局。102 个 token 各有 day/night。alpha 无 theme 概念：你要么写两份文件，要么发明 primary-night 命名，要么像他们一样直接丢掉暗色。

07 够不够用？看任务而不是看信仰

新页面、要统一长相：够。agent 需要调色盘、字阶和一点品味时，DESIGN.md 是快且便宜的赢；也是 token 文件从不承载的规则终于能落笔的地方。

已上线产品内部：不够。那里 agent 必须吐出特定组件、正确 props、正确主题、今天的值。文件可读；agent 需要的是可 resolve 的东西——问 button-primary 就返回当前值、变体、映射到的组件。

这是所有摘要的交易：写下来那天准确，之后没有人提醒你它何时不准。他们联想到文档过期的同一模式。

对照 No.30 Atlassian：生产 playground 里整份 DESIGN.md 往往更贵、更慢、更不准，MCP/Skills 更合适。本篇从「手写真实 DS 子集」侧证明同一结论——不是 Atlassian 特例，而是便携快照的结构命运。

08 意图留在 md，精确值指向 MCP / 源头

建议策略很干净：

  • DESIGN.md 保留 intent：Overview、色彩角色、Do's and Don'ts；YAML 保持短，并在 Overview 注明取值自哪个 package version。
  • 凡是必须「今天精确正确」的，指向系统本身——这正是 design system MCP server 的工作：返回实体而非页面，例如带 resolved value 的 token、以及使用它的组件，在 agent 询问当下读取系统。

Supernova 提到自家 MCP 在各计划（含免费 Starter）上 lookup 不限次数，并另文比较各家 DS MCP、以及接到 Claude Code / Cursor 的步骤。对 Zhu：个人站若还没有 MCP，至少把「真值在 CSS variables / tokens.json」写进 Agent rules，并禁止模型把 md 里的旧 hex 当最终答案。

09 和 No.30 / No.03 / No.45 怎么排

  1. No.03 Vercel design.md：公开品牌向 md + 样式表 + eval——偏「仓库外也要像我们」。
  2. No.30 Atlassian：同一意图的便携文件，在生产对照里输给 MCP / Skills；护照 vs 档案柜。
  3. 本篇 Supernova：用真实 Backpack 数字回答「文件里该装什么」——装意图与角色，不装全集真值；并点名 alpha 的三缺口。
  4. No.45 Jakub：人怎么用 AI 加速而不外包思考——没有好的上下文路由（md vs MCP），再强的 craft 习惯也会被过期色值带偏。

建议顺序：先写短 DESIGN.md / design.md 锁定气质与禁令 → 绿野原型直接喂文件 → 组件库与主题稳定后接 MCP / 源包做真值 → 人侧用 No.45 的方式只加速脚手架与琐务，审美判断不外包。

10 可粘贴：写作清单与最小骨架

# DESIGN.md 编辑清单（动手前）
[ ] Overview 写清：气质一句话 + 取值 package 名与版本 + 今日只覆盖 day 还是双主题
[ ] YAML 只留「生成新屏用得到」的子集（目标：可读完，而不是 400+）
[ ] Colors 正文写角色：谁上按钮、谁上链接、谁绝对不能当主按钮
[ ] Do's and Don'ts 至少 5 条可执行禁令（对照 Zhu 硬规则可写入）
[ ] Components 只手写高频 1–3 个；props 细节指向源或 MCP
[ ] 另开一条 Agent rule：精确值以 MCP / tokens 源为准，md 仅 intent

# 最小骨架（示意）
---
version: alpha
name: MyProduct (day)
colors:
  primary: "…"
  accent: "…"
  surface: "…"
typography:
  body-md: { fontFamily: "…", fontSize: 1rem, lineHeight: 1.5rem }
rounded:
  sm: 0.5rem
components:
  button-primary:
    backgroundColor: "{colors.primary}"
    textColor: "{colors.surface}"
---

## Overview
一句话气质；token 取自 `@scope/pkg@x.y.z`（日期）；无暗色（或见 `DESIGN.night.md`）。

## Colors
说明 primary / accent 的职责边界（比再贴 20 个 hex 重要）。

## Do's and Don'ts
- Do …
- Don't …（含：禁止左侧竖向色条等产品级硬规则）

11 自查清单

  • 我是在写「意图护照」，还是在徒手复制第二份 token 字典？
  • 文件里最强的段落，是不是色彩角色与 Do/Don't，而不是 YAML 长度？
  • Overview 有没有写明 package 版本？三个月后有人知道它可能过期吗？
  • 当前任务是 greenfield 新页，还是改已上线组件？后者是否已指向 MCP / 源？
  • alpha 的三缺口（过期值 / 无 props 槽 / 无主题）我选了哪条权宜之计？
  • Agent 输出是 import 设计系统组件，还是根据 md 散文重画了一遍 Button？
  • 与 No.30 / No.03 的公开 md 是否职责清晰，避免三份互相打架的「真相」？

一句话收束：434 压成 32 不是偷工，是编辑。DESIGN.md 该装的是「你打算让产品感觉成什么样」以及「绝对不要怎样」；「今天准确的色值、props、主题」请指向还在发版的源头或 MCP。文件说你的意图，源头说今天的事实——让 agent 两个都听，而不是只听一份会过期的摘要。
