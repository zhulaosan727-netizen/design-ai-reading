01 先给结论：三句话读懂这篇

第一，Figma Agent 再强，也只等于你给它的上下文。上下文越具体——系统原则、当下任务——它越能做出「像你们产品」的决策，你越少花时间纠正 generic / off-brand 结果。

第二，设计系统里其实已经有大半原料：该用的组件与 token、文档化的规则、展示如何拼装的例子。难的是：在 prompt 时刻让 Agent 拿得到。

第三，记住四层投递：Guidelines（常驻规则）→ Library examples（拼装范例）→ Add context（任务专用文件 / 画板）→ Skills（可复跑流程）。库是砖，指南是选砖规矩，例子是砌法，Skill 是工法手册。

层住在哪何时自动生效最适合
Library已发布组件 / 变量聊天里启用 Libraries用对砖，而不是手搓
Guidelines挂在已发布库上的说明文件库启用时自动带入从零创建时的选用 / 例外
ExamplesExamples 页或名尾 _example作为可复用范例 / 或本次附件字段怎么分行、可选区怎么呈现
Skills斜杠命令你输入 / 触发审计、分析组件等重复流程

02 Agent 只与上下文一样好——DS 里已经有答案

Wayne 开篇定调：Agent 像任何协作者，价值上限由你提供的信息决定。有了正确上下文，输出会看起来、用起来像你们的产品，你少纠正「平均脸」。

设计系统本就囤着这些：组件、token、规则、例子。缺口不在「再写一份长 prompt」，而在 access at prompt time（提示时可达）。

Output from an agent is only as good as the context it’s given — Wayne Lin / Figma Blog（大意：Agent 输出只与它所获上下文一样好）

与 No.31 的衔接：维护篇让架子上的书回到格子；本篇让 Agent 新建时默认从正确格子取书。顺序建议：库能被读懂（名字 / 变量 / guidelines）→ 再谈生成质量。

03 第一层：接上 Library（组件与 token）

做法很具体：打开 Agent 聊天 → 在 prompt 框选 Libraries → 选中本项目要用的已发布库。接上之后，Agent 能识别团队批准的资产，并在输出里使用那些组件与 token。

结账流例子：若你要它做一张订单摘要卡，它可以拉取库里已有的 Card/OrderSummary/Default、批准的按钮变体、间距与颜色变量来组装——而不是从零发明一张「自带样式」的新卡。

若只要改屏上某一个资产（例如换某一个按钮），用 @-mention 点名组件或 token，做定向编辑。

04 库质量信号：名字、变体、变量、可复用模式

库对 Agent 有多有用，取决于它把行为说得多清楚：有意义的组件名、定义好的 properties / variants、应用 variables、以及展示小块如何拼成模式的可复用 pattern。这些是给 Agent 的强信号——每个资产是干什么的、该怎么动。

信号Agent 更容易做什么缺失时的典型翻车
有意义命名选对主组件另起 Frame 127 风格的手搓件
Properties / variants在已有变体里切换复制一层再改色
Variables绑间距 / 色 token硬编码 8px / #hex
可复用模式按你们的组装习惯拼组件对了，版式仍像陌生产品

05 第二层：Guidelines——判断写进库，自动进 prompt

有了库，Agent 知道有哪些砖；但「何时用、有何例外」往往读不出来。Guidelines 是挂在已发布设计库上的书面说明文件：库一启用，它们自动进入相关 prompt，设计师不必每句重申。

原文建议写进 guidelines 的内容：

  • 应 consistently 遵守的规则
  • 例外
  • 要避免的错误，以及改怎么做
  • 相似组件 / 变体 / 模式之间如何选择

添加路径：打开设计库 → Library → Manage guidelines → 上传文件 → Apply changes。

例子：库里同时有 primary / secondary 按钮，但结账屏「Place order」CTA 团队永远用 primary、「Back」用 secondary——把规则写进 guideline，Agent 就有具体选择依据。Guidelines 在 从零创建时效果最好；编辑已有设计时的一致性仍在改进中。

类型一句话寿命

07 第三层：Examples——比解释更强的「做成什么样」

给 Agent 一个「应该长什么样」的例子，往往比纯文字 prompt 更有力——就像你给同事一张现成结账屏当起点。

长期范例：把完整设计发布为组件，放在名为 Examples 的页面上；或在名称末尾加 _example（大小写敏感）。若是 component set，命名 / 页位置应用到父 set，不要只改某个 variant。可参考 Material 3 Design Kit。

本次专用：点 + → Attach Figma files，选或粘贴相关设计；也可直接贴画板 / 图片，或让 Agent 把截图变成可编辑设计。

航运地址表单例子：库提供字段与复选框；但「哪些字段共一行、公寓号等可选字段怎么呈现」需要例子来告诉 Agent。过去的设计范例给出分组与间距起点，它再适配本次结账体验。

Examples 与 _example 是约定，不是装饰。个人站若只有一套小组件：建一个 Examples 页，放 2–3 个「完整小节」（表单、空态、定价卡）当范例，比再写 500 字 prompt 管用。

08 第四层：Skills——教一次，斜杠触发

创建 skill：告诉 Agent 这个 skill 要做什么，给出步骤；可预览并在 markdown 编辑器里改。也可用 Community 技能或分享自己的。

重复流程——无障碍审计、检查是否用上最新组件——不要每次重写。冻成 skill，任意聊天里用 / 触发。例：

  • /design-system-audit：对照库检查选中屏，标出 detached 实例、硬编码值、误用组件、无障碍缺口
  • /analyze-components：查重复、命名错误、与库断开的组件，并建议路径

两者都可先 flag，再由团队决定让 Agent 执行或人自己改——与 No.31 的维护 skill 同构，只是本篇强调「生成侧也可复用同一套肌肉」。

09 从输出学习：修画布，回写规则

和任何 AI 协作一样，要复核。发现问题：在画布上直接让 Agent 改，或 @ 点名该用的组件 / token。若它 反复犯同一错，信号是：回去更新 guidelines、重访设计库、或给更好例子——而不是无限加长单次 prompt。

# 反馈闭环（建议贴在团队 wiki）
1. 生成 → 人审（品牌 / 选用 / a11y）
2. 单次错误 → 画布上 @ 修正
3. 同类错误 ≥2 次 → 写进 Guidelines 或补一个 _example
4. 流程性错误 → 冻进 /skill，下次斜杠触发
5. 库缺口（缺变体 / 烂命名）→ 开 DS 债，不靠 prompt 硬扛

10 与 No.31 怎么分工；个人站最小配置

  1. No.31 维护：文档、审计、批量换件、命名、token 采纳——归架。
  2. 本篇生成：Libraries + Guidelines + Examples + Skills——喂饱创建。
  3. 建议顺序：主库启用 + 一页 guidelines（选用 / 例外）→ 2 个完整 Examples → 1 个 /ds-audit-screen skill → 再扩。
# 个人站 / 小项目最小包（1 小时可起）
[ ] 发布一个小 library（哪怕 8 个组件）
[ ] Manage guidelines：上传 1 份 md
    - primary CTA vs secondary
    - 禁止另起按钮；必须用库变体
    - 间距只允许 spacing token
[ ] Examples 页：放「表单小节」「卡片列表」各 1
[ ] Skill：/brand-check —— 对照库列出未用组件的手搓层
[ ] 每次 Agent 聊天：先开 Libraries，再说话

11 自查清单

  • Agent 聊天里是否已启用正确 Libraries，而不是只靠自然语言描述品牌？
  • 需要定点替换时，我有没有 @ 组件 / token，而不是「把那个按钮改红」？
  • Guidelines 是否写了例外与「如何二选一」，而不只是赞美式原则？
  • 从零创建 vs 编辑已有——我是否接受后者仍可能要更多人工校正？
  • Examples 是否在 Examples 页或正确使用 _example（含 set 父级）？
  • 重复流程有没有冻成 / skill，而不是每次粘贴长 prompt？
  • 反复错误是回写了 guidelines / 库 / 例子，还是只在单次对话里生气？
  • 席位是否匹配（Full seat 等）？协作者是否只在草稿可用 Agent？

收束给 Zhu：No.31 教你归架，本篇教你喂料。Figma Agent 不会「懂你们队」，除非 library 砖块、guidelines 判断、examples 砌法、skills 工法在 prompt 时刻都在场。个人站也一样——先让小库可被启用，再谈生成像你。少纠正平均脸的时间，应来自上下文工程，而不是更长的一句「请做得有品味」。
