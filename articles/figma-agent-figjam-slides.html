01 三句话结论

第一，Figma Agent 走进 FigJam 和 Figma Slides，改变的不是又多了两个可以「生成界面」的地方，而是它开始接手设计工作里最耗时、却最不像画界面的两段：开会前的铺桌，和开会后的收束。设计经理用它把研究、上次结论、竞品和稿子并排铺到同一块板上；工程师用它把满板贴纸收成一份规格草稿；品牌设计师用它把已经写好的讲稿拆成演示架构。这些人要的不是自动开会，而是把准备和清理交出去，把讨论和叙事留给自己。

第二，铺桌的价值不是生成一块看起来完整的板，而是让会开始的那一刻，该到场的上下文已经到场。原文里，Figma 设计经理 Megan Bednarczyk 会先把设计稿摆上 FigJam，再让 Agent 通过连接器把以往评审反馈、竞品例子拉到稿子旁边，并整理出上次达成的方向和这次该问的问题。会因此不必从「我先翻一下记录」开始。

第三，收束的价值也不是让 Agent 替你做决定，而是把口头共识变成一份可以审、可以改、可以接着做的稿，并且这份稿就停在原讨论旁边。Johnny Dallas 把它写成规格，Jarrod Barretto 把它写成演示大纲。决定、取舍、故事怎么讲，仍然是人的。Agent 负责的是从杂乱到结构的那一段搬运。

会开完，满板贴纸和评论要靠一个人会后回忆、手抄成纪要或规格整理被推迟，决定留在大家的印象里，下一次又要从头解释当场把相关贴纸交给 Agent，收成带「决定 / 下一步 / 未决问题」的规格草稿，并且草稿就放在原反馈旁边，方便对照

02 画布上的 Agent，还没走进会议室

读本里已经有不少 Figma Agent 的篇目，它们多半发生在设计文件（Figma Design）的画布上：改布局、做变体、写规格、把静态稿做成代码图层（code layers）。那是「把界面做出来」的现场。可是一个资深设计师的一周，并不是只由画框组成的。大量时间花在设计评审（design crit）、研究综合、和工程对齐、以及把已经想清楚的事讲给别人听。这些工作发生在 FigJam 和 Slides 里，过去却常常要靠人在会前四处搜集、会后逐条整理。

Kamdar 这篇文章的产品消息很简单：Agent 现在可以在 FigJam 和 Figma Slides 里工作，并且能通过连接器和附件，把你已经在用的设计文件、会议转写、研究笔记带进来。真正值得停下来看的，是它把 Agent 的位置往外移了一格——从「在稿子上改」移到「让讨论能够开始、并在结束后留下可执行的东西」。

原文反复出现的句式几乎是同一件事的两种说法：在 FigJam，它帮你做准备和收尾，让团队把时间留给讨论本身；在 Slides，它帮你起头和收尾，让你把时间留给塑造叙事、把话讲清楚、为听众做准备。换句话说，Agent 被放到了会议的两端，而不是会议的中间。

编者点评：这和「让 AI 参加评审、替你发言」不是一件事。中间那一段——谁在坚持什么、哪个取舍不能让、哪句话其实还没达成共识——仍然要人在场。如果把两端的整理也理解成「会已经开完了」，你会少掉最需要判断的那一小时。

03 会前铺桌：让评议会开始在已经铺好的桌上

Bednarczyk 的做法值得拆开看，因为它很具体，也不神秘。她并不是对一块空白板说「帮我准备一场评审」。她先把这次要看的设计稿在板上摆好，然后才让 Agent 和连接器把材料招到稿子旁边：以往评审的反馈、竞品例子。Agent 会概括上次听到了什么、团队当时同意往哪走、这次会上该问什么，并在竞品例子旁加上模式提示。

There’s usually a lot of context to catch up on. What did we hear in research? What came up in Slack? What did we agree on last time?

——Megan Bednarczyk，Figma 设计经理，转引自 Jinen Kamdar，「The Figma agent is now available in FigJam and Slides」，Figma Blog，2026 年 11 月 23 日

这三句问法，其实就是评议会开始前最容易丢的三样东西：研究里听到的、非正式讨论里冒出来的、以及上次已经达成却没有写死的共识。过去它们分散在不同工具里，于是会的前二十分钟常常被「我先打开那个文档」吃掉。现在，铺桌的动作可以提前完成：把连接器（如 Notion、Google Drive）或截图、附件加进提示词，让这些材料出现在同一块画布上，和稿子并排。

用一个更贴近企业后台的例子。假设你要评审「运营平台的批量下发」。会上真正要判断的，往往不是按钮放左边还是右边，而是：上次可用性测试里，误下发的确认是不是还不够硬；客服工单里，有多少失败来自选错对象；上一次评审留下的开放问题是「要不要按权限拆成两步」；以及竞品是把确认做成模态框（modal）还是做成分步向导（wizard）。如果这些分别躺在研究库、工单系统、上次 FigJam 和一份竞品文档里，评议会就会先变成一次集体翻找。先把它们铺到稿子两侧，讨论才可能从判断开始。

原文还列举了 FigJam 里其他同样属于「铺桌或收拾」的用法：从研究和数据生成旅程图（journey map），把贴纸归成主题，把待办收成带负责人和截止日期的表格，以及布置一块头脑风暴板。它们的共同点是：把已经有的材料变成可以围着看的结构，而不是从一句空提示里凭空长出一块板。

编者点评：对企业后台，铺桌往往比消费级产品更值钱，因为上下文更碎，也更不在设计文件里。但有两件事不能省。第一，先摆这次要审的稿，再招材料进来，否则 Agent 很容易按「主题」重排，把你真正要对比的两版稿拆散。第二，Agent 的会前摘要只是起点，不是已经对齐。它最容易写得流畅的，往往是没有争议的部分；真正要在会上打的结，还得你自己标出来。

04 会后收束：从贴纸到规格，而不是会后再回忆

如果说会前要解决「上下文有没有到场」，会后要解决的是「决定有没有留下痕迹」。Dallas 的场景很典型：工程评审之后，板上会留下几十上百张贴纸、评论和各种聪明的意见。他的工作是把这些变成可以实施的东西。过去，这意味着会后再把每一条评论读一遍，既可能漏掉原话，也可能在细节上耗太久。现在，他可以选中相关贴纸，打开 Ask agent，直接往规格的第一稿走，而不是从空白页开始。

原文给出的提示词几乎可以直接用：Summarize this discussion as a spec. Include decisions, next steps, and open questions, and review the comments on the board, too. 翻译成工作语言：把这次讨论收成一份规格，写上决定、下一步和未决问题，并且把板上的评论也看一遍。Bednarczyk 在评审结束后也做类似的事：选中反馈贴纸，用 Organize → Summarize，让 Agent 生成一份概括讨论的规格，作为回顾决定、开放问题和下一步的起点。

这里有一个比「会后少做清理」更重要的设计选择：规格不是被带走、另存到一个再也找不到原讨论的地方，而是和原来的反馈停在同一块板上。Dallas 特别强调这一点——回头看的时候，既能看见团队决定了什么，也能看见他们是怎么走到这一步的。对后续实施、对下一次评审、对要向没参会的人解释「为什么不走另一方案」，这种并置都比一份孤立的纪要有用。

I’ll have a FigJam board that has dozens or hundreds of stickies and comments and opinions from all these smart engineers. My job is to take that and actually turn it into code.

——Johnny Dallas，Figma Specs 技术负责人，转引自同上

仍然回到企业后台的例子。权限矩阵（permission matrix）评审常常会出现相互顶着的贴纸：一组人要求更严的二次确认，另一组人嫌步骤太碎。Agent 很擅长把这些话写成一段通顺的「综合建议」。如果会上其实没有拍板，规格里就应该把分歧保留在「未决问题」里，而不是把它圆成一个看起来已经决定的方案。会后你要做的第一件事，不是赞美这份草稿写得完整，而是对照原贴纸，把被抹平的分歧找回来。

编者点评：会后收束最危险的失败，不是格式不好看，而是「假装已经决定」。综合（synthesis）和裁决（decision）不是同一件事。Agent 能把散落的意见收成结构，但不会自动知道哪一张贴纸只是情绪、哪一张才是约束、哪一句其实还在吵架。人要做的，是审这份规格，而不是签署它。

05 演示是同一套逻辑：先有材料，再生成结构

Figma Slides 这一侧，看起来像在做演示，其实重复的是同一套顺序：先有已经存在的材料，再让 Agent 生成结构或承担手工活，然后人来改叙事。

Barretto 做 Config 和内部活动的主题演讲时，并不是从空白幻灯片开始。他先拿到管理层一起写过的讲稿，然后让 Agent 按逻辑把内容拆成一页页的大纲：Break this up into individual slides so the content flows logically. Agent 给出一个他可以审、可以改的架构，再点 Generate deck 生成片子。他说，这给了他一个 architecture（架构）——一个可以开始往里填的起点。注意顺序：讲稿先在，大纲其次，成片最后；中间有一次人的编辑，而不是一次生成到底。

手工活的例子更具体。他可以丢一张电子表格截图给 Agent，让它按数据填出柱状图。过去他要按比例亲手把图描出来；现在他可以精确地要求图表看起来怎样，同时把数学准确性交给 Agent。也可以用你提供的数据从头做图，或用 CSV 更新已有图表。原文还列举了其他收尾动作：把同一套片子改给另一群听众、压缩全文案、请 Agent 对故事和页面给反馈、根据演讲者备注估算时长。

把这套顺序搬到产品评审的汇报里，会更清楚它为什么不是「AI 做 PPT」。假设你要向业务负责人讲「会议预约冲突怎么处理」。不该从「帮我做个汇报」开始，而该先有一页已经写清的结论：三种冲突各怎么处理、为什么放弃自动改期、哪些假设还没被验证。然后才让 Agent 把这页结论拆成演示结构。片子可以很快有，立场不能靠生成来补。

编者点评：演示这一侧最容易被用错。会前铺桌和会后出规格，材料边界相对清楚；做片子时，人们更容易把「还没想清楚」交给生成。Barretto 的方法能成立，是因为他输入的是已经共同写过的讲稿。如果你输入的只是一个功能名，Agent 会给你一套结构完整、但没有判断的演示——看起来像已经准备好了，其实只是把空白换了一种更体面的形状。

06 把手工活交出去，把判断和叙事留下来

把 FigJam 和 Slides 放在一起看，会看到一条分界线。该交出去的，是搜寻、归类、描图、按数据生成图表、把已有文稿拆成大纲、把满板贴纸收成章节。该留下来的，是这次会上到底要讨论什么、哪件事已经决定、哪件事还不能写死、以及面对这群听众，什么该先讲、什么该省略。

这也解释了为什么原文要强调连接器和附件。Agent 之所以能铺桌，不是因为它更会开会，而是因为它终于可以碰到设计文件之外的材料：转写、研究笔记、表格截图、云盘里的参考。上下文不到场，综合就只能靠模型的一般知识；上下文到场了，人才能检查它综合得对不对。

交给 Agent留给人
把分散在连接器和附件里的研究、旧反馈、竞品例子拉到稿子旁边决定这次评审要回答哪三个问题，并把真正的分歧标出来
把贴纸和评论收成带决定、下一步、未决问题的规格草稿对照原讨论，确认「决定」确实被决定过，没有被圆成假共识
把已有讲稿或规格拆成演示大纲，按数据生成或更新图表改结构、改语气、决定对这群听众先讲什么，以及哪张图其实在帮倒忙
缩短文案、估算时长、按另一群听众改一版片子的初稿判断这次改编有没有丢掉关键约束，尤其是风险和未验证的假设

07 对照表：三种用法，三种不该外包的事

场景原文里怎么做它真正加速的不能交给生成的
会前铺桌先摆稿，再用连接器和附件把研究、旧反馈、竞品拉到旁边，生成上次方向和本次问题让评议会从判断开始，而不是从翻找开始哪些材料必须到场、哪些摘要里的「共识」其实还是争议
会后收成规格选中贴纸和评论，要求写出决定、下一步和未决问题；规格留在原板旁边把清理变成当场可审的第一稿，并保留追溯什么算决定，什么仍是开放问题；下一步的优先级
从材料到演示从共同写过的讲稿出大纲，人改过后再生成片子；图表交给 Agent 按数据画结构草稿和手工描图叙事立场、对听众的取舍、以及数据该不该被画成那种图

08 可粘贴：评议会与演示的提示词模板

下面几段按原文里的实际用法写成可改的模板，并补上企业场景里常缺的约束。先把稿子、贴纸或讲稿选中，再把连接器或附件加进去。中文提示词 Agent 通常也能执行；关键字段建议保留英文，便于和原文功能对齐。

你是这场设计评审的会前助手，不是决策者。
这块板上已经放了本次要审的设计稿。请使用我附上的连接器 / 附件（上次评审记录、研究笔记、相关讨论、竞品例子），把上下文铺到稿子旁边：
1. 上次评审里达成的方向，以及当时明确留下的未决问题
2. 研究或反馈里，和这次稿子直接相关的发现（注明来源，不要改写成新结论）
3. 竞品或参考里反复出现的模式，用简短注释标在例子旁
4. 建议本次会上优先讨论的 3 个问题
规则：没有在材料里出现的共识，不要写成「团队已同意」；有分歧就并列列出。
请把我选中的贴纸、评论和讨论，收成一份规格草稿，仍放在原反馈旁边。请按下面三节组织，不要把它们混在一起：
- Decisions（决定）：只写讨论里已经明确拍板的事项，附上对应的原话或贴纸依据
- Next steps（下一步）：谁在什么时候做什么，未知就留空，不要编造负责人
- Open questions（未决问题）：把仍有分歧、被跳过、或只有一个人提到却没有回应的问题单独列出
然后再做一次自查：有没有把未决问题写成了决定？有没有漏掉我选中范围之外、但板上评论里出现的约束？
下面是已经写好的讲稿 / 规格结论，请先拆成演示大纲，先不要生成完整片子。
要求：
1. 每一页用一句话写出它在叙事里的任务（这一页要让听众相信什么）
2. 标出哪些页需要图表或原设计稿，哪些页只需要结论
3. 单独列出不该省略的约束、风险和未验证假设
请等我改完大纲，再生成页面。不要补充讲稿里没有的成果或承诺。
请根据我附上的表格截图 / CSV，更新（或生成）这张柱状图。
视觉上按我的指定来：[柱宽、轴向、是否显示数值、标注方式]。
数据必须和附件一致，不要四舍五入成「更好看」的数，也不要自行补全缺失值。若有算不清的单元格，请标出来，不要画进去。

09 自查清单

用下一场已经排上的评审或汇报试一次就够了，不必先改组流程。

  • 会前：要审的稿是不是已经摆在板上，而不是让 Agent 从空白板生成一场「评审」？
  • 会前：研究、上次结论、关键讨论和竞品是不是已经铺到稿子旁边，并且每条摘要都能指回来源？
  • 会前：你有没有亲自标出 2–3 个真正要讨论的分歧，而不是只带着一份流畅的会前摘要进场？
  • 会中：讨论有没有被「板上已经写了结论」带着走，还是仍在处理那些没写顺的争议？
  • 会后：规格草稿是不是在当场、从选中的贴纸和评论收出来的，并且就放在原讨论旁边？
  • 会后：你有没有对照原贴纸，把被写成决定的未决问题改回去？
  • 演示：输入的是已经有立场的讲稿或规格，还是一个功能名？
  • 演示：大纲是不是先经过人改，再生成页面？图表的数据有没有和附件对过？
  • 两端做完之后：准备和清理省下的时间，有没有真的回到讨论、判断和叙事上？

10 原文还没回答的问题

这是一篇功能说明，不是一篇方法论。它把三条真实工作流写清楚了，但下面这些问题仍然要你在自己的团队里回答。

  1. 连接器和附件能带到板上的，只是「所能及的材料」，不是「应该到场的全部材料」。权限、脱敏、以及企业里根本不在 Notion 或 Google Drive 的工单、日志、会议系统，原文几乎没有谈。铺桌之前，要先承认盲区。
  2. 会后综合会不会把分歧抹平？原文给了「决定 / 下一步 / 未决问题」这个结构，但没有谈当讨论本身含糊时，草稿该如何避免写成假共识。审稿规则需要团队自己立。
  3. 设计画布上的 Agent，和 FigJam / Slides 里的 Agent，什么时候该切换？例如，一个交互还没想清楚，是该先在设计文件里做成可玩的代码图层，还是先在 FigJam 里铺研究、开评审？原文把它们分开介绍，没有给切换原则。
  4. 生成出来的演示，如何守住品牌与设计系统？Barretto 的例子里，讲稿和图表精度是重点，视觉系统如何约束 Agent，几乎没写。做对外汇报时，这一点不能靠默认外观。
  5. Agent 起草的规格，所有权在谁？谁来审、谁来改、谁对「未决问题被写成决定」负责？如果没有人认领，收束就只是多了一份看起来完整的文件。
  6. 付费方案和「部分连接器」意味着什么，各团队能接到哪些内部系统，要以官方说明为准。本篇只讨论工作方式，不把它写成已经全员可用的承诺。

对做复杂 B 端系统的人，第 1、第 2 和第 5 条尤其尖。后台评审的关键上下文，常常不在设计工具的连接器名单里；而一旦规格草稿进入开发，假共识的代价会比消费级产品更高。铺桌和收束能加快会议两端，但不能代替会上那一次真正的拍板，以及会后有人认领这份稿。
