01 先给结论：三句话读懂 Specs

第一，Markdown 已是和 Agent 协作的默认格式，但本地 .md 是单人、脆的、和项目弱绑定的。多数上下文是短暂的；少数会演化成需要反复打磨、多人共写的关键输入——后者需要新容器。

第二，Specs = 住在 Figma / FigJam 画布上的多人容器：承载共享决策，并能引用 / 嵌入画布上的图、代码层、设计、frame、FigJam 节点，让文字与视觉并排，而不是截图或过期链接。

第三，工作流闭环是：用 Agent 拉入外部上下文 → refinement 成详细 Spec → 经 Figma MCP 送给编码 Agent（或在画布上建 code layer 边学边改）。对 Zhu：Specs 是「意图的持久家」，本地 AGENTS.md / design.md 仍管仓库规则；两者互补，不是替换。

02 为什么本地 .md 不够用了

越来越多产品建造者用 Markdown 和 Agent 协作——它几乎是分享上下文的事实标准。但原文点破：Markdown 帮助表达的上下文之外，它也缺很多上下文。本地 .md 往往是 single-player、文件之间关系脆、和「生出它的那个项目」几乎没什么硬绑定。

短暂上下文可以扔进聊天；会演化成关键输入、需要 refinement 与协作的那些——才值得 Specs。这和读本谈过的「durable context」同一问题：Agent 越强，意图越需要一个不会丢、可评论、可嵌入真材实料的住所。

Zhu 的对照：个人站仓库里的 AGENTS.md / design.md 很好——但它们看不见你 FigJam 里刚定的信息架构，也嵌不进那组已标 ready for dev 的 frame。Specs 要解决的正是「文字意图」和「画布真相」分裂的那条缝。

03 Specs 是什么：画布上的多人上下文容器

Specs 装的是共享决策（shared decisions），并引用你在画布上的工作——diagrams、code layers、designs 等等。它带有 Figma 独有的协作能力：可以把 FigJam 文件、frame、或画布上任意节点嵌进 Spec，于是文本与设计并排，而不是截图或 stale links。

因为 Figma agent 能读、能回评论，你可以像跟人协作一样和 Agent 协作——同一份 Spec 上开多条评论线程并行。

本地 .md / PRD 文档画布 Specs
玩家多为单人；评论靠外链工具多人 + Agent 同屏评论
与设计的关系截图 / 链接，易过期嵌入 frame / FigJam / 节点，可拖出再拖回
与代码的关系口头对齐或另开 ticket经 MCP 整包上下文；可旁挂 code layer
演化文件分叉、版本难对齐画布上的 durable 落点；可复制多版再收敛
适合仓库常驻规则、CI 约定仍在成形的意图、跨角色决策

04 怎么建、怎么嵌、Agent 怎么参与

创建：键盘 D，或点工具栏里的 Specs 图标（Figma / FigJam 皆可）。现有 Markdown：把任意 .md 拖进画布即可变成 Spec。

原文演示路径包括：把一份 PRD Spec 拖上画布，再让 Agent 结合 FigJam 脑暴里的新想法去扩展与 refine；Agent 可直接在 Spec 里回复评论。嵌入不是装饰——拖进画布内容（探索稿、用户流图）后，再拖出去仍可保留 Figma 属性。

# Specs 最小上手
1. D / 工具栏 Specs → 空白 Spec
2. 或：把 PRD.md / tech-spec.md 拖上画布
3. 从画布拖入 frame / FigJam 节点嵌入正文旁
4. @Agent 或评论区：请按 FigJam 结论补「开放问题」一节
5. 定稿后复制 Spec 链接 → 贴进编码 Agent 的 prompt（经 MCP）

05 一条真实工作流：Noah Finer 造 Specs 本身

Figma 工程师 Noah Finer 在做 Specs 功能时，用 Spec 给自己的编码 Agent 提供上下文：先写 guiding principles 覆盖边界情况，嵌入 FigJam 流程图，再分享给同事评论。

After the spec was finalized, I provided it along with my coworkers’ comments as context to my agent via the Figma MCP server. — Noah Finer（Figma eng，原文）

代码推进时，他用 MCP 回写画布上的原 Spec；并持续让 Agent 经 MCP 在 FigJam 画新图、嵌回 Spec、发给做 code review 的同事。这是「意图 ↔ 实现」双向更新，而不是一次性丢给 Agent 的死文档。

可抄的节奏：原则 + 图 → 人评 → MCP 给编码 Agent → 实现反哺 Spec → 新图嵌回给 reviewer。Specs 不是写完就归档的 PRD，而是活在画布上的工作内存。

06 连接器：GitHub 与 Hex 把外部真相拉进意图

Connectors 把外部上下文拉进 Specs。起草技术规格时，可用 GitHub connector 从代码库拉上下文；若团队用 Hex 做产品用量分析，而 PRD 里还留着开放问题——选中问题、挂上 Hex connector，让 Agent 跑分析并把结论以评论形式写回 Spec，「答案落在提问的位置」。

连接器典型用法落点
GitHub技术 Spec 对齐现有代码结构 / 约定Spec 正文或附注
Hex用数据回答 PRD 开放问题对该问题的评论
（画布本体）设计探索、用户流图嵌入节点，可拖出编辑

07 材料之间怎么流动：PRD ↔ 设计 ↔ 代码层

Specs 住在协作画布旁，紧挨它所描述的工作。可复制多份，让每人先改自己的版本再对齐方向。

Intuit Staff PD Mark Harvey 做图标系统时，把 Spec 放在图标旁边：每条记 filename、category、search tags、description——设计文件对非设计师也更好读。原文引用他的话大意：用一致格式的结构化文档，文件对非设计师更 accessible、更好 follow。

材料之间可以流体移动：Agent 把 PRD → designs / prototypes / code；也可把 designs / code → Spec。若在用 open beta 的 code layers（画布上的可运行代码），可选 Extract designs，按单屏 / 某状态 / 完整流程抽回可编辑设计层；在意图上加注释，工程师标 ready for dev 后，frame 继续挨着 Spec，双方对齐「到底要 ship 什么」。

08 定方向与飞轮：探索 → 沉淀 → 再探索

上下文一多，很难合成清晰下一步。无论是工程师在屏幕上的批注、描述新 DS 模式的 code layer、还是 crit 里的反馈，都可以合成一份可编辑文档，和相关上下文并排——任何人 zoom out 都能看到结构化文字 + 材料。

研究员 Mike Blight：探索时用 stickies / comments / annotations 推拉方案；反馈齐了，把决策与仍开放的问题收进 Spec；下一轮探索就有上一轮的 jumping-off point。他的飞轮：Explore together → consolidate → keep moving；Specs 给思考一个 durable place to land。

工程师 Kat Busch：准备广而告知时，把工作收进 Spec；Agent 当 Markdown 读。例如功能改名，可提示 Agent 直接改 Spec——「和 Agent 协作、又要广而分享」时最省事的方式。

09 交给编码 Agent：MCP + 链接即上下文

经 Figma MCP，像 Codex 这样的 Agent 可以读一份 Spec，并看到它链接的全部上下文：Markdown、frames、diagrams、code layers、Code Connect snippets。团队方向对齐后：复制 Spec 链接，贴进编码 Agent 的 prompt——上下文整包带走。

Specs 现为 open beta，全计划可用（web / desktop / mobile）。对 Zhu：这比「导出一堆截图 + 口头讲 PRD」稳定得多；也比只丢一个 GitHub 里的 spec.md 更贴近设计真相。

交接方式编码 Agent 看到什么风险
截图 + 聊天口述碎片、易过期漏状态、漏注释
仅仓库 Markdown文字完整，缺画布节点和最新 frame 漂移
Specs 链接 + MCP文 + 嵌图 + 代码层 + Code Connect需 Spec 本身维护得当

10 本地 AGENTS.md / design.md vs 画布 Specs

不要二选一。仓库 Markdown 管「永远生效的规则」；Specs 管「这个方向正在成形的意图与证据」。

AGENTS.md / design.md（仓库）Specs（画布）
生命周期长；跨任务常驻中；随功能 / 探索轮次
读者编码 Agent、CI、未来的你PM / 设计 / 工程 / Figma Agent
内容口味硬规则、目录约定、禁止事项PRD、决策、开放问题、嵌图、数据评论
多人靠 PR画布原生 + 评论线程
和视觉弱（除非再嵌链接）强（嵌入节点）
交给编码 Agent默认进上下文复制链接 / MCP 显式附上

跨篇：读本谈过 Atlassian DESIGN.md、Figma Agent Skills、Uber/Granola 用法——那些是「怎么让 Agent 懂你的系统」。Specs 补的是「系统之上、这一单功能的意图住哪」。先有仓库规则，再有画布 Spec；顺序反了容易把一次性 PRD 写进 AGENTS.md，污染全局。

11 Zhu 清单：何时放进 Specs

# 放进 Specs（画布）的信号
[ ] 决策还在变，需要评论线程与 Agent 同屏改
[ ] 必须并排看到 frame / FigJam / 流程图，截图会过期
[ ] 开放问题要用 GitHub / Hex 等连接器回答并落回原文
[ ] 准备把同一包上下文经 MCP 交给 Codex 等编码 Agent
[ ] 多角色（PM / 设计 / 工程）要对齐「到底 ship 什么」
[ ] 图标 / DS 条目等需结构化说明紧挨视觉稿（Harvey 模式）

# 留在仓库 Markdown 的信号
[ ] 口味与硬禁令（如禁止卡片左侧色条）——应进 AGENTS.md / skill
[ ] 目录结构、部署、测试命令——每次对话都该在
[ ] 与某一功能无关的长期约定

# 不要做的
[ ] 把仍在脑暴的粘滞便签直接当最终 Spec 丢给编码 Agent
[ ] Spec 定稿后不再回写（Noah 的反例：实现要反哺 Spec）
[ ] 只用 Specs 替代 design.md——全局规则会丢

12 提示词模板：FigJam + frames → 可交付技术规格

你在 Figma 画布上操作。当前已有：
- FigJam：<脑暴 / 流程板名称>
- Frames：<关键屏 / 状态，已标或未标 ready for dev>
- （可选）现有 PRD.md 已拖成 Spec

请生成 / 更新一份 Spec，结构如下：
1. 目标与非目标（各 3–5 条）
2. 用户流程（嵌入相关 FigJam 节点，勿截图）
3. 界面范围（嵌入 frames；注明哪些状态未覆盖）
4. 共享决策（已定）与开放问题（未定）
5. 工程约束（若有 GitHub connector，先拉代码库约定）
6. 验收标准（可测试、可演示）
7. 给编码 Agent 的交接摘要（≤15 行）

约束：
- 不确定处写成开放问题，不要编造答案
- 保留同事已有评论；对开放评论给出建议回复草稿
- 完成后给出 Spec 链接，供我粘贴进编码 Agent（MCP）
  • 你最近一份「给 Agent 的说明」是仓库 md，还是和 frame 脱节的聊天？
  • 开放问题是留在 Notion 里腐烂，还是能在提问处被数据评论回答？
  • 编码 Agent 拿到的是链接整包上下文，还是一堆过期截图？
  • 实现推进时，Spec 有没有被 MCP 回写？
  • 全局口味规则是否误塞进了某次功能 Spec？（应回到 AGENTS.md / Skill）

收束给 Zhu：Specs 的真正命题不是「又一个文档类型」，而是——当 Agent 进入设计与工程循环，意图需要一个多人的、可嵌入真相的、能经 MCP 整包交接的家。本地 Markdown 仍管常驻规则；画布 Specs 管正在成形的方向。下一周做功能前先问：这份上下文会过期吗？需要和图并排吗？要交给编码 Agent 吗？三个「是」，就按 D，开一份 Spec。
