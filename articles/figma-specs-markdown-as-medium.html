如今，随着与智能体协作逐渐成为常态，越来越多的产品构建者开始使用 Markdown 工作。它已成为共享上下文的事实标准格式。但 Markdown 虽然能帮我们表达大量上下文，也缺失了不少上下文。Markdown 文件往往是本地电脑上的“单人游戏”，文件之间的关联脆弱，也很少与催生它们的项目挂钩。大多数上下文转瞬即逝，但有些上下文会演变为关键输入，需要随时间推移不断打磨，并经过协作完善。因此我们打造了 Specs：一个支持多人协作的容器，让上下文得以充分表达，并能流入、流出 Figma，以及在其中流转。

Specs 承载你们共同做出的决策，并引用你在画布上的工作成果，包括图表、代码图层、设计稿等。它具备 Figma 独有的协作功能，例如可以直接在规格说明中嵌入 FigJam 文件、画框或画布上的任意节点，让文字与设计并排呈现，而不是散落在截图或过期链接里。而且由于 the Figma agent3 ways product designers use the Figma agent for craft, speed, and creative expressionHere’s how teams at Uber, Granola, and Atlassian support high-quality, fast-moving work with the Figma agent, now generally available. 可以阅读并回复评论，你可以像与真人协作者合作一样与智能体协作。

要创建规格说明，只需在键盘上按“D”，或点击 Figma 或 FigJam 工具栏中的 Specs 图标。

Specs 是设计意图成形的地方。你可以借助智能体引入外部上下文，一起把粗略的想法打磨成详尽的规格说明，再通过 Figma 的 MCP 服务器关于 MCP 的简明解读：为什么上下文很重要，以及如何用好它Figma 的 MCP 服务器把你的设计决策带入编写代码的工具中，让最终构建出来的产品与设计保持一致。以下是它能为每一位产品构建者带来的改变。发送给你的编程智能体，或者在上面构建代码图层，并随着认知的深入不断完善规格说明。

例如，Figma 软件工程师 Noah Finer 在构建 Specs 功能时，创建了一份规格说明，为他的编程智能体提供上下文。他先写下规格说明，梳理处理边缘情况的指导原则，嵌入 FigJam 中的图表来展示流程，然后分享给同事评论。“规格说明定稿后，我通过 Figma MCP 服务器，把它连同同事们的评论一起作为上下文提供给智能体，”他说。“随着代码不断推进，我用 MCP 在画布上更新最初的规格说明。我还持续让智能体通过 MCP 在 FigJam 中创建新图表，嵌入 Specs，再发送给负责代码评审的同事。”

连接器还能把外部上下文带进 Specs。例如在撰写技术规格说明时，你可以通过 GitHub 连接器，直接从代码库中提取上下文。再比如，你的团队用 Hex 查看产品使用数据，而 PRD 里有个悬而未决的问题，恰好可以用这些数据来回答。选中这个问题，添加 Hex 连接器，让智能体运行分析，并把结论作为评论留在规格说明上。答案就落在文档里，正是提出问题的地方。

你也可以把 Figma 画布上的内容拖进来，比如和团队一起头脑风暴出的设计探索，或是某个拟议用户流程的示意图。之后再把它们拖出去时，Figma 属性依然会保留。

在画布上的各种素材间自由切换

你的规格说明就放在 Figma 的协作画布上，紧挨着它所描述的作品。你可以把现有的 Markdown 文件拖到画布上，也可以让 Figma 的智能体在设计和代码旁边起草规格说明。你还可以在画布上复制规格说明，让团队成员各自同时处理自己的版本，再统一方向。

Intuit 的资深产品设计师 Mark Harvey 使用 Intuit Design System，正在设计一套新图标。为了记录这些图标，Mark 在 Figma 画布上图标的旁边添加了一份规格说明。每个条目都记录了图标的文件名、类别、搜索标签和描述，团队可以在同一个地方查看图标及其详细信息。“用排版清晰的方式记录下来非常有帮助，”Mark 说。“有了 Specs，引入一份结构清晰、格式统一、在每个文件里都保持一致的文档，设计文件对非设计师来说就更易于理解，也更容易跟进。”

在与团队头脑风暴时，你可以在不同的基础元素之间自如切换。用 Figma 智能体把 PRD 变成设计、原型和代码，也可以把设计和代码反过来整理成规格说明。如果你的团队正在用代码图层在画布上与代码一同设计今天，代码图层进入公开测试版。现在团队可以在画布上探索并构建由代码支撑的原型。进行探索，把可运行的代码带到画布上，选择 Extract designs 就能把它当前的状态转换回可编辑的设计图层。带回哪些内容由你决定：单个界面、某个特定状态，或完整的流程。为设计意图添加标注；工程师给出意见并把画框标记为可供开发之后，把它们和规格说明放在一起，这样设计师和工程师对最终要发布的内容就能保持一致。

把方向固化下来

上下文太多时，很难把它们提炼成清晰的下一步。无论你是想梳理工程师在界面上的标注、一个描述新设计系统模式的代码图层，还是设计评审中的反馈，都可以把这些输入整合成一份可编辑的文档，与你正在规划的内容放在一起。这样，任何人都可以缩小视野，在所有相关上下文旁边看到结构化的书面产出。

Figma 研究员 Mike Blight 在探索产品方向时，协作者会用便签、评论和标注来反复推敲各个选项。大家的反馈都收齐之后，他会把决定汇总到一份规格说明里，其中也包括团队仍在思考的问题。等团队准备开启下一轮探索时，上一次头脑风暴的上下文就成了现成的起点。“对我来说，这就是飞轮：一起探索，把成果沉淀下来，让工作持续向前，”Mike 说。“画布上有了 Specs，我们的思考就有了一个可以长久留存的落脚点，也有了下一步的起点。”

Figma 的智能体也可以参与协作。由于它能够读取和撰写 Specs 中的评论，你可以让它为规格说明上每一条未解决的评论回复一个建议的修复方案，同时团队成员也在同一份文档中发表意见。每场讨论都在各自的线程里进行，因此你可以像与真人协作一样，并行处理多个线程。

当 Figma 软件工程师 Kat Busch 准备好广泛分享自己的工作时，她会把内容整理成一份规格说明，之后她的智能体就可以将其作为 Markdown 读取。例如，如果某个功能的名称发生变化，她可以通过提示词让智能体直接更新规格说明。“对于我想广泛分享的内容，这是与智能体协作最简单的方式，”Kat 说。

发布到生产环境

通过 Figma MCP（模型上下文协议）服务器，Codex 等智能体可以读取规格说明，并查看其中链接的所有上下文。

团队就方向达成一致后，你可以把技术规格说明交给编码智能体去实现。只需复制规格说明的链接，并将其添加到你在编码智能体中的提示词里，所有上下文都会随之带上，包括 Markdown、对画框的引用、图表、代码图层以及 Code Connect 代码片段。

从最初的想法到最终的构建，Specs 为你的团队和智能体提供了一个共同的地方来打磨计划，并提供据此行动所需的上下文。

无论你是撰写 PRD 的 PM、记录决策的设计师，还是在规划架构变更的工程师，Specs 都能让团队中的每个人在完整上下文下探索、规划和实现。

Specs 支持网页端、桌面端和移动端，目前正面向所有套餐逐步开放公测。从这里开始使用，并在帮助中心了解更多。
