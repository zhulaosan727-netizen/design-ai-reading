01 三句话结论

第一，Skill 是按顺序写好的纯文本（markdown）指令，用来捕获设计师的观点与判断。不是工程师专属；你在 Figma 里用 Agent 就能写，许多 Skill 还能经 Figma MCP 在第三方 Agent 里跑，GitHub 上也有 MCP skills 仓库。

第二，真正可传播的是「你的品味被别人斜杠调用」。Miggi 的 /ease-like-miggi 让团队动效开始按他的缓动曲线走——这才是 Skill 相对普通提示词的跃迁：观点从个人习惯变成可触发资产。

第三，先抄十个社区 Skill，再发明你的。对照表覆盖影像、动效机会、镜头、手艺规则、交付文档、色 token、组件审计、状态展开、启发式评审、可用性讨论纲——几乎覆盖设计日常的关键镜头；抄的目的是学会「观点如何被切成斜杠命令」。

02 Skill 是什么：纯文本里的设计师观点

Miggi 把 Skill 说得很朴素：ordered instructions in plain-text markdown。关键不在文件格式，而在它捕获的是什么——设计师对「该怎么动、该怎么评、该怎么展开状态」的意见（opinion / judgment），而不是又一份组件 API。

层载体捕获什么触发方式
设计系统组件 / token / 文档站用什么（what）拖拽 / 查阅
SkillMarkdown 指令集怎么想、怎么评、怎么动（how）对话里 /
一次性提示词聊天框临时文字当场意图不可复用

原文还强调：你可以在 Figma 里直接让 Agent 帮你写 Skill；许多 Skill 通过 Figma MCP 在第三方 Agent 里同样可用。对团队这意味着——写一次观点，摊销到画布内与画布外。

若你读过 No.18，把本篇当成「案例货架」：No.18 给骨架与分工，本篇给十个已验证的斜杠命令标本，以及 Miggi 自己的「观点被调用」故事。

03 Miggi 的顿悟：/ease-like-miggi

Miggi 的 aha moment 很具体：他写了一个关于 easing curves 的 Skill，命名为 /ease-like-miggi。效果是——团队里的 motion 开始像他的手感。这不是「分享了一篇动效文章」，而是别人不用理解他的全部理论，只要斜杠一下，就能借用他的判断。

他还自己做了例如：

  • /image-audit——图像质量 / 问题审计；
  • /shader-starter——着色器起步脚手架；
  • /make-a-type-scale——生成字阶。

共同点：名字短、可念、指向一个清晰观点；输出是可执行结果，不是又一篇博客。

精神摘要：Skill 不是工程师专属——把你的观点写成斜杠命令，别人也能「ease like you」。—— 据 Miggi Cardona / Figma Blog

04 怎么写：从画板或步骤生成，再迭代

原文给出的创作路径很轻：

  1. 让 Agent 从某个 frame 或你描述的步骤生成 Skill；
  2. 预览（preview）它实际会怎么跑；
  3. 不满意就改——可以直接进 markdown 编辑器打磨措辞与边界；
  4. 发布到需要的范围（个人 / 团队）。
步骤你该盯什么常见翻车
从 frame / 步骤生成是否抓住了「观点」而不只是操作录像生成一长串菜单点击路径，换版本即失效
预览输出结构是否稳定、可扫读每次跑出来格式都不同
Markdown 迭代何时用 / 何时不用、边界、输出表头没有「不用」段，Agent 过度热情
发布名字是否可念、会不会撞车/helper、/fix 这类无法检索的名字

写 Skill 时把「工具相关落点」和「工具无关意图」拆开：意图段写「按我的缓动哲学选曲线」；落点段写「在 Figma 里改哪些属性」。MCP 换到别的 Agent 时，你只换落点段。

下面按原文介绍的十个社区 Skill 整理。抄之前先看「观点是什么」那一列——那才是你要偷师的，不是斜杠名字本身。

Emil 那条特别值得钉住：Skill 需要 persona 上下文，并且明确「哪里不该动」。没有「禁止项」的动效 Skill，往往会变成 over-animation 发生器——和 No.07 Agents with Taste 的提醒一致：生成是杠杆，克制才是品味。

06 按工作流归类：何时调用哪一类

工作流阶段优先 Skill你要的输出
视觉探索/xray-scan、/shader-starter（Miggi）非常规材质与起点，不是终稿
收进系统/create-color、/analyze-components、/make-a-type-scaletoken / 审计 / 字阶，可维护
补全状态/ui-state-expander状态矩阵 + 触发说明
动效与演示/find-animation-opportunities、/camera-pan-and-zoom、/ease-like-miggi该动何处、镜头怎么走、曲线像谁
交付与文档/component-handoff变体 / dos-donts / 解剖页
评审与研究/better-interface、/superfuture-design-review、/usability-test-guide问题清单、影响分级、讨论纲

实操建议：不要在一个对话里串十个 Skill。选一个阶段、一个镜头，跑完再决定要不要换镜头——否则输出会互相覆盖，你也不知道是谁的观点在说话。

07 Skill vs 设计系统：再钉一次钉子

和 No.18 同一根钉子，本篇用社区例子钉死：

信号更像 Skill更像设计系统
/better-interface 的规则书如何检查字体层级与文案语气具体的 type style 与组件 API
/create-color如何把现有色映射到 token 的步骤色板本身与语义命名表
/component-handoff文档页该有哪些区块、什么顺序组件源文件与代码绑定
/ui-state-expander要覆盖哪些状态与注释格式各状态的官方视觉规范

一句话：系统 = 组件；Skill = 你如何思考、评审、做动效、补状态。两者叠用，不要互相替代。

08 模板：发明你自己的 Skill

把方括号换成你的观点。名字要像 /ease-like-miggi 一样可念、可归属。

---
name: ease-like-[yourname]
description: 按 [你的名字] 的动效哲学为选中界面建议缓动曲线与时长；在动效评审或加 micro-interaction 时使用。
trigger: /ease-like-[yourname]
audience: 设计与前端；发布范围 = 本团队
---

## 观点（Point of view）
用 3–5 条写下「我相信什么」：
- 例：功能反馈用短 snappy；空间转场用稍长的 ease-out；装饰动效默认不加。
- 例：同一层级的元素共享曲线家族，不各自炫技。

## 何时用 / 何时不用
- 用：主路径已定，开始加 motion；或评审里争论「这个该不该动」。
- 不用：信息架构未定；或正在做无感 / 无障碍优先的静态稿。

## 输入
1. 询问 persona 与场景（谁在什么设备上完成什么任务）。
2. 请用户框选要评估的 frames / 组件。
3. 若上下文不足，先问 3 个问题再继续，禁止瞎猜。

## 步骤
1. 列出候选「可动点」，每个标注：触发、属性、建议时长、曲线。
2. 明确列出「不该动」的点及理由（防 over-animation）。
3. 按你的观点过滤：删掉违反观点的建议。
4. 输出表；若在 Figma，只改用户确认过的属性。

## 输出格式
| 元素 | 动？ | 属性 | 时长 | 曲线 | 理由 |
| ... | Y/N | ... | ... | ... | ... |

## 边界
- 不发明品牌里不存在的弹性夸张曲线，除非用户明确要求「好玩向」。
- 不把装饰动效标成高优先级。
- 规则盖不住时列为「待你决定」。

# 换一个镜头：状态展开版（可另存为 /states-like-[team]）
## 观点
我们默认主路径之外至少覆盖：loading / empty / error / disabled / partial / edge。
每条状态必须写：如何触发、用户第一眼看到什么、恢复路径。

## 步骤
1. 识别主路径帧。
2. 为每个关键组件展开上列状态；缺数据时用诚实占位，不编造业务文案。
3. 输出画布上的状态矩阵 + 注释。

09 自查清单 + 和读本其他篇对照

  • 斜杠名是否包含观点归属（like-miggi / like-team），而不是空洞的 /helper？
  • 有没有「何时不用」与「不该动 / 不做」段？
  • 输出是否强制表格或分级（红黄绿），方便人 10 秒扫完？
  • 是否需要 persona / 场景上下文？缺了是否会先问？
  • 和设计系统是否抢地盘——色值表有没有误塞进 Skill？
  • 是否在真实文件里跑通两次再发布到团队？
  • 经 MCP 外发时，是否默认草稿 + 人工确认？

10 编者点评

编者点评：Miggi 这篇最好的贡献不是「又推荐了十个插件」，而是把 Skill 从工程师话术里拽回设计桌：你的缓动、你的评审苛刻度、你的状态覆盖强迫症——都可以变成别人能 / 出来的东西。先抄表里的十个，不是为了堆斜杠，而是为了看见「观点如何被切成命令」。抄完之后，真正的作业只有一道：写出一个带你名字的 /…-like-you，让下周入职的人不用读你的长文，也能借用你的判断。和 No.18 一起读：一篇给理论与骨架，一篇给货架与勇气。
