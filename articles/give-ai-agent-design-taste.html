你的智能体并不是因为笨才没有品味，而是因为你没给它任何可以拿来判断品味的东西。语言模型会用训练数据的统计中心去填补你留下的每一处空白，而“漂亮的现代网页 UI”的中心，就是 Inter 字体、紫色渐变、居中的首屏，再加三张功能卡片。你要求“简洁、现代”，其实是在要求平均水平，得到的自然也是平均水平。

对智能体来说，品味就是上下文：具体的参考、真实的数值、有名字的模式，以及严格的约束，它们能把概率最高的答案从一团平庸中推开。下面是九种具体的供给方式，按影响从大到小排列，最后几项偏收尾打磨。uiscanner 只是清单中的一项，不是全部。

1. 从真实的参考出发，而不是形容词

最大的单项提升，是用具体的参考取代抽象的描述。NN/g 关于用 AI 做原型的研究说得很直白：含糊的提示词注定失败，解决办法是指向一种成熟的风格或某个具体的作品，而不是描述感受。“做得高级一点”，只会让你在同一团平均值里挪动几寸；“照 Linear 营销网站的样子来做”，则能一次性收敛上千个悬而未决的决策。

在你要构建的类型里，挑一两个你真心欣赏的网站，并点名它们。探索图库是浏览值得研究的网站拆解的快捷入口，从 Stripe 到 Linear 都有。以真实参考为锚点，是下面所有方法的基础。

2. 把参考变成设计令牌（design token）

点出网站名字会有帮助，但智能体仍然得去猜它的实际数值。要弥补这个缺口，就提取 Token：精确的颜色、字体族、字号阶梯、圆角、间距节奏、阴影和动效。Token 是一种外观风格的原子单位。把 #635bff 和 14/16/20/24 的字号阶梯交给智能体，它就不会再从训练数据的一锅乱炖里凭空编造颜色和字号了。

uiscanner 正是用武之地。粘贴任意公开 URL，它会返回一份设计拆解：Token（颜色、字体、字号阶梯、圆角、间距、阴影、动效）、逐个板块的结构，以及一份为 Claude 定制的构建提示词。它结合视觉识别与 DOM 来读取渲染后的页面，因此能找到真正的主按钮，而不是源码里的第一个按钮；能判断首屏是居中还是左右分栏；还能分辨哪些图像只是装饰（并附上提示词，用于重新生成原创素材）。它只做描述和 Token 提取，绝不复制或转存原始素材文件，所以你可以基于这些 Token 和结构，在自己的技术栈里重新搭建。

在网页应用里粘贴 URL，即可在浏览器中查看拆解结果；或者在接入 MCP（模型上下文协议）后（见第 5 节），让智能体通过一次工具调用直接获取：

ui_teardown("stripe.com", target: "landing")

3. 不只给 Token，也要给组件

Token 决定调色板，组件决定形态。一个基于 8px 网格的 #111 按钮，仍然可以有十种不同的实现方式。如果你的项目有组件库（shadcn/ui、Radix 或自研的基础组件），就按名称告诉智能体去用：“使用我们的 Button 和 Card 基础组件，不要另起炉灶。”你越明确地指向真实组件，智能体自行发明的东西就越少，跨会话的输出也就越一致。

这里常见的失败模式是：智能体悄悄重新实现了一个其实隔着三个文件就已存在的按钮。明确引用该组件，这种情况就不会发生。

4. 在上下文中给它看示例

品味最适合通过示范来传递。与其描述你的规范，不如从自己的代码库里挑两三个真实、写得好的组件放进上下文，然后说“照这个来”。比起一大段规则，智能体从三个优秀示例中，更能推断出你的间距习惯、命名方式、prop 模式，以及那份克制。

这是清单里成本最低、杠杆最高的一招。示例你本来就有，直接摆到模型面前，别指望它自己知道。

5. 接入 MCP 服务器，获取实时设计上下文

提示词转瞬即逝；而模型上下文协议（MCP）服务器是一条常驻的管道，智能体可以随时按需从中拉取结构化的事实。Figma 团队之所以把 MCP 视为关键突破，正是因为它用准确、机器可读的上下文取代了猜测：工具请求一个 Token 或组件，服务器返回的是真实的值，而不是幻觉出来的值。

uiscanner 就可以作为这样的服务器运行。一行命令即可将它接入 Claude Code：

claude mcp add uiscanner -- npx -y uiscanner-mcp@latest

它是一个 MCP（模型上下文协议）客户端工具，可用于 Claude Code、Cursor 和 Codex，安装页面涵盖了每一种的配置方法。它提供五个工具：

工具功能
ui_teardown(url, target?)将页面扫描为 Token、结构和构建提示词
ui_probe(url)低成本预检，不消耗扫描次数
get_teardown(id|link)重新获取已完成的 teardown
retarget_teardown(id, target)无需重新扫描，即可将构建提示词调整为另一种原型
whoami()查看套餐和剩余扫描次数

目标原型包括 landing、dashboard、marketing、ecommerce、portfolio、mobile 和 general。它仅支持 stdio，因此在你的本机运行，没有可指向的远程端点。每次扫描都会返回一个 id 和一个可分享的 uiscanner.com/t/<id> 链接。

6. 给它一份包含“采用”与“避免”清单的风格指南

一旦确定了方向，就把它写成一份简短、有态度的说明，让智能体每次都读一遍。这里最有效的模式是明确的“采用/避免”表述。由于模型会被强烈地拉向最常见的答案，列出要避免的内容和列出要采用的内容同样重要：不要三张一模一样的卡片排成一行，不要 99.99% 这类虚假精确的数据，不要处处使用渐变，不要用破折号。十条犀利的规则，胜过千言万语的描述。

把它放进仓库（AGENTS.md、DESIGN.md 或系统提示词），这样每次生成都会自动生效，不用你反复粘贴。

7. 把约束写进提示词

即便做到了以上所有，请求本身仍然需要边界。GenDesigns 的 AI UI 提示词框架是一份很实用的清单：平台、用户、输出规格说明、情绪/风格、模式/组件，以及技术约束。先把框架和样式方案交代清楚（Next.js、Tailwind、我们的 Token），点明布局模式（“分栏首屏、底部标签页导航、bento 网格”），迭代时使用精确数值。“增加 32px 的垂直内边距”胜过“多留点空间”，因为含糊的说法只会再次招来平均水平的结果。

8. 借助视觉反馈循环迭代

初稿只是草稿。真正的差异在于生成之后做什么。Agentic Coding Handbook 提出的视觉反馈循环就是这种模式：渲染 UI、截图、把截图回传给智能体、指出问题所在、重新生成，然后不断重复。把截图和提示词一起提供，模型就能直接看到实际输出，而不是它想象中的输出。条件允许时给截图加标注；圈出问题区域胜过用文字描述。

在这个循环里，参考稿才真正派上用场：把你的截图与最初使用的拆解稿对照，差距一目了然。

9. 用评测把关，而不是凭氛围

最后，在看输出之前先定义什么是“好”，这样你对照的是标准，而不是感觉。一个轻量的 UI 评测，就是每次都跑一遍的简短清单：是否使用了我们的 Token，是否复用了现有组件，是否达到 AA 对比度，是否避开了被禁止的模式，以及在间距和层级上是否与参考稿一致。让智能体按清单自查，并将新页面与之前的页面做 diff，以便在多页面构建中发现偏离。凭氛围检查只适用于一个页面；评测可以扩展到五十个。

贯穿始终的主线

这里的每一条，都是在不同层面做同一件事：用具体的事实取代悬而未决的决定。参考稿胜过形容词，Token 胜过参考稿，组件胜过 Token，示例胜过描述，实时的 MCP feed 胜过一次性粘贴，风格指南胜过记忆，约束胜过期望，反馈循环胜过初稿，评测胜过氛围。品味不是你说服模型去拥有的东西，而是你提供的上下文；你提供得越多，平均水平获胜的空间就越小。

最快的起步方式，是给你的智能体一份带有真实数值的真实参考。扫描一个你欣赏的网站，把 Token 和结构交给智能体，再在你自己的技术栈里构建。如果想在接入之前先看看拆解长什么样，可以去 explore gallery 浏览几个。
