01 三句话结论

第一，Skill 是「用自然语言写好的、可斜杠触发的工作方式」。在任意 Agent 对话里打 /，就能调出团队已经写好的指令集；可以发布到团队或组织，让别人不用再从零复述同一套流程。

第二，它不替代设计系统（design system），而是叠在上面。设计系统给组件与模式；Skill 给品牌语气、合规检查、评审镜头、仪式清单，并在更大工作流里调用设计系统。

第三，真正拉开差距的，是把藏在脑子里的默会知识（tacit knowledge）写成命令。Figma 自己先做了「模拟利益相关方反馈」「UX 文案初检」「首次用户视角」，以及 /catch-me-up、评审准备与复盘这类仪式 Skill——这些才是个人提示词变团队资产的路径。

“Skills are reusable plain-English instruction sets for the Figma agent.” — Sachi Shah & Sean Lee, Figma Blog

02 Skill 和设计系统各管什么

很多人一听到「把规范交给 AI」，立刻想到再写一份设计系统文档。原文的划分更清楚：两者互补，职责不同。

层管什么典型内容谁来维护
设计系统可见的组件与模式按钮、间距、色板、布局模板、可访问性基线设计系统 / 平台团队
Skill怎么用这些东西干活品牌声音、合规镜头、评审流程、批判清单、调用 DS 的步骤任何愿意把流程写清楚的人 / 小队

换句话说：设计系统回答「画布上该出现什么」；Skill 回答「Agent 在对话里该按什么顺序想、查、评、改」。一篇把两者糊成一份超长提示词的做法，往往既维护不动，又让 Agent 在组件细节和工作流之间来回迷路。

读本 No.04 已经讲过 Figma Agent 的自定义工具、上下文与 Skills 产品面；No.15 讲 Agent 如何直接在画布上守住设计系统。本篇往下钻一层：一旦 Skills 成为团队默认入口，你该写哪一类指令，才不会和 DS 抢地盘。

03 Figma 内部三类「视角 Skill」

原文举了 Figma 自己在用的三类「换一双眼睛」的 Skill。它们共同特点是：不生成一整页新 UI，而是用固定镜头压测现有方案。

Skill 类型做什么解决什么痛什么时候触发
利益相关方模拟按某位高管 / 干系人的评论风格给反馈（原文举例：模拟 CEO Dylan 的语气）评审前没人敢「唱反调」，正式会上一堆意外投评审页之前；关键决策前夜
UX writing 风格指南先过一遍大小写、标点、语气一致性文案细节占用真人评审时间文案冻结前的第一遍机器初检
首次用户视角假装第一次打开产品的人，标出专家看不见的摩擦熟手设计师对空状态、术语、入口视而不见新功能可用性走查；onboarding 改版

这三类都符合「视角（lens）」隐喻：同一张画布，换一副眼镜，输出的是问题清单，不是另一套视觉稿。和 No.07 Emil 的「用 skill 做评审」是同一家族——生成是杠杆，评审才是品味真正落地的地方。

做「模拟某人」时，务必写清：只模仿评论维度与严格程度，不要伪造真人原话对外传播。Skill 里应写明「输出为内部压力测试，不得当作该干系人的正式意见」。

04 把团队仪式写成 Skill

比视角 Skill 更「组织化」的，是把团队本来就在做、但每次都靠人肉串场的仪式，固化成斜杠命令。

/catch-me-up：总结文件里最近发生了什么。适合请假回来、跨时区接手、或评审前快速建立上下文。好的 catch-up Skill 会要求：按时间 / 决策 / 未决问题三段输出，并标明「仍不确定、需要问人」的条目，而不是假装读懂了一切。

评审准备（crit prep）：先访谈你要评什么——persona、范围、受众——再按 NNGroup 一类讨论提示，在画布上生成一张 crit 页。关键是「先问清楚再摆页」：很多失败的评审，不是反馈差，是评审页上堆了不该讨论的东西。

评审复盘（crit recap）：把反馈收成主题，再拆成决定（decided）/ 行动（action）/ 延后（deferred）；可以落成画布卡片，或经 MCP 推到 Slack。复盘 Skill 的价值在于强迫分类——没分类的反馈会在下一周消失。

仪式输入输出失败时常见症状
catch-me-up文件近期编辑 / 评论时间线 + 决策 + 未决只罗列图层改动，不谈意图
crit preppersona / 范围 / 受众问答带讨论提示的 crit 页跳过问答，直接贴一堆帧
crit recap评审评论与笔记主题化：决定 / 行动 / 延后原样粘贴聊天记录，无人认领

05 接上 MCP：上下文从哪来、结果往哪去

Skills 本身是指令；MCP 连接器（connectors）决定 Agent 能读什么、写回哪里。原文提到 Slack、Notion、Asana 等：可以把反馈记成任务、拉研究材料、用数据支撑方向。

方向例子Skill 里该写清的约束
进（context in）从 Notion 拉研究摘要；从 Slack 拉上周讨论只引用已授权空间；标注来源链接；过期资料要提示
出（result out）把 deferred 项建成 Asana 任务；把 recap 发到频道默认草稿 / 需人确认再发送；字段映射表写死
双向Crit 页上的 action 与任务系统同步状态以哪边为 source of truth；冲突时怎么提示人

原文还强调：Skills 同时适用于 Figma agent 与 Figma Make；并且很快会通过 MCP 在 Figma 之外也可用。对团队来说，这意味着「写一次斜杠命令」的投资，可能跨画布与原型工具摊销——前提是你把步骤写成工具无关的意图 + 工具相关的落点两段，而不是锁死在某一菜单路径上。

MCP 一接上外部系统，Skill 就从「提示词玩具」变成「半自动工作流」。安全与权限要写进 Skill 正文：哪些操作只读、哪些必须人工确认、哪些频道禁止机器人发言。没有这三行，发布到 org 级是不负责任的。

06 默认共享对话：提示词变成可学资产

协作文件里，Agent 对话默认共享。这听起来像隐私问题，原文却把它当成学习机制：你可以看见同事怎么提示、怎么改、怎么追问，从而学会更好的 prompting。敏感工作可以切到私人模式。

对设计负责人，这改变了「培训 Agent 用法」的成本结构：

  • 以前：开分享会演示自己的神级提示词，会后无人复用；
  • 现在：好的对话轨迹留在文件里，新人打开就能对照；
  • 配套动作：把反复出现的好对话，提炼成正式 Skill 发布——共享聊天是原料，Skill 才是产品。
模式适合风险建议
默认共享日常探索、评审准备、设计系统问答半成品思路被误读为结论在对话开头标注「探索中 / 已定稿」
私人人事、未公开路线图、客户敏感数据好提示词无法沉淀事后把脱敏版步骤写成 Skill

07 对照表：什么时候写 Skill、什么时候写设计系统文档

信号更适合 Skill更适合设计系统 / 文档
内容形态步骤、问题清单、输出格式、语气组件 API、token、布局网格
变化频率随项目仪式迭代（周 / 月）需版本治理（季度 / 半年）
触发方式对话里 / 即时调用画布里拖组件 / 查站点
成功标准输出可执行、可评审、可复盘界面一致、可访问、可实现
反例把色值表塞进 Skill（难维护）把「如何开评审」写进 DS 站点（没人打开）

一条实用启发式：如果你发现自己在三个不同文件里粘贴同一段「请你扮演…」——那就是 Skill 候选。如果你发现三个文件里按钮圆角不一致——那是设计系统问题，不是再写一条提示词能修好的。

08 模板：一份可粘贴的 Skill 骨架

下面骨架同时适用于 Figma Skills 与常见 Agent skill 文件；YAML 头可按平台删减。把方括号换成你们的内容即可。

---
name: crit-recap
description: 把设计评审反馈收成决定 / 行动 / 延后；可在画布生成卡片或经 MCP 发到 Slack。在评审结束后、需要主题化反馈时使用。
trigger: /crit-recap
audience: 设计与产品；发布范围 = 本团队
---

## 目标（Goal）
把零散评论变成可追踪的三类条目，并标明负责人与截止时间（若未知则标 TBD）。

## 何时用 / 何时不用
- 用：评审会刚结束；画布或 Slack 里已有原始反馈。
- 不用：还在发散探索、没有「需要决定」的压力时。

## 输入
1. 询问：评审对象链接 / 帧名、参与者、是否已有笔记。
2. 若接 MCP：只读取指定频道或页面；列出将访问的来源请用户确认。

## 步骤
1. 聚类：按主题合并重复意见（最多 7 个主题）。
2. 分类：每个主题下拆成 Decided / Action / Deferred。
3. 质检：Action 必须有动词 + 对象；禁止「再想想」这类空动作。
4. 输出：先给摘要表，再生成画布卡片；发送外部系统前暂停等人确认。

## 输出格式
| 主题 | 类型 | 内容 | Owner | Due |
| ... | Decided/Action/Deferred | ... | ... | ... |

## 边界
- 不伪造未出现的干系人意见。
- 不自动关闭或重开任务，除非用户明确授权。
- 规则未覆盖的情况列为「待你决定」，不要擅自发明流程。

# 视角 Skill 追加段（可嵌进上述骨架）
## 镜头（Lens）
你正在用「首次使用本产品的人」视角。
假设：不了解内部术语；只愿意花 90 秒完成首要任务。
禁止：用专家口吻辩护现状；禁止建议大改信息架构除非摩擦致命。
每条问题标注：位置（帧/文案）· 摩擦类型 · 建议的最小改动。

09 自查清单

  • 这条 Skill 解决的是「怎么干」，还是在重复设计系统已经规定的「用什么」？
  • 触发词（slash name）是否短、可念、不会和别的命令撞车？
  • 有没有写清「何时不用」，避免 Agent 过度热情？
  • 输出是否强制结构化（表 / 三类分类 / 严重级别），方便人扫一眼？
  • 涉及 MCP 写出时，是否默认「草稿 + 人工确认」？
  • 发布到团队前，有没有在一个真实文件里跑通至少两次？
  • 共享对话里出现的好提示，有没有人负责提炼进 Skill 库？
  • 敏感场景是否约定了何时切私人模式？

编者点评：Figma 这篇最有价值的不是又一个「快来用 Skills」的发布口径，而是他们自己先把默会流程产品化了——模拟老板、文案初检、新人视角、catch-me-up、crit 准备与复盘。很多团队停在「个人提示词收藏夹」；真正的飞轮是：共享对话里长出好做法 → 提炼成 Skill → 斜杠命令成为默认入口 → 新人不再从零学 prompting。设计系统让界面不像野花；Skill 让协作方式不像黑盒。两者都写清楚，Agent 才谈得上「更好的协作者」。
