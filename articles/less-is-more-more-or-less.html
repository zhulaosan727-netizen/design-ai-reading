01 先给结论：三句话读懂这篇

第一，AI 把「加」的成本降到了几乎为零，但没有降低「删」的成本。以前加一个动画、一个功能要几小时到几周，现在只要一两句提示词；可是判断「这个东西该不该存在」，仍然需要你理解用户、场景和后果。成本的天平一歪，产品就会越来越满。

第二，简洁 (simplicity) 来自理解，而不是来自删除。Jakub 借 Jony Ive 的话说，真正的简洁远不只是没有杂物和装饰，而是给复杂性建立秩序。你得先知道用户每天怎么用，才知道哪里该静、哪里该动。

第三，Agent 擅长执行，还不擅长判断。所以要把你的理解和判断「编码」下来：写成 skill、写成评审命令，让队友和 Agent 都按同一把尺子工作。原文的结论是：在 AI 时代，知道什么不该做，可能是最重要的技能。

“In the age of AI, knowing what not to build might be the most important skill of all.” — Jakub Krehel

02 为什么 AI 时代加法变「免费」了

原文开头是一种很多人都有的体验：每个想法、每个新功能、每个一直想做的动画，都只差几句提示词。像拥有超能力。但 Jakub 用得越久，越怀疑「拼数量」是不是最好的做法。更多人能更快地做出更多东西，并不等于做出了更好的东西。

编者把这件事拆成一张「加与删的成本表」，你会看到问题出在不对称上：

动作AI 之前的成本有 Agent 之后的成本没变的部分
加一个动画写代码、调曲线，半天一句「给菜单加个入场动画」判断它会不会每天打扰用户上百次
加一个功能排期、设计、开发，数周一个下午出可用版本判断它是否让主流程更难找
加一段文案或一个徽章要找文案或设计改稿Agent 自动「顺手」补上判断它传递的信息是否真实、必要
删掉一个元素要想清楚所有影响仍然要想清楚所有影响全部都没变

原文有一句很直白的观察：删除时你必须有意图、要把所有影响想清楚；而加法不一样，有了 Agent，你可以「闭着眼加，然后祈祷结果好」。这就是为什么 AI 生成的界面常常「什么都有一点」：渐变、徽章、悬停动画、提示气泡……每一样单看都不坏，加在一起就失去了主次。

这和我们说的「AI 味」是同一个病根的另一面。读本 No.01、No.09 讲的是模型会退回高频套路；Jakub 讲的是人在零成本面前也会退回「多放一点总没错」。前者靠约束模型解决，后者只能靠设计师自己的判断力。

03 简洁不是少放东西，而是理解够深

Jakub 给「为什么简洁更好」找了两个心理学依据，设计师都应该熟悉：

  • 认知负荷 (cognitive load)：大脑在某种意义上是一台节能机器，简单、可预期的东西更省力，体验也更不让人疲惫（原文引用了 Laws of UX 的相关条目）。
  • 处理流畅度 (processing fluency)：越容易被处理的东西，越会让人觉得熟悉、愉快、可信。换句话说，「好用」和「看起来可信」在心理上是连在一起的。

但他强调的重点不是「所以要少」，而是 Jony Ive 那句话的后半段：

“It’s about bringing order to complexity.” — Jony Ive（Jakub 原文引用）

编者用一个例子说明「删除式简洁」和「理解式简洁」的区别。假设你在做一个记账 App 的首页：

删除式简洁（只做减法）理解式简洁（先建立秩序）
做法把图表、标签、按钮砍掉一半先确认用户每天打开只为两件事：记一笔、看本月还剩多少
结果看起来干净，但用户要找的「本月预算」也被砍进二级页首屏只有「剩余额度」和「记一笔」，其余信息按使用频率下沉
评审时的说法「这样更极简」「这样用户 3 秒内完成最常见的任务」
能否交给 Agent能，但它会随机砍前提判断必须由你给出，执行可以交给 Agent

04 精讲：一个右键菜单的时间账本

原文最精彩的部分是一个可交互演示：两个看起来一样的右键菜单 (context menu)。一个在打开和关闭时都有动画，另一个只在关闭时有动画；一个给菜单项的悬停背景色 (background-color) 做了过渡动画，另一个没有。哪个更好？

直觉会说「动画越多越精致」。Jakub 的回答是：先想想这个菜单是谁、多久用一次。假设它就是 macOS 上右键弹出的那种菜单，人们一天会用几百次，甚至上千次。他算了一笔账：

参数数值
每天打开次数（原文假设）200 次
每次动画时长（原文假设）300ms
每天花在「看动画」上的时间200 × 0.3s = 60 秒，约 1 分钟
一年累计超过 6 小时

一年六小时盯着同一段菜单展开。动画在第一次时是惊喜，第一千次时就是阻碍。所以原文的结论是：一旦你理解了你在解决什么问题、人们怎么使用它，「不加动画」就成了显而易见的决定。他还补了一句很有意思的话：在某种奇怪的意义上，现在给东西加动画反而比不加更容易了。

原文没有逐条解释「为什么关闭可以保留动画」，下面是编者的解读，供你判断：

  • 打开是用户在等你。用户右键之后，下一步就是选菜单项，任何入场动画都在拖延这一步，哪怕只有 150ms 也能被手感察觉。
  • 关闭时用户已经不在等了。选完之后注意力已经转移到结果上，一个很短的淡出不阻塞任何操作，却能避免菜单「啪」地消失造成的突兀，让空间关系更连贯。
  • 悬停背景的过渡同理。鼠标在菜单项间快速滑动时，过渡会让高亮「拖尾」，看起来反而慢、软、不跟手；即时切换才显得利落。

这个例子之所以好，是因为它不是在讲动画技巧，而是在讲动画的前提。曲线、时长、弹性这些参数 AI 都能帮你调到很漂亮，但「这里该不该动」只能从使用频率和用户意图里推出来。这正是 Jakub 说「Agent 还做不到」的那部分判断。

05 编者延伸：按使用频率分配动效预算

把右键菜单的账本推广一下，就得到一张可以直接拿去评审的「动效预算表」。下表是编者整理的经验分档，不是原文内容，数值是起点而非标准：

使用频率典型元素动效策略建议时长
每天数百次右键菜单、命令面板 (command palette)、下拉、Tab 切换入场即时，最多保留极短的退场；悬停即时切换0–150ms
每天数次到数十次弹窗 (modal)、侧边抽屉、Toast 提示短而克制的过渡，用来交代空间来源150–250ms
每周或每次会话一次页面级转场、空状态、成功反馈可以有一点个性，但不能挡住下一步200–400ms
一生一两次首次引导 (onboarding)、发布页主视觉、成就时刻这里才是放「惊喜」的地方不设硬上限，但要可跳过

给 Agent 写动效需求时，把这张表的逻辑塞进提示词里，效果会比「加一些精致的微交互」好得多。关键是告诉它频率，而不是告诉它风格：

给这个菜单写交互动效之前，先回答：
1. 用户每天大约会触发它多少次？（我的估计：200 次）
2. 用户触发后，下一步要做什么？动画是否挡在这一步前面？
3. 一年累计会占用用户多少时间？（次数 × 时长 × 365）
如果第 3 题结果超过 1 小时，入场动画一律去掉，只允许 ≤120ms 的退场淡出。
悬停状态不加 transition。说明你的取舍，再写代码。

06 工程侧的同一件事：最少代码的 PR

Jakub 把同样的逻辑放到工程上。现在人人都能写出大量代码，用代码量衡量工程师产出的日子早就过去了。在他所在的 Interfere，团队会专门「庆祝」那些用尽可能少的代码完成目标的 PR。

他认为，审查代码、分辨好坏、批判性思考的能力，正在变得比写代码的能力更重要，也更稀缺。如果你缺乏理解就直接跳到「做」，你就很难判断 Agent 的输出是好是坏，也就没法把它引向好的方向。

Interfere 的做法值得设计团队照搬：

  • 一个自建的 /codebase-standards skill：写下团队希望人和 Agent 共同遵守的知识与原则；
  • 一个配套的 /interfere-review 命令：按这些标准审查代码。

原文的说法是，这样做是在尝试把团队的理解和判断「编码」成队友和 Agent 都能使用的形式。对设计团队来说，对应关系很清楚：

Interfere 的工程做法设计团队的对应物里面写什么
/codebase-standards/design-standards（或 design.md）你们的取舍原则，例如「高频组件不做入场动画」「一个页面只有一个主操作」
/interfere-review/design-review 评审命令逐条检查生成的界面是否违反上述原则，并给出删减建议
庆祝最少代码的 PR庆祝「删掉了什么」的设计评审评审记录里单列一栏：这次我们决定不做什么

07 Jakub 的七条 Agent 协作原则

原文末尾列了他自己与 Agent 协作时的一份短清单。编者把每条换成设计师的具体场景和动作：

原则（意译）在设计工作里意味着什么具体动作
别把思考外包出去问题定义、信息层级、取舍由你做先写一句「这个页面让谁完成什么」，再开 Agent
保持批判，别默认 AI 做的就是对的生成稿是草稿，不是答案每轮至少指出一处「为什么这样不对」
想清楚每样新增的东西是否让结果更好徽章、渐变、动画都要过「拿掉测试」逐个隐藏元素，看页面是否变差
Agent 是你的延伸：你越强，它越强你的审美上限就是它的上限持续积累参考与原则，而不是只积累提示词
尽可能多给上下文用 skills、命令、MCP，并明确你的偏好把设计系统、真实文案、使用频率一起给它
至少大致讲得清 Agent 加的代码在做什么别盲目接受每一处改动让它用三句话解释改了什么、为什么
不懂就让 AI 解释AI 是最强的学习工具遇到看不懂的 CSS 或动画参数，先问清原理再决定留不留

第四条「你越强，它越强」最值得反复读。很多人把 AI 当成弥补短板的工具，Jakub 的经验恰好相反：它是放大器。一个对动效频率没有概念的人，用 Agent 只会更快地做出更多打扰人的动画；一个有判断力的人，才能用它更快地做出克制的作品。

08 编者的保留意见

「少即是多」很容易被误读成「极简风格」。但 Jakub 的标题本身就留了余地：more or less，大概吧。原文自己也说，数量仍然重要，并且永远重要。编者补充两点边界：

  • 克制不等于没有个性。读本一直在讨论如何避开「AI 味」，而一味删减也会得到另一种千篇一律的「高级灰极简」。正确的做法是把表现力集中在低频、高价值的时刻（第 05 节表格最后一行），让高频操作保持安静。
  • 探索阶段可以放开加。用 AI 一次铺开十个方向非常有价值（读本 No.10 Nate Parrott 就是这么做的）。「少」针对的是最终交付的东西，而不是你的草稿数量。

10 模板：减法评审 Skill

下面是编者仿照 Interfere 的「标准 + 评审」组合写的设计版骨架，可以放进 Claude Code / Cursor 的 skills 目录，在每次生成界面后运行：

---
name: subtraction-review
description: 生成或修改界面后使用。逐个元素做减法评审，找出可以删除、可以安静下来的部分。
---

## 先收集上下文（缺了就问我，不要猜）
- 这个界面的主要用户和唯一核心任务是什么？
- 每个可交互元素的大致使用频率：每天数百次 / 数十次 / 每周 / 一次性

## 对每个元素回答四个问题
1. 拿掉它，核心任务会变难吗？不会 → 建议删除
2. 它表达的信息在页面其他地方已经有了吗？有 → 建议合并
3. 它的动效是否挡在用户下一步操作之前？是 → 去掉入场动画
4. 按「次数 × 时长 × 365」估算，它一年占用用户多少时间？

## 输出格式
| 元素 | 建议（删除 / 合并 / 去动效 / 保留） | 理由（一句话） |
最后单列「本次决定不做的事」，并说明理由。
不要新增任何元素；本 skill 只做减法。
# 单次使用的提示词
请对当前页面运行 subtraction-review。
核心任务：[例如：用户 3 秒内记一笔账]
高频元素：[例如：记账按钮、分类选择器，每天 10–30 次]
低频元素：[例如：首次引导、月度报告封面]
只输出评审表，等我确认后再改代码。

11 自查清单

  • 这次新增的每个元素，我都能说出它让结果「更好」在哪里吗？
  • 我知道界面里每个交互元素大概每天被用多少次吗？
  • 高频操作（菜单、命令面板、下拉）是否没有入场动画、悬停即时切换？
  • 惊喜和表现力是否集中在低频、高价值的时刻？
  • 我是否把团队的取舍原则写成了 skill 或 design.md，而不是只存在脑子里？
  • 我能用三句话解释 Agent 刚刚改了什么吗？
  • 评审记录里有没有「这次决定不做什么」这一栏？

一句话总结这篇：AI 让「能不能做」不再是问题，于是真正的问题变成了「该不该做」。克制不是一种风格，而是理解的副产品——你越懂用户每天怎么用，就越知道哪里应该什么都不发生。
