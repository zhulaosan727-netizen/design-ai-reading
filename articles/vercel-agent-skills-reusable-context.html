AI skills 把“一次性提示词”变成可复用、可版本化的智能体行为库。目标很简单：不必每次打开新对话，都重新解释项目里那些只可意会的经验知识。

Copy link to heading为什么需要 skills：“白板”问题

模型了解通用的编程语言和框架，但并不了解：

  • 你的文件夹结构
  • 你的设计系统
  • 你的部署规则
  • 在你的组织里“好”意味着什么

Skills 是上下文领域的“npm 时刻”：无需每次会话都复制粘贴冗长的指令，只需安装一次 skill，让智能体在相关时自行加载。

Copy link to heading1）理解架构

Copy link to headingSkill 与 skill package

  • 一个 skill 是包含 SKILL.md 的单个文件夹（可附带可选的辅助文件）。
  • 一个 skill package 是包含一个或多个 skill 的仓库（或目录）。

Copy link to heading被动上下文与主动上下文

你应该把上下文分成两类：

  • 被动上下文（始终可用）：对于始终适用的规则，使用 AGENTS.md（或你所用智能体的等效文件）。
  • 示例：安全护栏、格式规则、“始终使用 strict TS”、“绝不绕过身份验证”等。
  • 主动上下文（按需加载）：对于智能体仅在需要时才应加载的专门工作流，使用 skills。
  • 示例：“部署到 Vercel”、“分析 CSV”、“撰写 PRD”、“审查 React 代码的性能”。

Copy link to heading渐进式披露（skills 如何避免上下文臃肿）

Skills 的设计目标是让智能体不必一次性加载所有内容：

  1. 元数据（name + description）会提前提供，以便智能体判断该 skill 是否相关。
  2. 完整指令（SKILL.md 的正文）只在智能体激活该 skill 时才加载。
  3. 资源（脚本/参考资料/资产）只有在 skill 指示智能体使用时才会加载。

Copy link to heading2）Skill 的结构（必须准确无误的部分）

Copy link to heading必需的目录结构

一个 skill 是一个目录，至少包含一个 SKILL.md 文件：

my-skill/└── SKILL.md

Copy link to heading必需的 YAML frontmatter

SKILL.md 必须以 YAML frontmatter 开头，并包含：

  • name（必填）
  • description（必填）

最小示例：

---name: my-skilldescription: Do X for Y projects. Use when the user asks about X or mentions Y.---
# Instructions
(Your steps, constraints, and examples go here.)

Copy link to headingname 与 description 的关键约束

  • name 必须与所在父目录的名称一致。
  • name 只能包含小写字母、数字和连字符（不允许大写）。
  • description 应说明该 skill 做什么，以及何时使用。

Copy link to heading可选的 frontmatter 字段（可移植）

这些字段属于规格说明的一部分，可在各生态中放心使用：

  • license
  • compatibility（仅在存在环境要求时使用）
  • metadata（任意键值数据；适合存放你的 semver 版本号）
  • allowed-tools（实验性；各智能体的支持情况不一）

Copy link to headingSkill 正文（Markdown 指令）

Markdown 正文没有强制格式，但若想要稳定可靠的效果，建议采用可预期的结构：

  • 该 skill 的作用
  • 何时使用（以及何时不用）
  • 所需输入
  • 分步骤流程
  • 验证 /“如何确认已完成”
  • 常见失败模式与修复方法

Copy link to heading可选的辅助目录（推荐用于实际的 skill）

使用这些目录可以保持 SKILL.md 简洁，并仅在需要时才加载细节：

  • scripts/ — 可执行的辅助脚本
  • references/ — 较长的文档、检查清单、模板
  • assets/ — 静态模板、示例配置、图表

Copy link to heading3）加载策略，以及“何时应该做成 skill？”

Copy link to headingdescription 就是触发器

大多数系统主要根据 description 来决定是否激活某个 skill。所以不要把 description 当作标题，而要把它当作路由规则。

不好的写法：

  • “帮助处理 PDF。”

好的写法：

  • “从 PDF 中提取文本和表格、填写表单、合并文档。当用户提到 PDF、表单、扫描或文档提取时使用。”

Copy link to headingSkill 与 AGENTS.md（什么内容放在哪里）

直说吧：

满足以下情况时，放进 AGENTS.md：

  • 几乎适用于所有任务
  • 你希望可靠性最大化（无需判断是否激活）
  • 智能体绝不能忽略它

满足以下情况时，放进 skill：

  • 属于专门化的工作流
  • 只是偶尔使用
  • 你希望它能在不同仓库/团队间被发现和复用

Copy link to heading渐进式复杂度（一种实用的经验法则）

从简单开始，只有真正碰壁时才增加复杂度：

  1. 仅用 Markdown 的 skill（大多数 skill）
  2. 需要确定性自动化时，添加 scripts/
  3. 只有在需要严格的类型化载荷，或需要对外部调用进行强力控制时，才使用工具/MCP（模型上下文协议）集成

Copy link to heading4）使用 skills CLI（安装、管理、发现）

Copy link to heading安装 skills

像这样安装一个包（仓库）：

npx skills add <owner/repo>

CLI 支持多种来源，包括直接指向 skill 的路径和本地文件夹：

npx skills add vercel-labs/agent-skills
npx skills add https://github.com/vercel-labs/agent-skills
npx skills add https://github.com/vercel-labs/agent-skills/tree/main/skills/web-design-guidelines
npx skills add https://gitlab.com/org/repo
npx skills add git@github.com:vercel-labs/agent-skills.git
npx skills add ./my-local-skills

Copy link to heading实际会用到的常见安装选项

npx skills add -g vercel-labs/agent-skills
npx skills add vercel-labs/agent-skills --list
npx skills add vercel-labs/agent-skills --skill frontend-design --skill skill-creator
npx skills add vercel-labs/agent-skills --skill frontend-design -g -y
npx skills add vercel-labs/agent-skills --all

Copy link to heading安装范围（项目级 vs 全局）

CLI 可以安装到：

  • 项目范围（随仓库提交，与团队共享）
  • 全局范围（当前用户的所有项目均可使用）

也可以根据你的环境，通过符号链接（推荐）或复制的方式安装。

Copy link to heading5）发布与可发现性（“上架”究竟如何运作）

Copy link to headingskills.sh 没有专门的发布命令

要“发布”一个 skill：

  1. 把它放进一个 git 仓库。
  2. 分享这个仓库。
  3. 当人们通过 npx skills add 安装它时，它可以借助安装遥测自动出现在 skills.sh 上。

就这么简单，无需提交到任何注册表。

Copy link to heading公开 skill 仓库应包含哪些内容

最低要求：

  • 你的 skill 文件夹，其中包含 SKILL.md

强烈建议：

  • 一份 README.md，说明这些 skill 的用途及安装方式
  • 清晰的许可证与归属信息
  • 若包含脚本，附上安全备注

Copy link to heading安全现实检查

像对待代码一样对待 skill：

  • 安装前先阅读
  • 尤其要小心 scripts/（它们可以执行命令）
  • 固定使用已知仓库，更新时审查差异
