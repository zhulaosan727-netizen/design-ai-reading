01 先给结论：三句话读懂 Skills

第一，Skills 把一次性提示词变成可版本管理的 Agent 行为库——解决 blank-slate：模型不懂你的目录、设计系统、部署规则、以及你们组织里「好」的定义。

第二，Skill = 含 SKILL.md 的文件夹（可加附属文件）；skill package = 含一个或多个 Skill 的仓库。被动上下文用 AGENTS.md（永远生效）；主动上下文用 Skills（按需加载的专项流程）。

第三，靠 progressive disclosure 控体积：先暴露 name+description 做路由 → 激活后再读正文 → scripts / references / assets 仅在需要时加载。对 Zhu：别再每个新对话重讲设计系统——装一次 Skill，让 Agent 在相关时自己捡起来。

02 空白石板问题：模型不懂「你好」意味着什么

模型懂通用语言和框架，不懂：你的 folder structure、design system、deployment rules、以及在你组织里 what “good” means。每次开新聊天都把部落知识再粘贴一遍——这是在用人力补上下文协议的缺口。

原文把 Skills 称作上下文的「npm moment」：不是每次会话 copy/paste 长说明，而是安装一次，让 Agent 在相关时加载。

和读本 No.01 附近 Anthropic「Improving frontend design through Skills」同构：前端变好看，靠的不是更长的一次性 prompt，而是可复用的 Skill。本篇补工程层：怎么写、怎么装、怎么和 AGENTS.md 分工。

03 架构：Skill vs 包、被动 vs 主动上下文

SkillSkill package
形态单文件夹，至少有 SKILL.md仓库 / 目录，含一个或多个 Skill
安装单位可按 --skill 名挑选npx skills add owner/repo
类比一个 npm 包里的一个 bin/模块整个 npm scope / monorepo
被动上下文（AGENTS.md）主动上下文（Skills）
何时在几乎每个任务专项工作流被路由到时
例子安全护栏、严格 TS、永不绕过鉴权、格式约定部署到 Vercel、分析 CSV、写 PRD、React 性能审查
可靠性最高（无激活决策）依赖 description 路由质量
体积压力必须短而硬可厚，因按需加载

04 渐进披露：三层加载，避免上下文肥胖

Skills 故意不让 Agent 一上来读完全部：

  1. Metadata（name + description）早期可见，供决定是否相关。
  2. Full instructions（SKILL.md 正文）仅在激活时加载。
  3. Resources（scripts / references / assets）仅当 Skill 指示需要时再加载。

这是在和「把 40 页设计规范塞进系统提示」对着干：路由薄、正文适时、附件更懒。

披露层
┌─────────────────────────────┐
│ 1 name + description（路由） │  ← 几乎总在
├─────────────────────────────┤
│ 2 SKILL.md 正文（步骤/约束） │  ← 激活后
├─────────────────────────────┤
│ 3 scripts/ references/ assets/│  ← 用到才读
└─────────────────────────────┘

05 SKILL.md 解剖：name、description 才是路由

最小布局：目录里至少一个 SKILL.md。文件必须以 YAML frontmatter 开头，且包含必填字段 name、description。

---
name: my-skill
description: Do X for Y projects. Use when the user asks about X or mentions Y.
---

# Instructions
（步骤、约束、例子）

硬约束：name 必须与父目录名一致；仅小写字母 / 数字 / 连字符。description 要写清 做什么 + 何时用——它是 routing rule，不是标题。

坏 description好 description
写法Helps with PDFs.Extract text and tables from PDFs, fill forms, merge documents. Use when the user mentions PDFs, forms, scanning, or document extraction.
问题Agent 不知何时激活触发词与能力边界清楚

可选、跨生态相对安全的 frontmatter：license、compatibility、metadata（适合放 semver）、allowed-tools（实验性）。

06 正文结构与可选目录

正文无强制格式，但想要可靠，用可预期结构：

  • What this skill does
  • When to use it（以及 when not）
  • Inputs needed
  • Step-by-step procedure
  • Validation / 怎样算做完
  • Common failure modes and fixes

可选目录，用来保持 SKILL.md 精炼：

  • scripts/ — 可执行辅助
  • references/ — 长文档、清单、模板
  • assets/ — 静态模板、示例配置、图

07 何时用 AGENTS.md，何时用 Skill

原文说得很直：

放进 AGENTS.md放进 Skill
几乎每个任务都适用专项工作流
要最大可靠性（不做激活决策）偶尔才用
Agent 绝不该忽略希望跨仓库 / 团队可发现、可复用

Zhu 硬规则「卡片/告警禁止左侧竖向色条」——这是几乎每次做 UI 都不能破的，更适合 AGENTS.md 或「永远相关」的短规则；完整的 frontend-design / taste 流程（步骤、反例、检查清单）则做成 Skill，避免把 AGENTS.md 撑成小说。

08 复杂度阶梯：先 Markdown，再脚本，最后才 MCP

  1. Markdown-only（多数 Skill 停在这）
  2. 需要确定性自动化时再加 scripts/
  3. 需要严格类型载荷或强控外部调用时，才上 tool / MCP

别一上来就为「改间距口味」挂三个 MCP——先把 description 和正文写清楚。

09 skills CLI：安装、发现、更新

# 安装包
npx skills add <owner/repo>
npx skills add vercel-labs/agent-skills
npx skills add https://github.com/vercel-labs/agent-skills/tree/main/skills/web-design-guidelines
npx skills add ./my-local-skills

# 常用选项
npx skills add -g vercel-labs/agent-skills          # 全局
npx skills add vercel-labs/agent-skills --list      # 只列不装
npx skills add vercel-labs/agent-skills --skill frontend-design --skill skill-creator
npx skills add vercel-labs/agent-skills --skill frontend-design -g -y   # CI 友好
npx skills add vercel-labs/agent-skills --all

# Day-2
npx skills list
npx skills find typescript
npx skills remove web-design-guidelines
npx skills check
npx skills update
npx skills init my-skill

安装范围：项目级（进仓库、团队共享）或全局（本机跨项目）。可用 symlink（推荐）或 copy。生态入口：skills.sh、agentskills.io、vercel-labs/agent-skills 等（见原文 Resources）。

10 发布与安全：git 即发布，脚本要当代码审

没有单独的「publish 到 skills.sh」命令：把 Skill 放进 git 仓库 → 分享 → 别人用 npx skills add 安装时，可经 install telemetry 出现在 skills.sh。公开仓库至少要有 Skill 文件夹 + SKILL.md；强烈建议 README、许可、若有 scripts 则写安全说明。

安全现实：把 Skill 当代码——安装前读；对 scripts/ 尤其小心（会跑命令）；钉住已知仓库，更新时看 diff。

11 映射到设计工作：decision table

设计侧材料更像建议载体
禁止左侧 accent bar、字体栈、圆角阶梯永远生效的硬规则AGENTS.md（短）或 always-on 片段
「做营销页 / 仪表盘」的完整步骤与反例专项工作流Skill（如 frontend-design）
某品牌页的色板与语气项目便携上下文design.md（读本多篇）+ 必要时 Skill 引用它
一次性「帮我改这页 hero」会话提示聊天即可；重复第三次 → 抽成 Skill
Figma 画布上的功能意图多人、嵌图Specs（见 No.38），不是 SKILL.md

12 Zhu 迷你 SKILL.md：UI 口味 / 禁左侧色条

下面是一份可直接改名使用的草稿——description 按路由规则写；硬禁令与读本共用 skill「zhu-design-hard-rules」对齐：绝对禁止在卡片 / 告警 / 详情面板 / 列表行左侧加竖向色条或 border-left accent bar；状态与强调改用标签、图标、表面色温或顶边 / 全框。

---
name: zhu-ui-taste
description: Apply Zhu's UI taste rules for cards, alerts, panels, and lists.
  Ban left accent bars; prefer tags, icons, surface warmth, or top/full borders.
  Use when generating or reviewing UI, polishing layouts, writing Codex design
  prompts, or the user mentions 卡片, 告警, accent, border-left, or 设计硬规则.
---

# What
Enforce distinctive, non-generic UI that matches Zhu's hard visual rules.

# When to use
- Generating or refactoring cards, alerts, detail panels, list rows
- Writing design prompts for Cursor / Codex
- Reviewing AI-generated UI for "AI slop" accents

# When not to use
- Pure backend / data tasks with no UI surface
- Brand systems that explicitly require a different accent language
  (still never invent left bars unless user overrides in writing)

# Inputs
- Target files or screenshots / descriptions of the UI
- Optional: design.md or component list

# Steps
1. Scan for border-left / left vertical accent bars on cards, alerts,
   panels, list rows — remove them.
2. Re-encode status with: tags, icons, surface temperature, top border,
   or full outline — not a left rail.
3. Prefer neutral light gray page chrome; avoid greenish/bluish gray drift.
4. Keep density intentional; no decorative gradients as status.
5. Summarize changes as a short checklist the user can skim.

# Validation
- [ ] No left accent bars on the listed surfaces
- [ ] Status still readable (color + label/icon, not color alone)
- [ ] No new generic "AI look" chrome

# Failure modes
- Model "softens" the ban into "subtle left bar" — reject; ban is absolute
- Over-tagging every row — prefer one clear status cue

13 安装清单与自查

# 安装前
[ ] 打开仓库 README / SKILL.md，通读 description 与 scripts/
[ ] 确认来源是已知 owner（如 vercel-labs）或自己的 fork
[ ] 需要全局还是仅本项目？默认偏项目级，团队可复现

# 安装
[ ] npx skills add owner/repo --list 先看有哪些
[ ] npx skills add owner/repo --skill <name>  [-g] [-y]
[ ] npx skills list 确认就位

# 维护
[ ] npx skills check / update；更新前看 diff
[ ] 重复粘贴第三次的提示词 → skills init 抽成 Skill
[ ] 硬禁令保持短，放进 AGENTS.md；长流程放 Skill

# 安全
[ ] 不装来路不明、含可疑 scripts/ 的包
[ ] 把 Skill 变更当代码审查
  • 你现在每个新对话是否仍在重讲设计系统？
  • AGENTS.md 是否已经太长，该把专项流程拆进 Skill？
  • 现有 Skill 的 description 是标题腔，还是带触发词的路由规则？
  • 左侧色条禁令写在「偶尔才加载」的 Skill 里，会不会被漏激活？（考虑 AGENTS.md 短句 + Skill 详版双写）
  • 安装过的第三方 Skill，上次 update 后有没有读 diff？

收束给 Zhu：Skills 的命题是上下文终于能像依赖一样安装——description 负责被找对，正文负责做对，scripts 负责偶发的硬自动化。AGENTS.md 管「绝不破例」；Skill 管「这类活怎么干」；画布 Specs（No.38）管「这一单功能的意图」。下一小时：把最常粘贴的那段口味说明 npx skills init zhu-ui-taste 写进去，并把左侧色条禁令同时落进 AGENTS.md 一句硬规则。Skills，not prompts。
