待解决的问题：如果编码智能体的产出能更早达到可上线水准，会怎样？

Radicle 是一款虚构的 STEM 学习应用，它的工程团队比以往任何时候都更快。过去需要数周的工作，现在只要几天，甚至几小时。然而，这样的速度并没有让他们走得多远：AI 生成的代码常常偏离设计规格说明。团队把截图和开发工单交给编码智能体，但这还不足以得到正确的结果，团队只能陷入反复返工。

如果 AI 的第一版产出更接近可上线水准，会怎样？只要有更多设计上下文可依据，比如在 Figma 中记录的已批准组件和 Token，编码智能体就能用更少的提示词达到你的意图。在这个示例工作流中，Radicle 的一位开发者借助 Figma 开发工具，为编码智能体提供更好的上下文，让它生成更好的代码。请跟随我们一起看看，这位开发者如何让新功能的设计与代码从第一版线框图到最终评审始终保持同步。

问题所在

Radicle 团队想要翻新收件箱，学生可以在这里给导师和其他同学发消息。首先，他们计划新增一个批量更新流程，包含三个界面：工具栏、模态框和轻提示（toast，一种临时通知）。用户可以通过工具栏全选消息、删除消息或将其标记为未读；模态框会请用户确认或取消操作；最后，轻提示会显示操作是否成功，并提供撤销选项。

团队的设计师在 Figma Design 中创建了每个界面，项目开发者则把这些设计交给编码智能体。代码很快就返回了，但 UI 并不对：图标不匹配，模态框的间距不均匀，轻提示还缺少失败状态。开发者本可以花一下午来返工，但他们选择退一步，借助 Figma 的开发工具重新开始。

先规划，再写提示词

在编写任何代码之前，开发者先梳理出各个屏幕、状态和过渡的预期行为，这些共同定义了新的批量更新流程。他们把这份大纲连同 PRD（产品需求文档）以及目前构成收件箱的组件代码一起交给智能体。随后，开发者借助 generate_diagram 工具和 Figma 的 MCP server，在 FigJamFigJam is now your coding agent’s whiteboard tooAgents are changing your code faster than your team can follow. Now you can close that gap with new MCP skills, architecture layouts, and more in FigJam. 中创建一张可编辑的图表，展示贯穿三个界面的流程：

  • 工具栏的“全选”选项会勾选所有邮件
  • “删除”选项会打开确认模态框
  • 轻提示（toast）中的“撤销”按钮会把仪表盘刷新回之前的状态

这张图表为智能体提供了可据以构建的额外上下文，也让团队在开发开始前有东西可以讨论。开发者把这份 FigJam 分享给对应的设计师和设计系统负责人，两人都直接在图表上留下反馈，而不是在 Slack 的讨论串里。

智能体根据 PRD 生成可编辑的 FigJam 流程图，设计师可以在实现开始前进行评审。

为智能体提供可用于构建的系统

Here’s what that unlocks for everyone who builds products. 把 FigJam 图表交给编码智能体，使其能够访问 Radicle 设计系统中的组件、Token 和布局。

如果开发者手里只有一张截图，就得在代码库里翻找合适的组件，或者去找设计师确认细节：那 12 px 的间隙是否用对了间距 Token，按钮是不是仓库里已有的次级按钮，模态框是新的模式还是团队已经上线过的。而现在，这些答案都在文件里，Figma 的 MCP server 会把智能体所需的全部设计上下文提供给它。

将设计系统连接到代码

知道该用哪个组件，并不等于知道它是如何构建的。这部分要靠 Code Connect，由 Radicle 的设计系统负责人来搭建。他们先在 Figma 中将组件库连接到团队的 GitHub 仓库，让每个组件都指向实现它的文件。然后，他们在代码库中为按钮、图标和模态框等组件编写模板文件，把 Figma 属性映射到代码属性。

现在，开发者提示智能体根据其在 Figma 中的选区进行构建，由 Code Connect 判断该导入哪个组件。智能体不必再耗费时间和额度去编写新代码，而是从已有的实现蓝图出发。

但批量更新的选中状态是全新的，因此这是 Code Connect 唯一无法映射的部分。在从零开始构建之前，开发者先用提示词调用 search_design_system，它会在团队的 Figma 组件库中查找现有的选择组件。智能体找到了团队几个月前上线的某个功能中的类似组件。随后，智能体在代码库中定位该组件，并针对批量更新流程加以调整。最终成果既符合品牌调性，又与 Radicle 应用的其余部分保持一致，智能体也无需重新发明团队已经构建过的模式。

开发者使用 search_design_system 查找现有的批量选择组件，这样智能体就不必从零开始构建。

防患于未然，提前发现偏差

开发者接着开始编写确认模态框。但就在开发期间，设计团队做了两处修改：模态框需要换成更深的品牌色，其按钮的圆角半径也有了新的数值。设计师在 Radicle 的组件库中发布了更新，并在工单里标注了这些变更。开发者没有手动修改，而是让智能体检查是否存在偏差（drift）。

他们在编码智能体中调用 get_variable_defs，它会返回模态框中使用的变量，这些变量已经反映了设计师的修改。智能体将它们与代码中的 Token 进行比对，立刻发现了两处不一致，并更新了模态框。

通往生产环境之路

开发者已经完成了工具栏、消息选中状态和确认模态框，这三者都来自团队维护的组件。剩下的是轻提示（toast）：它是在构建过程中创建的，目前只存在于代码中，还缺少失败状态。开发者通过提示词调用 use_figma，把轻提示（toast）以可编辑图层的形式放到画布上，设计师则补上带有“重试”操作的缺失状态。随后，设计系统负责人发布这个新组件，并通过 Code Connect 将其映射到代码。现在，这个轻提示（toast）与 Radicle 组件库中的其他组件用法一致。

之后的流程就和其他发布没什么两样。开发者发起拉取请求，diff 里大多是功能逻辑。工程师评审代码，设计师检查预览构建。

Figma 的 MCP 服务器和 Code Connect 让智能体能够访问所有人共同使用的同一套系统，因此团队可以把精力放在打磨影响用户体验的细节上，而不是反复修改 AI 生成的代码。更多的时间用于构建，意味着更好的成果，而不只是更快的速度。

安装 Figma MCP 服务器并将其连接到你常用的编码智能体，就能为智能体提供更好的上下文。为团队复用最多的组件设置 Code Connect。
