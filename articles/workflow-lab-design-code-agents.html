01 先给结论：三句话读懂这篇

第一，编码 Agent 再快，也只等于你给它的输入。只喂截图和工单，图标会错、间距会飘、失败态会缺——速度变成整下午返工。

第二，先计划再 prompt：把行为大纲 + PRD + 现有 inbox 代码交给 Agent，用 generate_diagram（经 Figma MCP）生成可编辑 FigJam，让设计师与 DS lead 在流程图上留言，而不是在 Slack 里对空。

第三，系统上下文三件套：MCP 暴露组件 / token / layout；Code Connect 把 Figma 属性映射到真实实现；漂移用 get_variable_defs 抓；缺的 UI 用 use_figma 拉回画布补全。更好的上下文 → 更少返工循环 → 时间留给真正影响体验的细节。

02 问题：截图 + 工单喂 Agent，为什么总会跑偏

Radicle 工程侧已经「周变天、天变小时」，但 AI 生成的代码常偏离设计规格。团队给编码 Agent 截图和开发工单——不够。典型翻车：图标不对、modal 间距不匀、toast 缺 failure state。开发者本可以下午改到吐；这篇选的路径是：停下来，用 Figma 开发工具重开一局。

What if your coding agent’s output could be production-ready sooner? — Workflow Lab 设问（大意：若编码 Agent 的输出能更早接近可上线呢？）

Zhu 若用 Cursor / Claude 之类写个人站：只贴一张 Figma 导出 PNG，几乎必然「看起来像、细节全错」。本篇的解药不是更长 prompt，而是 结构化上下文管道（流程图 + MCP + Code Connect）。

03 场景：收件箱批量更新（toolbar → modal → toast）

学生收件箱要加 bulk-update flow，三块表面：

表面行为容易被 AI 搞砸的点
Toolbar全选 / 删除 / 标为未读图标集不一致、选中态自创
Confirm modal确认或取消间距 token 错、按钮变体用错
Toast成功提示 + Undo；还应有失败态只做成功、缺 failure + retry

设计师在 Figma Design 出屏 → 开发者扔给编码 Agent → 快，但 UI 偏。下面从「计划」重新开始。

04 先计划再 prompt：PRD + 现有代码 → FigJam 流程图

写代码前，开发者先列清屏、状态、转场行为，把大纲 + PRD + 当前 inbox 相关代码一起交给 Agent。经 Figma MCP 调用 generate_diagram，得到可编辑 FigJam：

  • Toolbar「全选」勾上每条消息
  • 「删除」打开确认 modal
  • Toast「Undo」把仪表盘恢复到前一状态

流程图既是 Agent 后续的上下文，也是给人看的：设计师与设计系统负责人直接在 FigJam 上留反馈，而不是另开 Slack 长线程。

可迁移习惯：任何「截图开写」之前，先强迫自己有一张三节点流程图（入口 → 确认 → 反馈）。个人站改定价页同理：价卡 → 结账 modal → 成功 / 失败 toast，先 FigJam 再生成。

05 用 MCP 给 Agent「系统」而不是「截图」

签过字之后，开发者把 FigJam 经 Figma MCP server 喂给编码 Agent——Agent 因而拿到 Radicle 设计系统里的组件、token、layout。

若只有截图：人要自己翻代码找对组件、问设计师「12px 是不是 spacing token」「这是 secondary 按钮还是新花样」「modal 是新模式还是已上线模式」。这些问题在文件里已有答案；MCP 让 Agent 直接读到。

# 给编码 Agent 的上下文优先级（建议）
1. FigJam 行为图（状态与转场）
2. 已发布 Figma library（组件 / 变量 / layout）
3. 相关现有代码（inbox 已实现部分）
4. 截图 —— 仅作补充，不作唯一真相

06 Code Connect：库与 GitHub 的属性映射

「知道用哪个组件」≠「知道它怎么实现」。后者来自 Code Connect：DS lead 把 Figma 库接到团队 GitHub，让每个组件指向实现文件；再为 button / icon / modal 等写 template，映射 Figma properties → code properties。

开发者提示「从当前 Figma 选区构建」时，Code Connect 告诉 Agent 该 import 哪个真实组件——省掉烧额度从零手写，从已有 blueprint 起步。

07 新状态：search_design_system 改编而非发明

批量选择态是新的，Code Connect 映射不到。别急着发明：先 search_design_system，在库里找类似过去功能的 selection 组件；Agent 找到几个月前上线的近亲，再在代码库里定位并改编。结果 on-brand、与 Radicle 其余部分一致，且没有再造一套模式。

策略何时用风险
Code Connect 直映库里已有、GitHub 已挂映射过期要维护
search_design_system 改编新交互但有近亲改编时漏掉 a11y / 状态
从零发明真·新品类最易 off-brand；最后才用

08 漂移检查：get_variable_defs 对齐 token

开发者在写确认 modal 时，设计侧改了两处：modal 要更深品牌色、按钮新圆角。设计师发布库并开票。开发者不手改，而是让 Agent 查漂移：get_variable_defs 返回 modal 现用变量（已含设计更新）；Agent 对比代码 token，立刻抓到两处不匹配并修正。

漂移检查应变成 PR 习惯：改品牌色 / radius / spacing 后，对相关屏跑一次变量对比，而不是靠视觉 QA 碰运气。个人站 token 文件与 Figma variables 也应有同一条「对账」命令。

09 只在代码里的 toast：use_figma 拉回画布

Toolbar、选中态、modal 都来自团队维护的组件；toast 却是构建中才出现、目前只存在于代码，还缺 failure 态。开发者用 use_figma 把 toast 放到画布成可编辑层；设计师补 failure + retry；DS lead 发布组件并用 Code Connect 映射回代码。之后 toast 与库里其他东西一样工作。

收尾像普通发布：开 PR，diff 大多是功能逻辑；工程师审代码，设计师看预览构建。

# 个人站 / 小 B 端最小 lockstep（周末可起）
[ ] 安装 Figma MCP，接到你的编码 Agent
[ ] 主按钮 / 输入框 / Modal 做 Code Connect（哪怕 3 个）
[ ] 新功能先写 5 行行为大纲 → generate_diagram
[ ] 生成前：MCP 附库；禁止「只贴截图开写」
[ ] 新交互先 search_design_system
[ ] 合并前：get_variable_defs 对账色与圆角
[ ] 代码先长出来的 UI：use_figma 回画布，补齐空/错态

11 自查清单

  • 编码 Agent 的第一输入是流程图 + 库，还是一张 PNG？
  • FigJam 是否在写码前给设计师 / DS lead 看过？
  • 高频组件有没有 Code Connect，而不是每次靠 Agent「猜」import 路径？
  • 新状态是搜索近亲改编，还是默认从零发明？
  • 品牌色 / radius 变更后有没有跑变量漂移检查？
  • 仅存在于代码的 UI 有没有拉回画布补 failure / empty / loading？
  • 返工时间是在减「对不齐设计」，好把精力用到 UX 细节上吗？

收束给 Zhu：Workflow Lab 的命题很朴素——更好的上下文，更少的返工循环。截图喂 Agent 会跑偏；FigJam 行为图 + MCP 系统上下文 + Code Connect 映射，让第一版更接近可上线。个人站同样适用：先接通 3 个组件的 Code Connect 与一条漂移检查，再谈「AI 写页面有多快」。快，应该来自 lockstep，而不是来自忽略设计系统。
