01 先给结论：三句话读懂这篇

第一，「知道该交什么」本身是设计技能。不是「会不会用 Agent」，而是不断问：这步需要我的判断（judgment），还是只需要做完（doing）？

第二，维护也是设计工作。替换过期组件、修好变量绑定，不如画新屏炫目，却决定设计系统（design system）是「一套系统」还是「几个同名碎片」。Agent 适合做聚焦检查与重复修复；例外仍由你解释。

第三，Agent 最有用的形态是保护注意力。它承接上下文、处理重复步骤、准备下一步，让你少花时间管理「通往上线的路径」，多花时间决定「什么值得上线」。

留给设计师交给 Agent刻意避免
功能主路径、产品取舍、政策怎么改体验库对齐、评论归类、合规标注、增强规格草稿让 Agent「顺便」定权限规则或法务结论
模糊匹配怎么办、要不要增强系统组件清晰可替换的 deprecated 实例与变量一上来全文件大扫除，再回头做功能
验收「改哪些、不改哪些」先列出 findings，再按你的指令 apply静默改完才告诉你「都修好了」

02 核心问题：什么需要判断，什么只需要做完

原文开篇几乎就是全文口号：用 AI 做设计，就是不断问——What needs my judgment, and what just needs doing? 听起来平淡，一到 deadline 就容易崩：你既想每个产品和设计决定仍是自己的，又不想在过期组件、散乱评论、合规文档之间来回跳。

场景是虚构 App Offtrail（本地户外聚会）。现有权限体验没法让人「只主持一场活动」；团队要加临时主持人权限：到期显示、管理员可管、过期与失败可恢复。功能建在旧权限屏上——而那些屏已经混了当前组件与手改过期变量。

对 Zhu 这种自己用 AI 搭站、又要躲开「AI 脸」的人：你真正稀缺的不是「再画一屏」，而是注意力带宽。杂活（busywork）会把判断力挤出心流（flow）。这篇给的不是又一个「生成界面」demo，而是一张分工图。

03 先修库，再做功能：/repair-library-usage

设计师先选预计复用的 frame，连上当前库，跑 /repair-library-usage。Agent 对照库检查实例与变量绑定：有明确新等价物的，直接替换；两边都能凑合、看不清意图的，留下不动，并在旁边标注发现了什么、为什么停手。

目标写得很清楚：只更新新工作会建其上的那一段体验，不是清扫整个文件。设计师只处理影响本项目的例外，然后进入临时访问流的第一稿——不必在「修文件」和「做功能」之间来回弹。

Agent 做设计师做为什么
匹配清晰的 deprecated → 当前组件/变量读模糊案例的 annotation清晰替换是执行；模糊是语义判断
只扫你选中的复用范围决定范围边界全文件大扫除会制造新上下文税
把「为什么停」写在画布上决定例外是保留还是改例外往往编码了真实产品历史
“Maintenance is design work.” — Brett McMillin / Figma（大意：维护也是设计工作）

原文提醒：这些小决定重复做下去，决定系统是连贯还是名存实亡。Agent 做检查与重复劳动；你仍解释例外意味着什么。

04 功能本身：判断必须留在主路径

源文件修好后，设计师自己设计临时访问流：主路径，加上到期、失败、恢复状态。这里没有「让 Agent 先出十个权限方案」——因为权限、身份、过期边界，正是产品与政策判断的高密度区。

原文另有 Zoom out：文案、品牌语气、多语言也是流程的一部分；Agent 可以拉品牌语气、试替代文案、看其他语言下的屏。那是表达层的加速，不是把「该不该临时授权」交给模型。

读本里 Linear「主判断留在自己手里」、Vercel product-design Skill「代码不告诉为什么」是同一立场的不同工具面。这篇更贴 Figma 画布：判断画在主路径上，杂活从侧枝被 Agent 接走。

05 评审之后：把评论堆成高信号简报

Crit 之后，评论会混成两类：一类是清楚动作（改到期文案、收紧层级、让恢复路径更好找）；一类是政策问题（邀请过期未接受怎么办？权限更新失败时谁看到什么？会话中途到期成员看见什么？）。

设计师让 Agent 整理线程：归并重复反馈、标出矛盾、突出未决问题，压成一份短的高信号简报（high-signal brief）——什么立刻可改，什么仍需想。

评论里常见噪声Agent 整理后你仍要亲自做的
同一建议说了三遍合成一条可执行项排优先级
「这合法吗？」散落各处标成开放政策问题找合规伙伴或跑合规 Skill
互相打架的视觉建议显式列出矛盾选边或重开讨论

06 合规 Skill：对照规则，不替你猜政策

有些法务问题设计组答不上来。设计师不猜，而是跑团队的 /compliance-review：Skill 里挂着安全/合规伙伴维护的检查项，Agent 带着那些人期望设计师自问的问题来看访问、身份、权限相关流，并把发现标注到对应 frame。

关键边界：Agent 搜集外部指引并给出 guided feedback；设计师决定这些发现会怎样改变功能。它不扮演律师，也不替你拍板政策。

个人站很少有正式合规文档，但仍可自建「对照表」：隐私文案、权限披露、第三方登录边界。Skill 的价值是「带着固定问题清单看稿」，不是「模型懂法」。

07 组件增强写在同一文件里

合规发现：列表用的系统组件 item row 还不支持展示「临时访问何时到期」。做一次性自定义组件，既扩 scope，又让体验脱离设计系统。更耐用的路是增强系统组件本身。

此时功能已近完成。另开一套设计系统交接容易拖项目、逼设计师切上下文。于是用 /document-component-enhancement，在同一 Figma 文件新分区起草规格：需要什么行为、现状差在哪、缺哪些状态、可能改动与开放问题。

设计师审草稿、确认开放问题，把该分区交给设计系统团队。规格与出问题的 frame、评论、组件同文件——评审能追溯动机；所有权也清楚：功能怎么发展归功能设计师，组件怎么改归系统团队；Agent 说明需要什么改、为什么，让系统团队能审，功能侧继续往前。

08 一次需求，四份产出

原文收束得很利落：一个产品请求，落到四件具体产出——

  1. 现有屏上的设计系统缺口被识别（并部分修复）
  2. 临时访问流覆盖主路径 + 到期 / 失败 / 恢复
  3. 对照合规指引的标注 + 合成后的反馈简报
  4. item row 增强规格（行为、缺口、推理链回链到现场）

共享、可视、多人画布把这些产出留在同一工件上：流、评论、标注不散到别的工具。Agent 的价值不是「又画了一屏」，而是检查、修复、蒸馏反馈；设计师做的是定义功能的设计、产品与政策决定。

产出主要执行者若不做会怎样
库缺口识别与局部修复Agent + 设计师裁定例外新功能建在不可信基座上
完整临时访问流设计师只有 happy path
合规标注 + 反馈简报Agent 整理，设计师决策政策问题淹没在评论噪声里
组件增强规格（同文件）Agent 起草，系统团队拥有一次性野组件，或交接丢上下文

09 预览再应用：保护注意力的操作习惯

原文 Zoom out 给了一个可立刻养成的模式：先让 Agent 只列 findings、不改文件——「对照已连接库审查选中 frame，列出过期组件与变量，提议当前等价物，标出模糊匹配。不要做任何修改。」读完画布上的标注后，再让它只应用匹配清晰的项，模糊案保留。

这就是 preview-before-apply。它把「静默大改」变成「你批准的补丁」，也让你在心流里只处理真正需要判断的差分。

10 什么时候不要交给 Agent

  • 政策与法务结论。可以跑合规对照，不能让模型「觉得大概合规」。
  • 产品取舍。临时权限到期后谁还能看什么——这是产品决定。
  • 模糊的库匹配。两个新组件都能凑合时，留下标注比瞎替更好。
  • 系统组件的最终形态。增强规格可草稿；拥有权仍在设计系统团队。
  • 全文件「顺便清理」。 范围一扩，杂活会反噬注意力。
  • 你还说不清成功标准时。先写清 brief，再开 Agent；否则它只会加速混乱。

11 可直接改写的 Skill / 提示模板

下面三段可改成你自己的斜杠命令或聊天模板。名称可自定；结构对齐原文三 Skills。

# /repair-library-usage（预览模式）
对照当前已连接的设计库，审查【选中的 frame】：
1. 列出过期组件实例与错误/过期变量绑定
2. 对每一项给出「当前等价物」建议
3. 标出模糊匹配（两个都能用 / 意图不清）并说明为何不确定
4. 本轮不要修改文件，只在画布旁标注 findings
等我确认后，再只应用「清晰匹配」项；模糊案保持原样。
范围：只处理本功能会复用的屏，不做全文件清理。

# 评审后简报
阅读本文件中关于【功能名】的评论线程：
- 归并重复反馈为可执行项
- 显式列出互相矛盾的建议
- 把政策/法务/权限类问题单独成「开放问题」清单
输出一份短简报：立刻可改 / 需讨论 / 需合规对照。不要改设计。

# /document-component-enhancement
基于【合规/评审发现】与周围设计上下文，在本文件新分区起草组件增强规格：
- 需要的行为（含状态）
- 当前组件缺口
- 缺失状态列表
- 开放问题（留给设计系统团队）
- 回溯链接：指向触发该需求的 frame / 评论
不要发明新的一次性组件；默认路径是增强系统组件。
我审完开放问题后再分享给系统团队。

12 自查清单

  • 开 Agent 前，我有没有先问「这步要判断还是要做完」？
  • 修库时有没有限定在「本功能会建其上」的 frame，而不是全文件大扫除？
  • 模糊匹配是留下标注，还是被静默改掉了？
  • 功能主路径、到期/失败/恢复，是不是仍由我设计？
  • Crit 后有没有把评论压成高信号简报，而不是在线程里游泳？
  • 合规结果是「改变功能的输入」，还是被当成最终判决？
  • 系统缺口是增强组件 + 同文件规格，还是又做了一个野组件？
  • 有没有先 preview findings，再 apply？
  • 四个产出里，我缺了哪一块：库缺口 / 完整流 / 合规与简报 / 增强规格？

这篇和读本里「Got skills」「Agents meet canvas」「Teaching agents product design」是同一条生产线的不同工位：那些篇教你怎么写 Skill、怎么接画布；这篇教你怎么在真实功能压力下分工。若你已经会让 Agent 画屏，下一步不是画得更多，而是让它把你捞出杂活，好把判断留在主路径上。
