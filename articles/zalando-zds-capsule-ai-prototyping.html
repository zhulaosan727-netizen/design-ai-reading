How Zalando built its own AI prototyping environment on top of its design system

01 三句话结论

第一，品牌感出不来，往往不是提示词不够好，而是设计系统还不能被机器读对。Zalando 设计系统团队试过改进提示、清理图层，Figma Make 仍然做不出符合品牌的原型。他们的幻灯片写得很干脆：Figma Make 没做到。于是团队在自己的设计系统上，用 Claude Code 搭了一套名为 ZDS Capsule 的原型环境：可以从一张 Figma 设计、一段自由提示，或两者的混合，做出带真实商品数据、能切换主题、能导出 HTML 的可运行原型。

第二，套具能转起来之前，要先改地基。Gonzalo 列出五件事：令牌（token）以中立格式放在 Figma 之外的仓库里；用 Figma Code Connect 让智能体选中仓库里的真实组件；把原来给人口粮的视觉规范，改写成人和机器都能用的文档；把规范拆成许多份小的 design.md，并配一份索引；以及人的启用（enablement）——只写文档，没有人会用。技能（skill）本身是概率性的（probabilistic）：同样的说明，每次可能走出不同的决定。他们的修法是，在必须只有一个正确答案的步骤上，让技能去执行脚本，而不是用一段话描述任务。

第三，探索变容易，并不自动等于协作变容易。最大的启用失败发生在工作坊开始之前：访问申请、VPN、终端、Git，把许多人挡在了原型之外。而在一个已经获得认可的儿童购物概念上，他们请模型代写交给工程的动效规格（motion specs），工程师的反馈却是：为什么不继续用 Figma？我真正要看的那一小部分，反而被模型可能的多种写法遮住了。原型快了，实现却可能更慢，功能到达用户的时间也被推迟。机器就绪，是设计系统对智能体可读；协作就绪，还要看工程师拿着这份产出，能不能一起做决定。

02 通用生成器做不出品牌，他们决定自建

Dana 和 Gonzalo 所在的 ZDS 团队，还有一位负责人、另外两名设计师和一名产品经理，周围密切合作的工程师超过十位。他们要支持 Zalando 内部两百多名设计师、五百多名工程师。这些年，团队已经从「维护 UI 库」走到「自己拥有一套不必每次求工程帮忙的工具」：Figma 插件可以把真实商品数据灌进组件，也可以同步令牌、生成组件规格和文档；一个迁移技能能把设计师从已废弃的组件迁到最新版本；还有一个 Chrome 扩展，可以在 zalando.de 上现场改令牌，让设计决策发生在生产界面里。

缺的是可靠的原型。他们在幻灯片上写下一句不加修饰的结论。

Figma Make didn't make it. — Zalando 设计系统团队幻灯片

不是没试过。提示词改过，图层也清理过，结果仍然不像 Zalando。于是他们决定不把希望放在通用生成器再「聪明一点」上，而是在自己的设计系统之上另做一套环境，名字就叫 ZDS Capsule。

编者点评：把「不像品牌」首先当成提示词问题，会把人锁在同一间屋子里打转。通用生成器看到的如果只是视觉样张和一层商品橙色，它最容易学到的规则就是：强调等于品牌色、标题可以全大写、语气可以自行发挥。后面工作坊里出现的偏差，几乎都是这种误读的复述。先问「机器此刻到底读到了什么」，比再写一句「请更有品牌感」更接近根因。

03 五块地基：先让设计系统机器就绪

Capsule 能工作之前，Gonzalo 说他们必须先改地基。五块可以挨着看：

  1. 中立格式的设计令牌，单独放在仓库里。令牌不关在 Figma 里。智能体可以直接读、对着它排查，需要时再拉取更新。
  2. Figma Code Connect。智能体根据画布上的设计，去仓库里挑对应的代码组件。这样写出来的是真组件，而不是一套新的近似物，令牌成本也会下降。
  3. 同时写给人、也写给机器的文档。原来的指南充满视觉示例，对人有效，对智能体不够。
  4. 把指南改写成一份份 design.md。不是把原文档导出成一个大文件，而是拆开，让机器按需取用。
  5. 人的启用。文档齐了，不等于有人会用。这一条后来被证明比他们预想的更硬。

前四块解决的是「机器读到的是不是真源」；第五块解决的是「人怎样进得去这套环境」。少任何一块，后面的演示都站不住：没有仓里的令牌，智能体只能猜色；没有 Code Connect，它会重画一个按钮；没有可检索的小文件，上下文窗口会被一份大文档塞满；没有启用，工作坊会停在登录页。

把这件事放到一个更日常的尺度里。假如你在为自己的站点做一篇新的阅读页，令牌和「禁止在卡片左侧加竖向色条」这类硬规则只活在 Figma 文件或口头交代里，模型仍然可能按常见后台模板加一条左边框。把令牌放到仓库，再写一份短的 usage 说明——「强调用标签、图标或表面色温，不要用左侧色条」——机器才有机会第一次就读对。Capsule 的地基，就是把这类「看起来像常识、对机器却不是默认值」的事，从画布里搬到它能稳定拿到的地方。

编者点评：五块地基里，最容易被当成「写给机器的附加文档」的是第四块，最容易被排到会后的是第五块。Zalando 后来的经验正好把这个顺序反过来：规范可以迭代，访问和工具链如果没在工作坊前打通，规范写得再好也没有读者。机器就绪和人就绪，是同一件工作的两面，不是先做完套具再培训。

04 design.md：拆成小文件，真值不要重复

写给智能体的指南，他们没有做成一份通篇 markdown。原因很具体：上下文窗口（context window）有限。智能体先读索引，再只拉自己需要的那一份。文件里只保留指引和用法；已经在代码里定义过的值，不再抄一遍，以免两处日后各改各的。

这和「把设计系统全文喂给模型」不是同一条路。全文喂进去，看起来很完整，实际上会把令牌、组件 API、用法和建议混在同一段上下文里，既贵，又容易在更新后出现两份互相打架的真值。拆开之后，一份文件回答一个问题：品牌橙什么时候用、什么时候不能拿来做所有强调；正文要不要设置成全大写；语气是什么；某个组件在什么情况下才该出现。代码里的色值和间距，继续以代码为准。

一个可以动手的拆法是：

  • index.md：目录，告诉智能体遇到哪类问题该打开哪份文件
  • color-usage.md：品牌色的用法与禁区，不罗列色值本身
  • typography.md：层级、大小写、什么时候才用展示性处理
  • tone-of-voice.md：语气、称呼、不能出现的腔调
  • components/<name>.md：用法、组合、不要重做一遍 props 表

读本在 No.46 里写过同一条原则：意图放进文件，真值指向源头。Zalando 把这条原则用在了「索引 + 许多小文件」的物理结构上，并拿工作坊的输出当检验：文件若含糊，偏差会立刻长在界面上。

05 工作坊里露出的三种偏差

地基还没完全长成 Capsule 之前，团队先办了大约五场混合工作坊：设计师只带着 markdown 指南，用 Claude Code 做快速原型。结果让他们吃惊，也把问题照得很清楚。

  • 品牌色：智能体把 Zalando 橙用到各处，当作所有需要强调的地方的默认解。
  • 字体：文本有时会变成全大写。
  • 语气：跑偏了，因为当时还没有语气指南。

这三类偏差值得当成诊断，而不是当成「模型不行」的证据。橘色铺满，说明它把「品牌色」理解成了「强调色」；全大写，说明某一处展示性样式被过度推广；语气不对，则是文件里根本没有这项约束，模型只能自行发明。团队随后多次改指南、加护栏（guardrail），输出才稳定下来。幻灯片上有一个例子：只凭一句提示，加上这些指南，做出了一个 Twitter 风格的克隆。

注意这里的顺序。他们不是先做完 Capsule 再写规范，而是用工作坊里长出来的错误，反过来改文件。规范的第一读者，是会把误读立刻画到界面上的智能体。

编者点评：把这三种偏差写成回归用例（regression case）很有用。下次改指南或升级模型，就专门跑一遍：强调是不是又变成了品牌色，正文是不是又被设成全大写，语气是不是又滑回一套通用客服腔。指南「写完了」不够，要能反复触发这些曾经失败过的地方。否则迭代只发生在记忆里，不会发生在文件里。

06 Capsule 怎样从画布或提示词做出能跑的原型

Gonzalo 在 VS Code 里用 Claude Code 做了现场演示。Capsule 可以从 Figma 设计出发，也可以从自由提示出发，或把两者混在一起。他运行的技能名叫 build-prototype，任务是一个移动端的「Trend spotter」：传入 Figma 链接，并要求一排选择器组件，在欧洲城市之间切换潮流内容。

技能会并行拉起智能体。一个经由 Figma 的模型上下文协议（MCP）去取设计上下文；另一个把 Figma 设计提取成 JSON，供下一步搭建原型。通常还有第三个智能体，演示时为了省时间关掉了。做完的原型复原了那张 Figma 设计，并加上了巴黎、柏林、伦敦、米兰等城市筛选。

套具本身还提供几件让原型「像真产品」的能力：

  • 真实商品数据：粘贴 zalando.de 的商品链接，原型会带入图片、名称、价格和品牌；粘贴目录链接，轮播里会填上商品，包括折扣。
  • 模板：对生产页的镜像，例如带尺码选择和结账的商品详情页（product detail page）。
  • 主题：在基础主题和深色模式之间切换。
  • 测试：减弱动效（reduce motion），在真实设备上测试，或模拟其他设备。
  • 导出：把原型下载为 HTML。

后面那个儿童购物的例子，把这些能力的意义说得很清楚。用户把商品加入心愿单时，屏幕上会爆出一阵贴纸：十一款设计，每次落下的数量是随机的，位置、缩放和旋转也会变，还要处理滚动时如何触发和收起。Figma 原型表现不了这种随机，也表现不了滚动里的时序。团队拿 Capsule 和商品详情页模板，用几句提示就做出了可看的效果，包括减弱动效和深色模式版本，概念因此获批。工具在这里补上的，不是「更好看的静态稿」，而是静态稿无法演示的行为。

07 关键步骤不要交给概率：让 Skill 去跑脚本

技能每次运行都会给出不同结果，因为智能体会阅读说明，再自己做决定。Gonzalo 的修法不是把说明写得更长，而是在对的时刻让技能去执行一段脚本，使结果更确定。

他们的脚本负责：整理 Figma 设计的结构、扫描 Figma 图标、生成原型的元数据和缩略图。图标是一个干净的例子。若只给智能体看 Figma 截图，它只能猜测那是什么图标，再重画成 SVG——形体会漂，名字会对不上组件库。一段返回「这是什么图标、在哪里被使用」的脚本，给的是真实答案，而不是又一次绘画。

这里有一条可以带走的分工。技能适合做需要判断的事：这一屏像不像原设计、筛选器该怎么排、文案语气对不对。脚本适合做只有一个正确答案的事：图标叫什么、令牌叫什么、这个画布节点对应仓库里哪一个组件、元数据如何生成。把后一类步骤写成「请识别这些图标」，就是把确定性任务重新交给了概率。

编者点评：判断一条技能稳不稳定，不要只看「大多数时候还行」。要列出那些不允许发挥的步骤：命名、映射、校验、导出。这些步骤一旦让模型自由发挥，后面所有看起来很聪明的生成，都会建在一次猜测上。Zalando 把图标从「重画」改成「查询」，是在保护后面整条链路，而不只是在提高图标的相似度。

08 启用失败发生在工作坊开始之前

Dana 接手讲启用时，问题已经不在原型质量上了。许多工作坊参与者根本没走到做原型那一步。他们卡在 Zalando 内部的访问申请和 VPN 上，在公司 IT 结构里打转。真正花掉的时间，往往和原型无关：终端命令、显示隐藏文件夹之类的 Finder 快捷键、VS Code 教程、Git 的逻辑、PR 怎么走、Claude Code 的技能怎么用。

他们的修法是给小团体开设支持时段（support slots）。每个人按自己的节奏先把环境配好，再进入正式的原型环节。文档也改了：技术部分配上截图，让人看见一份 design.md 或一项技能长什么样；命令用等宽字体；并且做成协作文档，谁发现漏了一步都可以补上。

到演讲时，已经有二十多名设计师在向 Capsule 提交 PR，团队合并了 98 个。内容从新的原型和模板，到设计元素，再到工具自身的界面改进。启用一旦跨过「进得去」这道门，套具就开始被它的使用者改写，而不是只停留在设计系统团队内部。

这也解释了第五块地基为什么不能省略。一套只能由搭建者本人运行的 Claude Code 工作流，还不是给两百名设计师用的环境。VPN 和 Git 看起来不像设计问题，却决定了工作坊是在做原型，还是在做入职。

编者点评：以后若要办「用 AI 做原型」的内部工作坊，最好把「环境配好」和「做出原型」分成两次，并分开计量。前者清点的是：账号、VPN、仓库权限、终端、编辑器、Git、技能是否装好；后者才清点输出质量。把两件事放在同一下午，失败会被记成「大家还不会用 AI」，其实失败发生在登录之前。

09 探索容易了，工程师却问「为什么不继续用 Figma」

心愿单贴纸的概念通过之后，团队请 Claude 为工程撰写动效规格。一位工程师的反馈被原文完整记下，值得慢慢读：

Why are we using this approach for prototypes? Why not Figma?
The parts I'm interested in as a developer are tiny, but even them are obfuscated because there are so many different ways Claude might create them. — Zalando 工程师对 AI 动效规格的反馈

Dana 把这当成一次有用的当面核对。原型更快了，实现却可能要多花两到三倍时间，功能到达用户的时间反而被推迟。人工智能让探索变得容易，并不自动让协作变得容易。更严的一点是：一份不留含糊的规格，也往往不给设计师和工程师一起讨论意图、共同做决定留下位置。

工程师要看的通常只是很小一块：触发条件、滚动时如何收起、随机数量的范围、减弱动效时退到哪一种表现。模型若用一种完整但任意的方式把整段动效都写死，工程师反而找不到那块「真正要一起决定」的地方——不是信息太少，是信息太多，且来路像是一次偶然的生成。Figma 稿在这里的优点，未必是保真度更高，而是大家还知道该指着哪一层说话。

所以「机器就绪」只走完了前半段。设计系统能被智能体读对，探索会变快；若产出不能被工程师定位、讨论和改写，后半段会在交接处重新变慢。Bormüller 后来给自己写下的一条，也是为此：在为工程生成规格之前，先问他们到底需要原型提供什么。

编者点评：面对这类反馈，最差的反应是把规格写得更长，把每一种可能性都补上。那只会加深「被遮住」的感觉。更好的问法是：你真正要看的那一小部分是哪几条？触发、边界、可访问性退路、随机是否允许？把这几条写成双方都能改的约定，比再导出一份完整动效说明更接近协作。探索用套具，交接用双方认得出的结构，不必是同一份文件。

10 能做，不等于该做

Capsule 越来越能做之后，找上门的想法也变多了：可用性测试、重建站点地图、把整个设计过程自动化、让产品经理来做原型、直接交给工程、从一开始就做到像素级精确。团队用 Jina Anne 的一段话，作为决定下一步做什么的罗盘：

Remember our purpose. We create design systems to grow our products. But those products serve people. Design Systems are for people. — Jina Anne

设计系统是为了让产品长起来，而产品是为人服务的。工具能做的事，不等于此时该做的事。团队接下来是把 Capsule 做成 Zalando 内部的正式应用，并支持更多可用性测试场景——仍沿着「让人把产品体验看清楚」走，而不是沿着「还能自动什么」走。

他们送给现场的三句，可以和前面的故事叠在一起读：自己做工具，是为了能实验，并越过现成工具的限制；目标要定得高，但方式必须能促进对话和协作；始终把用户的体验放在中心。第一句解释了他们为什么离开 Figma Make；第二句解释了工程师那次反馈为什么被当成礼物而不是攻击；第三句则拦住了「既然能生成，就应该把流程全包下来」的诱惑。

问答里还有几件实施上的具体事。第一版 build-prototype 太慢，没人愿意为一份初稿等三十分钟，工作坊参与者会问：结果如果不好，为什么还要安装这一堆东西。Figma 提取出的 JSON 一度大到还没开始搭原型，就把上下文塞满了，后来改成先写一份短的摘要 JSON，完整文件只在真正需要细节时再打开。智能体从一名加到三名并行，省下大量等待。Gonzalo 会把不是自己做的 Figma 设计丢进工具里，看它在何处失败，再用这套工具本身去查原因。Capsule 还有一文件夹的 markdown，解释每一项功能——功能持续往上加时，不写下就会忘。至于向工程交接，他们还没有答案：Capsule 一开始就是原型工具，从未被设计成生产路径；如果它真的变成交接方式，就必须为工程师再改一版。下一步甚至在设想一套更中立的工具，让人不必安装 Claude Code、也不必提交 PR，就能直接做原型，并可能服务 Zalando 内部其他设计系统。

Bormüller 在文末写了四条她自己带走的东西，她特别标明：这不是 Dana 和 Gonzalo 的原话。把指南拆成带索引的小 markdown；技能不稳定时，把关键步骤搬进它要运行的脚本；AI 工作坊之前先安排环境支持时段；为工程生成规格之前，先问他们需要什么。四条都不神秘，却正好对应这篇记录里真正花过代价的地方。

11 对照表：调提示词、自建套具、把关键步骤写成脚本

继续调通用生成器的提示词自建套具（Capsule 这一路）在套具里把关键步骤写成脚本
默认假设结果不像品牌，是因为话说得不够细通用工具读不到真源，所以做不出品牌技能会自己做决定；必须唯一的答案不该再交给它发挥
主要动作改提示、清理图层、再生成一次令牌入库、Code Connect、小文件指南、模板和真数据在图标识别、结构提取、元数据这类步骤调用脚本
结果是否稳定每次看起来完整，品牌规则仍可能被发明组件和数据对了，探索变快同一输入更能得到同一映射，后续生成才有可靠地基
对人的要求每个人都会写更长的提示先过访问、Git、编辑器和技能，工作坊前要有支持时段设计系统团队要维护脚本，并写清技能在何时改去调脚本
和工程交接仍然是一张看起来完整的稿或一段任意规格可运行原型能演示随机和滚动，但规格不一定更好用先问工程师要看哪几条，再决定生成什么；不要用「写死一切」代替讨论
适合何时用个人试方向、还没有可共享的真源已经有设计系统，需要可重复、可给更多人用的原型环境套具已经跑起来，但同一任务每次结果都在关键细节上漂移

12 可粘贴：机器就绪检查单，和一段 Skill 约定

下面不是 Capsule 的配置原文，而是按这篇记录整理出的、可以贴进团队仓库的两份短材料。第一份用来检查地基，第二份用来约定：技能在何处必须改去执行脚本。

# 设计系统是否机器就绪（检查单）

## 真源
- [ ] 令牌以中立格式放在独立仓库，智能体可读、可对照排查、可拉取更新
- [ ] 画布组件通过 Code Connect（或同等映射）指向仓库里的真实代码组件
- [ ] 指南写成带索引的小 markdown，而不是一份塞满上下文的大文件
- [ ] 文件只保留用法与意图；色值、间距、API 以代码为准，不在文档里再抄一份

## 护栏（用曾经失败过的例子来写）
- [ ] 品牌色不是默认强调色；写明何时可用、何时禁止铺满
- [ ] 展示性的大小写不会被推广到正文
- [ ] 有语气指南，而不是让模型自行发明一种「友好腔」
- [ ] 每条护栏都能作为回归用例再跑一遍

## 套具能力（若你在自建原型环境）
- [ ] 可以用真数据，而不是空的占位图和「Lorem」价格
- [ ] 有生产页的模板（详情、列表、结账等），而不是每次从空白生成
- [ ] 能切换主题，能检查减弱动效，能在真实或模拟设备上看
- [ ] 初稿等待时间短到人愿意留在工作坊里（不要以三十分钟为默认）

## 启用
- [ ] 访问、VPN、仓库权限、终端、编辑器、Git、技能安装，都在正式做原型之前完成
- [ ] 文档有截图，命令用等宽字体，缺步骤时任何人都能补
- [ ] 为工程生成规格之前，先问：你们真正要看的是哪几条

# skill 约定：何时描述任务，何时执行脚本

你是设计系统上的原型技能。判断类步骤可以按指南推理；
下面这些步骤必须调用指定脚本，不要靠截图或描述去「识别」。

必须走脚本：
- 从图画节点得到图标名称及其使用位置
- 把 Figma 结构整理成下一步要用的数据（先写摘要，完整文件仅在需要时打开）
- 把画布组件映射到仓库中的真实组件
- 生成原型元数据和缩略图

不要做：
- 把图标重画成未经库确认的 SVG
- 把品牌色当作所有强调的默认解
- 在没有被询问之前，为工程写一份不留讨论余地的完整实现规格

开始搭建前，先读索引，只打开与本次任务相关的 design.md。

13 自查清单

  • 我还在用「再写细一点的提示」拯救不像品牌的结果，还是已经检查过令牌、组件映射和指南是否真的能被机器读到？
  • 指南是一份会撑满上下文的大文件，还是带索引的小文件？代码里已有的值，有没有在文档里再抄一遍？
  • 最近一次品牌偏差，我有没有把它写成护栏和回归用例，还是只在口头上说「下次注意」？
  • 技能里有哪些步骤其实只有一个正确答案（图标名、令牌名、组件映射）？它们现在是脚本，还是一段「请识别」的说明？
  • 若把不是自己做的文件丢进这套流程，它会在何处失败？我能不能用工具自己查出原因？
  • 内部工作坊里，人们是卡在 VPN、Git 和编辑器，还是已经在做原型？这两段时间有没有被分开计量？
  • 可运行原型证明了概念之后，我有没有先问工程需要什么，就直接生成了一份完整规格？
  • 工程师说「看不清要看的那一小部分」时，我是把说明写得更长，还是先请他们标出触发、边界和退路？
  • 套具还能自动的下一件事，是在帮人把产品体验看清楚，还是只因为「能做」就做？
  • 这套工具如果有一天变成交接方式，它是为工程师改过，还是仍停在「方便设计师探索」的形状上？
